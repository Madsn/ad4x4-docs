    Architecture, Request Flow, Auth & Permissions¶

    AI-context reference. Read AGENTS.md first for project overview and the load-bearing gotchas. This file covers request pipeline, JWT auth, and the PermissionMatrix authorisation model.

    Settings modes¶

    Settings live in ad4x4/settings.py. The mode is selected by whether DJANGO_SECRET_KEY is present in the environment:

    • Production — DJANGO_SECRET_KEY env var present → PostgreSQL, Redis, SSL enforced, email SMTP, Bugsink.
    • Development — env var absent → SQLite or local Postgres (via DEV_DB_* vars), in-memory cache, console email, Huey immediate mode (tasks run synchronously).

    Request pipeline¶

    Client (Flutter app / web)
  → HTTPS → nginx (reverse proxy, SSL termination)
  → Gunicorn (WSGI, prod) / manage.py runserver (dev)
  → Django middleware stack (in order):
      SecurityMiddleware → SessionMiddleware → CorsMiddleware → CommonMiddleware
      → CsrfViewMiddleware → AuthenticationMiddleware → MessageMiddleware
      → XFrameOptionsMiddleware → WhitenoiseMiddleware
      → CamelCaseMiddleWare        ← converts snake_case ↔ camelCase
      → CharsetMiddleware           ← adds charset=utf-8 to responses
      → MediaCorsMiddleware         ← CORS wildcard for /uploads/ and /media/
      → LastVisitedMiddleware       ← updates Member.last_visited (throttled 1/hr)
  → DRF authentication:
      JWTAuthentication (custom HS256, see Auth section below)
      → SessionAuthentication (fallback)
  → DRF permission classes (per-view)
  → ViewSet / APIView
  → Service layer (api/services/)
  → Models / ORM
  → PostgreSQL

    CamelCase conversion (critical)¶

    All JSON in and out is camelCase — handled automatically by djangorestframework_camel_case. Write snake_case internally; clients always see camelCase. Only exceptions: password1 and password2 (excluded via JSON_UNDERSCOREIZE).

    Response envelope¶

    // Success
{"success": true, "message": {...}}

// Error
{"success": false, "message": "error description or validation dict"}

// Warning requiring explicit client confirmation before mutation
{"success": false, "message": "trip_overlap_warning", "warnings": [...]}

// Paginated list
{"count": 100, "next": "url", "previous": "url", "results": [...]}

    Pagination¶

    Default 10 per page. Client can pass page_size up to 500.

    Throttling¶

    • Anonymous: 100 req/min
    • Authenticated: 200 req/min

    Authentication & JWT¶

    Library: djangorestframework-simplejwt with the token_blacklist app enabled. Header: Authorization: Bearer <access_token>. Algorithm: HS256 signed with SECRET_KEY.

    Token lifetimes (env-overridable)¶

    • Access token: 24 hours (ACCESS_TOKEN_MINUTES, default 1440)
    • Refresh token: 30 days (REFRESH_TOKEN_DAYS, default 30)

    Rotation¶

    ROTATE_REFRESH_TOKENS=True + BLACKLIST_AFTER_ROTATION=True. Every successful /api/token/refresh/ call returns a new refresh token and blacklists the old one. Reusing the same refresh token twice returns 401. Clients must overwrite their stored refresh token with the response value.

    Token payload¶

    token_type, exp, iat, jti, user_id. Invalidation is via simplejwt's token blacklist, not a token-version counter.

    Custom classes¶

    • api.util.JWTAuthentication — thin simplejwt subclass. Overrides get_user() only to preserve the legacy side effect of touching NotificationSettings on every authenticated request.
    • api.views.views_auth.LoginView — custom login mounted at /api/auth/login/ before rest_registration's URL include. Accepts login / username / email (case-insensitive on all) + password, returns {access, refresh} via RefreshToken.for_user(user) wrapped in the unified envelope.
    • api.views.views_auth.UnifiedTokenObtainPairView / UnifiedTokenRefreshView — wrappers around simplejwt's stock views that return the unified envelope. Mounted at /api/token/ and /api/token/refresh/.
    • api.views.views_auth.LogoutView, LogoutAllView, SessionsView — session management (see below).
    • api.views.views_auth.CustomChangePasswordView — see the gotcha in AGENTS.md: blacklists every refresh token for the user after set_password.

    Login fields¶

    login, username, or email (any of them, case-insensitive) plus password. The same case-insensitive lookup is reused by find_user_case_insensitive_by_send_reset_password_link_data for reset-password.

    Default permission¶

    IsAuthenticatedOrReadOnly (safe methods public by default unless a view overrides).

    Session invalidation¶

    There is no token_version counter — the legacy column was removed (migration 0130). Session invalidation flows through rest_framework_simplejwt.token_blacklist (password change blacklists every outstanding refresh token; see the gotcha in AGENTS.md). Do not reintroduce a token-version mechanism.

    Invalidation semantics¶

    Action Scope Mechanism
    POST /api/auth/logout/ Only the session whose refresh token is in the request body .blacklist() on that one JTI
    DELETE /api/auth/sessions/ (with keep_refresh) All sessions except the one whose refresh token is supplied .blacklist() on every other JTI
    POST /api/auth/logout-all/ Every session including the current one .blacklist() on every JTI for the user
    POST /api/auth/change-password/ Every session including the current one _blacklist_all_user_tokens(user) after set_password
    Refresh token rotated on use Previous refresh JTI invalidated, new one issued BLACKLIST_AFTER_ROTATION=True handles it
    Refresh token expires naturally That one session simplejwt rejects on exp check, no DB work

    Permission system¶

    PermissionMatrix is the authoritative authorisation model. Django Groups + PermissionMatrix records together drive every protected action.

    How it works¶

    1. Each PermissionMatrix row maps a (group, action) pair.
    2. If levels M2M is empty, the permission applies to all member levels (this is the opposite of what you might expect — see AGENTS.md gotchas).
    3. If levels is specified, the permission applies only when the target member is at one of those levels.
    4. PermissionMatrix.has_permission(user, action, member=None, trip=None, require_trip_lead=False) is the single authoritative check.

    Every protected view must add a PermissionMatrix check¶

    When writing a new view that exposes a protected action you must explicitly add PermissionMatrix.has_permission() — do not assume one exists. Do not use Django model-level perms (is_staff, is_superuser) for business logic; those are admin-panel shortcuts only. The rule is not just "don't bypass it" — it's "always add it to every view that needs it."

    Custom permission classes¶

    api/permissions.py contains 30+ DRF permission classes that wrap PermissionMatrix.has_permission() for specific actions and viewsets. Reuse the existing class for your action before inventing a new one.
