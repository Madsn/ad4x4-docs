    Dev Setup, Testing & Commands¶

    AI-context reference. Local dev environment, test recipes, and the day-to-day commands. The MkDocs human walkthrough lives at docs/quick-start.md.

    First-time setup¶

    # Virtual environment
python -m venv venv
source venv/bin/activate          # Unix
# venv\Scripts\activate            # Windows

# Dependencies
pip install -r requirements.txt -r requirements-dev.txt

# Database
python manage.py migrate
python manage.py createsuperuser

# Run
python manage.py runserver

# Background tasks (separate terminal)
python manage.py run_huey

    Swagger UI is at http://localhost:8000/docs/swagger-ui/ once the server is running. MkDocs preview: mkdocs serve.

    Quick command reference¶

    Task Command
    Run dev server python manage.py runserver
    Run background tasks python manage.py run_huey
    Run all tests python -m pytest tests api/tests
    Run with coverage python -m pytest --cov api tests api/tests
    Create migrations python manage.py makemigrations
    Apply migrations python manage.py migrate
    Regenerate OpenAPI schema python manage.py spectacular --file schema.yml
    Build docs mkdocs build
    Sync member level groups (backfill) python manage.py sync_member_level_groups

    Prefer .venv/bin/python (Unix) or venv\Scripts\python.exe (Windows) when the local venv exists — the system Python in some shells does not include the project dependencies.

    Testing with PostgreSQL¶

    • Framework: pytest + pytest-django with DJANGO_SETTINGS_MODULE=ad4x4.settings.
    • Before running tests, unset DJANGO_SECRET_KEY. If it's set, Django switches into production mode and expects the PG_POSTGRES_* settings, Redis, SSL, and production-like services.
    • pytest.ini pins testpaths = tests api/tests so collection doesn't wander into infra/db-data or other runtime folders.
    • Tests run against a local PostgreSQL instance via DEV_DB_* env vars. The configured Postgres user must be able to create and drop test databases; the default Docker postgres user is sufficient.

    Lightweight README dev container¶

    Start it with docker start ad4x4-postgres and:

    unset DJANGO_SECRET_KEY REDIS_HOST REDIS_PORT REDIS_PASSWORD
export DEV_DB_ENGINE=django.db.backends.postgresql
export DEV_DB_DATABASE=dev
export DEV_DB_USER=postgres
export DEV_DB_PASSWORD=postgres
export DEV_DB_HOST=localhost
export DEV_DB_PORT=5432
python -m pytest tests api/tests

    Full infra/docker-compose.yml stack¶

    Start the postgres service. Map PG_POSTGRES_DATABASE / PG_POSTGRES_USER / PG_POSTGRES_PASSWORD from infra/.env into DEV_DB_DATABASE / DEV_DB_USER / DEV_DB_PASSWORD. Use DEV_DB_PORT=15432.

    WSL local-development¶

    The repo's current .env exposes PostgreSQL on localhost:15432 with the credentials in infra/.env.

    Test naming convention¶

    tests/test_<feature>.py — e.g., test_trips.py, test_members.py, test_logbook.py.

    Run before every commit. Coverage: pytest --cov api. Shared fixtures live in test_util/ — TestData factory creates standard test objects (members, levels, trips, upgrade requests, logbook entries, etc.).

    Adding a new resource — checklist¶

    1. Add model to api/models/<name>.py, register in api/models/__init__.py
    2. Create migration: python manage.py makemigrations
    3. Add serializer to api/serializers/serializers_<name>.py
    4. Add view to api/views/views_<name>.py
    5. Register ViewSet in ad4x4/urls.py
    6. Add PermissionMatrix.has_permission() checks
    7. Put business logic in api/services/, not the view
    8. Add Huey task to api/background.py if async work is needed
    9. Register in api/admin.py
    10. Add @extend_schema decorators for Swagger docs
    11. Write tests in tests/test_<name>.py (unless a closer api/tests/ home exists)
    12. Document in docs/<name>.md and add to mkdocs.yml
    13. Update docs/ai-context/*.md per the AGENTS.md self-update rule (only the file whose authoritative content changed)
    14. Regenerate schema.yml

    Agent / Claude Code preferences¶

    • Do not commit automatically. Prompt when changes are ready and wait for explicit approval before git commit.
    • Always run tests before declaring done.
    • No comments unless requested. Follow existing code style.
    • Use existing serializers / views / services before introducing new ones.
    • Regenerate schema.yml after any endpoint change and commit it.

    Machine-specific config¶

    Per-user paths (custom venv locations, machine-specific environment variables) belong in your local Claude Code / Codex config (e.g. .claude/settings.local.json or shell rc), not in checked-in files.
