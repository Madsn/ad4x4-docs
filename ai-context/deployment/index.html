    Deployment, Environment & Disaster Recovery¶

    AI-context reference. Hetzner deployment, Docker stack, env-var inventory, host monitoring, and the DR runbook summary.

    Authoritative operational docs: - infra/README.txt — step-by-step deployment / redeploy runbook (docker build, SSL, DB migrations, FCM path) - infra/.env.example — canonical environment-variable template; ground truth. The list in this file mirrors it but may lag — always verify against .env.example and update both in the same PR when adding a variable. - infra/disaster-recovery/Disaster-README.md — full DR setup + restore procedures.

    Docker stack (production, via infra/docker-compose.yml)¶

    nginx          ← SSL termination, static files, reverse proxy
postgres       ← Primary database
redis          ← Cache + Huey broker
bugsink-db     ← Dedicated Bugsink Postgres database
bugsink        ← Self-hosted Sentry-compatible error tracker
app            ← Gunicorn (Django), built from Dockerapp
huey           ← Huey consumer, built from Dockerhuey

    Hosted on Hetzner. Images are Docker multi-stage Python 3.13 builds.

    CORS / CSRF¶

    Origins allowed (regex): *.codemagic.app, *.ad4x4.com, Novita AI sandbox. CSRF trusted: ap.ad4x4.com, ad4x4.com.

    Media files¶

    Served from /uploads/ path via a custom serve_media view in production (not Whitenoise — that's for static only). Media root: /app/uploads inside the container.

    Error tracking — Bugsink¶

    Bugsink is the production exception target. Django + Huey use sentry-sdk with DjangoIntegration, HueyIntegration, and RedisIntegration when SENTRY_DSN is set. The DSN points at the Bugsink project; the env var keeps the Sentry-compatible name on purpose.

    django.request logs always go to console. AdminEmailHandler 500 emails are enabled when SENTRY_DSN is blank; once Bugsink is configured, they're disabled unless DJANGO_ENABLE_ADMIN_ERROR_EMAIL=true overrides. Operational emails (backup-failure, disk-space) stay on their own channel.

    Sentry SDK is configured not to send request bodies or local frame variables. A before_send hook scrubs common secret-bearing keys, URL query parameters, and key=value breadcrumb strings before they leave the app.

    The default compose deployment keeps Bugsink internal to the Docker network and binds the UI to 127.0.0.1:${BUGSINK_HOST_PORT:-18000} on the host for SSH-tunneled admin access. BUGSINK_BASE_URL should stay set to that admin-accessible URL. Backend ingestion uses a SENTRY_DSN whose host resolves inside Docker (usually bugsink:8000). With the default localhost URL, Bugsink-generated email links are only useful from the VPS or via SSH tunnel; configure a real HTTPS URL before using Bugsink email features.

    Disaster Recovery¶

    Lives under infra/disaster-recovery/. Three files:

    • backup.sh — orchestrates backups of the PostgreSQL database, user uploads, source code, and infra config. Runs under flock so overlapping cron invocations are safe. Builds into /home/admin/backups/staging/ and atomically promotes to /home/admin/backups/latest/ only after a successful run, so a failed backup never leaves the server with zero local copies. Writes /home/admin/backups/backup-status.json after every run (for monitoring) and rotates its log via /etc/logrotate.d/ad4x4-backup. Bugsink issue data is treated as disposable operational telemetry and is not backed up; infra/bugsink-db-data/ and infra/db-data/ (live PostgreSQL data directory) are excluded from infra archives — the database is already captured via pg_dump. The Restic B2 repository is auto-initialised on first run if not found; a warning is added and the Restic step is skipped for that run if initialisation fails.
    • restore.sh — restores a backup to a fresh (or existing) Ubuntu host. Sources: gdrive, koofr, restic, or local. Restore order is source → infra → uploads → database — preserving this order is mandatory, otherwise the source-code extraction (rm -rf $APP_DIR) will wipe out already-restored infra and uploads. Handles both db.sql.gz (current) and db.sql (legacy) dumps. Discovers the postgres container name dynamically.
    • Disaster-README.md — setup instructions, fresh-VM quick restore, manual restore procedures.

    Backup targets and retention¶

    Target Tool Snapshots kept
    Google Drive (gdrive:ad4x4-backups) rclone 2 most-recent snapshots + incremental uploads sync
    Koofr (koofr:ad4x4-backups) rclone 2 most-recent snapshots + incremental uploads sync
    Backblaze B2 (b2:hetzner-ad4x4:/restic-backups) restic 24 hourly / 3 daily / 2 weekly / 1 monthly (encrypted)
    Local plain filesystem 1 (latest/ only — no timestamped local folders)

    Schedule: every 6 hours via cron (infra/disaster-recovery/crontab-example.txt).

    Critical DR gotchas¶

    • Restic encrypts on B2, but Google Drive and Koofr receive plaintext db.sql.gz and tarballs. Anyone with access to those accounts can read everything.
    • The source-code archive is created with tar -C /home/admin ad4x4, so its entries begin with ad4x4/. On restore it must be extracted to $(dirname "$APP_DIR") (= /home/admin), not $APP_DIR itself — otherwise files land at /home/admin/ad4x4/ad4x4/....
    • restore.sh local always uses $BACKUP_ROOT/latest regardless of any timestamp argument, because the backup script no longer retains timestamped local copies.
    • Changing pg_dump output format requires updating restore.sh at the same time — both sides must agree on db.sql.gz vs db.sql vs -Fc custom format.
    • Migration 0085 (migrate_car_fields_to_vehicles) is effectively one-way. Its reverse_migration references Member.car_brand/car_model/car_year/car_color/car_image — columns that the subsequent migration 0086 removes. Rolling back past 0085 after 0086+ has applied will fail with AttributeError. If a rollback past this point is ever needed, restore the database from backup rather than running migrate --backwards.

    Host monitoring¶

    infra/monitoring/check-disk-space.sh is a host-level cron script for Hetzner VPS disk-space alerts. It parses only the needed keys from /home/admin/ad4x4/infra/.env, checks DISK_ALERT_PATHS, and sends email via the host mail command to DISK_ALERT_EMAIL or BACKUP_NOTIFY_EMAIL. Defaults alert at 85% usage or less than 2GB free, and suppress repeated emails for 6 hours while the condition remains active. The recommended cron entry is in infra/disaster-recovery/crontab-example.txt, which also creates /home/admin/monitoring before running.

    Maintenance mode¶

    Nginx-level 503 gate with admin-URI bypass; an optional API bypass allows either a bot-managed external IP whitelist match or the configured secret header. Wired up via MAINTENANCE_BYPASS_* env vars; the monitor bot can manage the bypass files at runtime when given the right privileges.
