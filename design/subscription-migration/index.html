    AD4x4 — Subscription Model Migration: Joint Design Doc & Work Breakdown¶

    ON HOLD — reverted to one-time lifetime payment (2026-06-16, issue #169). The rolling 12-month subscription model described below was implemented and then rolled back to a one-time lifetime payment (Member.paid_member is the source of truth; no expiry/lapse/renewals). This doc is retained as the canonical reference for reviving subscriptions in the future. Reusable plumbing that survived the rollback (PayPal one-time orders, SubscriptionPaymentEvent audit trail, exempt groups, treasurer export, receipts, and the 3-state gating_mode) is still in the codebase; the expiry/reminder/grace layer was removed.

    Status: Design — not yet approved for implementation Audience: Backend team (Madsn/ad4x4-backend) and Flutter team (Hani-AMJ/Ad4x4-Flutter-App) Date: 2026-05-28 Goal of this doc: Make the next two implementation sessions (one per repo) executable without further design work. Endpoint-level detail is given where it pins down the contract; everything else stays architectural.

    This is the canonical copy. An identical copy lives in the Flutter repo at docs/design/subscription-migration.md. Keep them in sync, or collapse to one if the teams adopt a shared docs location.

    ⚠️ v1 scope update (2026-06-04) — one-time annual pass, not recurring¶

    Per the 2026-05-30 cross-stack session, v1 ships a one-year, non-auto-renewing "annual pass": pay once → +12 months → manual re-purchase. PayPal auto-renew (the Subscriptions API: Products → Billing Plans → Subscriptions, cancel, suspension/dunning, drift reconciliation) is deferred to Phase 2.

    What this means for the sections below, which were written around the Subscriptions API: - The backend implements the pass by reusing the existing one-time PayPal order flow in website/ (create_order/capture_order, PAYMENT.CAPTURE.COMPLETED). On capture it grants +12 months (grant_annual_pass, idempotent on the order id) and writes a SubscriptionPaymentEvent. - Not built in v1: MembershipSubscription, the Subscriptions-API client, POST /api/subscription/cancel, the /api/paypal/subscription-webhook, and the nightly reconciliation task. GET /api/subscription therefore omits paypalSubscriptionId/cancelAtPeriodEnd. - Added beyond the original doc (both clients asked for these): a computed reason field (exempt/paid/grandfathered/comped/lapsed) and a backend-owned gatedActions[] list (admin-configurable via ConfigurableSettings.gated_actions), both surfaced on GET /api/subscription. - Everything else (computed status + exempt-by-group, the subscription_required gate on sign-off/upgrade, kill-switch, grandfather grant command, T-30/7/1/0 reminders, treasurer CSV) is unchanged and as described below.

    The recurring implementation is preserved on branch archive/subscription-recurring-impl should Phase 2 pull it forward.

    0. TL;DR¶

    We are replacing the single lifetime paid_member boolean with a rolling 12-month subscription keyed off a per-member expiry date. Members renew via PayPal. Access to a small set of features is gated when a member lapses. Existing members are all granted a free 1-year subscription at launch so nobody is locked out on day one.

    Three things make this more than a CRUD change:

    1. PayPal exists but as one-time orders, not subscriptions. We must build on PayPal's Subscriptions API (Products → Billing Plans → Subscriptions) and a new webhook path. The current one-time-order flow in the website app does not update paid_member and is not reusable as-is.
    2. Payment is web-only — no in-app purchase, by decision (avoid the 30% Apple/Google fee). The app never sells anything: it is a neutral gate + status display. All renewal CTAs, links, and pricing live in email and on the website (which Apple/Google don't govern). This constrains in-app gating copy — see §13 for the binding rules.
    3. The gating contract must be designed once and consumed by both clients. A single computed subscription_status field + a single structured 403 error code is the contract both teams build against.

    1. Goals & Non-Goals¶

    Goals¶

    • Move membership from lifetime boolean to annual, rolling-from-payment-date subscription.
    • No grace period — gating applies the instant expires_at passes.
    • Backend-enforced gating on logbook skill sign-off (gate the signee) and upgrade-request submission (gate the applicant), with a structured, client-routable error.
    • Client-side gating (cosmetic/UX, not security) on analytics, member directory, and logbook UI — shown as a locked state, never a redirect or raw 403.
    • PayPal-driven subscribe / view / cancel / payment-history, managed from the client.
    • Renewal nudges: in-app banner + email at T-30, T-7, T-1; expiry notice at T-0; lapsed banner thereafter.
    • Exemption by Django group membership, configured via a global setting.
    • Audit trail of all payment/subscription events + treasurer CSV export + member-facing own-history endpoint.
    • Migration: grant every existing member a 1-year subscription at launch.
    • Operate via Django admin for overrides/comps/manual-paid — no new admin UI in the client for v1.

    Non-Goals (v1)¶

    • No multi-year prepay.
    • No tiered pricing — single annual price.
    • No refunds in v1 (policy assumption — see Q7).
    • No new admin UI in the Flutter client.
    • No in-app purchase / IAP. Payment is web-only by decision (avoid the 30% store fee). The app shows status and gates features but never initiates, links to, or describes a purchase (see §13).
    • No localization of subscription copy (app is English-only today; see Flutter §8).
    • Flutter implementation is out of scope for the backend session and vice-versa — but the shared contract below is binding on both.

    3. The Shared Contract (binding on both repos) — read this first¶

    Everything below derives from these three primitives. Implement them once; both clients consume them.

    3.1 subscription_status (computed, authoritative, server-side)¶

    A member's status is computed (never stored as a status string — only the inputs are stored):

    def compute_status(member, now):
    if member.groups ∩ settings.subscription_exempt_groups:  return "exempt"
    if member.subscription_expires_at and member.subscription_expires_at > now:  return "active"
    return "lapsed"
    • exempt always wins over expiry. An exempt member is never gated regardless of expires_at.
    • lapsed is the only state that triggers gating.
    • The client never recomputes exemption — it trusts the server's subscription_status. It may locally derive "expiring soon" from expires_at for banners.

    3.2 Profile / member serializer additions¶

    Add to the profile + member serializers (api/serializers/serializers_member.py):

    {
  "subscription_status": "active",          // "active" | "lapsed" | "exempt"
  "subscription_expires_at": "2027-05-28T00:00:00Z",  // null for exempt or never-subscribed
  "subscription_days_remaining": 365,       // convenience int; null when not applicable
  "paid_member": true                       // DEPRECATED shim, kept for old clients (see §4)
}

    Flutter must add subscriptionStatus, subscriptionExpiresAt, subscriptionDaysRemaining to UserModel (and to BasicMember/ConciseMember/MarshalDirectoryMember where the badge/filter is shown), accepting both snake and camel case as it does today.

    3.3 The gating error¶

    Backend-gated endpoints return HTTP 403 with:

    { "detail": "An active subscription is required.", "code": "subscription_required", "expiresAt": "2026-05-01T00:00:00Z" }
    • code is the routable discriminator — both clients branch on code == "subscription_required", not on the 403 status alone (other 403s exist, e.g. missing_sign_logbook_skills_permission).
    • expiresAt lets the client show "expired on …" in the paywall.
    • Implemented as a custom PermissionDenied subclass so DRF serializes the extra fields (see §6.3).

    4. Data Model Changes (backend)¶

    4.1 Member (modify) — api/models/models_member.py¶

    • Add subscription_expires_at = models.DateTimeField(null=True, blank=True, db_index=True) — the single denormalized field gating reads (fast, indexed). Source of truth for "active vs lapsed".
    • Keep paid_member as a deprecated compatibility shim through the transition: keep it written in sync (paid_member = status in {active, exempt}) so un-upgraded app builds keep working. Plan to drop it one or two releases after the client is fully migrated. Do not read it in any new code.
    • Note: level, trip_count, groups unchanged. Exemption is derived from groups, not a stored flag.

    4.2 MembershipSubscription (new) — api/models/models_subscription.py¶

    One row per member tracking the live PayPal subscription: - member (OneToOne → Member) - paypal_subscription_id (Char, unique, null until subscribed) - paypal_plan_id (Char — which billing plan) - status (choices: active, cancelled, suspended, expired) — mirrors PayPal subscription state - current_period_start, current_period_end (DateTime) - cancel_at_period_end (bool) — set true when member cancels but retains access (see Q3) - created_at, updated_at

    Member.subscription_expires_at is denormalized from current_period_end (or from a manual/migration grant). The subscription row may be absent for comp'd/migrated members who never went through PayPal — that's fine; gating only needs subscription_expires_at.

    4.3 SubscriptionPaymentEvent (new, append-only) — the audit trail¶

    This is the record for audit, member history, and treasurer export. Immutable, append-only. - member (FK → Member) - subscription (FK → MembershipSubscription, nullable for manual/migration) - event_type (choices: payment_completed, subscription_activated, subscription_cancelled, subscription_suspended, subscription_expired, manual_grant, migration_grant, comp, refund) - source (choices: paypal_webhook, manual_admin, migration) - paypal_event_id (Char, unique, nullable) — idempotency key for webhooks - amount (Decimal, nullable), currency (Char, default from settings) - payer_email (Email, nullable) - period_end_after_event (DateTime, nullable) — what expires_at became as a result; makes history human-readable and reconstructable - created_by (FK → Member, nullable) — admin who took a manual action - raw_payload (JSONField, nullable) — full webhook body for forensics - occurred_at (DateTime), created_at (auto)

    We deliberately do not reuse website.WebsitePayment (one-time-order shaped, lives in a different app, tied to the legacy flow). New events get their own model in api. If desired, a one-off backfill can import historical WebsitePayment rows as comp/manual_grant events, but that's optional.

    4.4 Removed / deprecated¶

    • paid_member: deprecated shim, removed in a later release.
    • Legacy website one-time PayPal order flow: left in place but not extended; superseded by subscriptions. Decide separately whether to retire it.

    5. Global Settings Additions — ConfigurableSettings (api/models/models_util.py)¶

    Add these fields. They are edited via Django admin only (no client UI — see Q5). Keep them out of the editable API serializer; optionally expose annual_subscription_price/_currency read-only if the web front end needs to show the price.

    Field Type Notes
    subscription_exempt_groups M2M → Group (blank) Serialized as list[int] of group IDs. M2M (not raw int list) for referential integrity, matching the existing FK-to-Group pattern (default_user_group, Level.auto_group). A member is exempt if in any of these.
    annual_subscription_price Decimal Single price, no tiers.
    annual_subscription_currency Char(3) e.g. AED.
    paypal_plan_id Char The active PayPal Billing Plan id.
    paypal_product_id Char The PayPal Catalog Product id.
    subscription_gating_enabled Bool (default False) Kill-switch. When false, no endpoint enforces gating — used for safe cutover/rollback (see §12).
    subscription_reminders_enabled Bool (default True) Pause nudges without code change.

    PayPal API credentials (client id/secret, webhook id) stay in env/secret settings and are excluded from the serializer, exactly like the existing excluded fields (email_*, default_user_*, notification_dry_run).

    Permission to edit (Q5) — DECIDED: Managed in Django admin only (gated by is_staff/superuser). No new permission, and these fields are not editable through the API. CanEditGlobalSettings/EDIT_GLOBAL_SETTINGS are untouched.

    6. API Contract Changes¶

    6.1 New member-facing endpoints¶

    Method & path Purpose Auth Response (shape)
    GET /api/subscription Current user's subscription summary self {status, expiresAt, daysRemaining, price, currency, paypalSubscriptionId, cancelAtPeriodEnd}
    POST /api/subscription/subscribe Create a PayPal subscription, get approval link self {approvalUrl, paypalSubscriptionId}
    POST /api/subscription/cancel Cancel the PayPal subscription self {status, cancelAtPeriodEnd, expiresAt}
    GET /api/subscription/payments Member's own payment history (paginated) self list of {occurredAt, eventType, amount, currency, periodEndAfterEvent}

    subscribe example:

    // POST /api/subscription/subscribe   (no body; plan/price come from settings)
// 201
{ "approvalUrl": "https://www.paypal.com/checkoutweb/...", "paypalSubscriptionId": "I-XXXX" }

    The client opens approvalUrl (browser/WebView), the user approves, PayPal fires BILLING.SUBSCRIPTION.ACTIVATED → backend sets expires_at. The client then re-fetches /api/subscription (or profile) to see active.

    6.2 New admin / treasurer endpoints¶

    Method & path Purpose Permission
    GET /api/admin/subscription-payments/export?from=YYYY-MM-DD&to=YYYY-MM-DD&format=csv Treasurer export of payment events in a range new EXPORT_SUBSCRIPTION_PAYMENTS action, or reuse EDIT_MEMBERSHIP_PAYMENTS — flag for confirmation
    GET /api/subscription/payments/{event_id}/receipt Printable HTML receipt / tax invoice for one payment (#158) owner, or EXPORT_SUBSCRIPTION_PAYMENTS
    POST /api/paypal/subscription-webhook PayPal subscription webhook intake AllowAny + signature verification (§9.4)

    The export is also available as a Django admin action on SubscriptionPaymentEvent (no client UI needed). CSV columns: member_id, member_name, occurred_at, event_type, source, amount, currency, payer_email, paypal_event_id, period_end_after_event, tax. The tax column is populated (#158) with the VAT backed out of each priced event per the configured vat_rate/vat_inclusive; blank for non-priced events (comps/grants). VAT details (club_legal_name, club_address, vat_registration_number, vat_rate, vat_inclusive) live on ConfigurableSettings. Until the treasurer confirms VAT practice the rate defaults to 0, so the column reads 0.00 and receipts show a 0.00 VAT line — see #158.

    6.3 Modified: manual "mark paid" endpoint¶

    The existing POST /api/members/<id>/payments flips a boolean. Re-purpose its semantics (keep the route):

    // New write payload (admin, HasEditMembershipPaymentsPermission)
{ "grant_months": 12 }            // extend expires_at by N months from max(now, current expires_at)
// or
{ "expires_at": "2027-05-28T00:00:00Z" }   // set explicitly (comp / correction)

    Both create a SubscriptionPaymentEvent (source=manual_admin, event_type=manual_grant/comp, created_by=request.user). Keep accepting the legacy {payment_received: true} for one release: true → grant_months: 12, false → set expires_at = now (immediate lapse). This preserves any tooling still posting the old shape.

    6.4 Modified serializers¶

    • ProfileSerializer + member list/detail serializers: add the three subscription fields from §3.2.
    • Admin members list filter: alongside the legacy paidMember=true/false, add ?subscription_status=active|lapsed|exempt so the Flutter admin filter (PaidFilter) can migrate to status.

    6.5 New error code¶

    subscription_required — the only new code. See §3.3. Register it in the OpenAPI schema (drf-spectacular) so both clients have a typed reference.

    6.6 Backend-Enforced Gating (where & how)¶

    Surface Gate on Where Behavior
    Logbook skill sign-off the signee (member in the payload), not the signer/request.user LogbookEntryViewSet.create() (views_logbook.py:176) and TripLogbookEntryCreateView — after resolving member, before perform_create If signee lapsed → 403 subscription_required with signee's expiresAt. Signer status irrelevant. Only blocks when skill_references are present (pure comment entries need no skills — confirm with product whether comment-only entries should also be allowed; default: only block when skills are being signed).
    Upgrade application the applicant (request.user for self-requests) UpgradeRequestViewSet.create() (views_upgraderequest.py:39) If applicant lapsed → 403 subscription_required.
    In-flight upgrade requests gate at creation only approve/decline views are not gated Do not auto-decline when an applicant lapses mid-flight. The board may approve or decline as normal, and an approval applies (level changes) even if the applicant is currently lapsed (Q2 — DECIDED). Rationale: gating happens once, at request creation; after that the board's decision is sovereign.
    Everything else (trips, profile, chat, directory APIs, etc.) — — Ungated. Lapsed members still register for trips at their level; trip history keeps recording.

    Because the logbook gate keys off a payload field (the signee) rather than request.user, it cannot be a vanilla DRF permission_class (those inspect request.user). Implement a small helper assert_subscription_active(member) used inline. The upgrade gate keys off request.user, so it can be a permission class or the same inline helper — use the helper for consistency.

    6.3 Error shape implementation¶

    # api/exceptions.py
from rest_framework.exceptions import PermissionDenied
class SubscriptionRequired(PermissionDenied):
    def __init__(self, expires_at=None):
        super().__init__(detail={
            "detail": "An active subscription is required.",
            "code": "subscription_required",
            "expiresAt": expires_at.isoformat() if expires_at else None,
        })

    DRF renders the dict as the 403 body verbatim.

    7. Migration / Cutover Plan¶

    7.1 Grant script (idempotent management command)¶

    python manage.py grant_launch_subscriptions --launch-date=YYYY-MM-DD [--dry-run] [--scope=active|paid] - For each member in scope: set subscription_expires_at = launch_date + 365 days; write a SubscriptionPaymentEvent(source=migration, event_type=migration_grant, period_end_after_event=…). - Idempotent: skip any member that already has a migration_grant event. Safe to re-run. - Also sync the paid_member shim.

    Scope decision (Q1 — DECIDED): Grant the free year to currently paid members only (paid_member=True). Run as --scope=paid. Members who were never paid start lapsed at launch and must subscribe via the web to gain access. (This is why the cutover step below uses --scope=paid.)

    7.2 Order of operations (critical)¶

    1. Deploy backend with subscription_gating_enabled = False (data fields live, enforcement dormant).
    2. Run grant_launch_subscriptions --scope=paid → every currently-paid member has expires_at = launch + 365d.
    3. Verify (spot-check statuses, run with --dry-run first).
    4. Release the Flutter build that understands subscription_status.
    5. Flip subscription_gating_enabled = True.

    Gating is never enabled before the grant completes, so no paid member is ever wrongly locked out during cutover. Members who were never paid will be lapsed once gating is on — that's intended; they subscribe via the web.

    8. Client-Side Gating + UX Surface Inventory (Flutter)¶

    Client gating is cosmetic/UX only — the backend is the security boundary. The client reads subscription_status from the profile and reacts.

    Store-compliance rule (binding — see §13): because payment is web-only/no-IAP, the app must not contain any purchase CTA, link, price, or "pay/renew on the website" instruction. In-app copy is informational only. All renewal CTAs/links/pricing live in email (and on the website). So everywhere below that previously said "Renew CTA", read "informational notice, no button/link."

    8.1 Site-wide lapsed banner¶

    9. Notification / Reminder Job Design¶

    9.1 Where it runs¶

    A new Huey periodic task periodic_subscription_reminders() in api/background.py, scheduled daily (propose 09:00 local), gated by subscription_reminders_enabled and respecting notification_dry_run. Fans out via the existing NotificationManager (email is required; push optional reuse of the FCM channel).

    9.2 What triggers each nudge¶

    For every non-exempt member with a non-null subscription_expires_at:

    days = (expires_at.date() - today).days
days == 30 → T-30 reminder (email + in-app)
days == 7  → T-7 reminder
days == 1  → T-1 reminder
days == 0  → expiry notice (T-0)
days < 0   → no email; client shows lapsed banner from status

    In-app banners are derived client-side from subscriptionExpiresAt (no server push needed for the banner itself); the four emails are what the job sends.

    9.3 Idempotency¶

    Use the existing NotificationLog keyed by (member, reminder_type, period_end_date). Before sending, check for an existing log row for this (member, T-bucket, current period_end); skip if present. This makes the job safe to run more than once a day and across deploys, and prevents a second email if the member renews and re-enters a bucket (new period_end ⇒ new key, which is correct — a renewed member legitimately gets future reminders for the new period).

    9.4 Email templates¶

    Four new templates under templates/emails/ (matching the existing email convention): subscription_reminder_30.html, _7, _1, subscription_expired.html. These emails carry the renewal CTA, the web renewal link, and the price — email is the primary renewal channel precisely because it sits outside the app stores' purchase-steering rules (§13). Link to the website renewal page, not an app deep-link.

    10. PayPal Integration Architecture¶

    Current code does one-time orders. Subscriptions are a different PayPal API surface. Treat this as new, not an extension of website/views.py.

    10.1 One-time setup (manual, recorded in settings)¶

    1. Create a Catalog Product (the "AD4x4 Annual Membership"). Store paypal_product_id.
    2. Create a Billing Plan (annual, fixed price = annual_subscription_price/annual_subscription_currency). Store paypal_plan_id.
    3. If price changes later, create a new plan and swap paypal_plan_id; existing subscribers stay on their plan until they re-subscribe.

    10.2 Subscribe flow¶

    1. Client POST /api/subscription/subscribe.
    2. Backend calls PayPal Create Subscription with paypal_plan_id + a custom_id = member.id (so the webhook can map back) + return/cancel URLs.
    3. Backend persists a MembershipSubscription row (status pending) and returns the approvalUrl.
    4. User approves in PayPal.
    5. PayPal fires BILLING.SUBSCRIPTION.ACTIVATED → webhook sets subscription active, sets current_period_*, sets Member.subscription_expires_at, writes a subscription_activated event.

    10.3 Webhook events handled (POST /api/paypal/subscription-webhook)¶

    PayPal event Action
    BILLING.SUBSCRIPTION.ACTIVATED mark active; set expires_at = current_period_end; event subscription_activated.
    PAYMENT.SALE.COMPLETED (recurring renewal) extend expires_at to new current_period_end (rolling 12 months from this payment); event payment_completed with amount/payer_email.
    BILLING.SUBSCRIPTION.CANCELLED mark cancelled, set cancel_at_period_end=True; retain expires_at (Q3); event subscription_cancelled.
    BILLING.SUBSCRIPTION.SUSPENDED mark suspended; event recorded; access continues until expires_at.
    BILLING.SUBSCRIPTION.EXPIRED mark expired; event recorded (gating then follows from expires_at).

    10.4 Webhook security (Q6)¶

    • Signature verification: verify every webhook via PayPal's verify-webhook-signature API using the stored webhook_id + transmission headers. Reject unverified.
    • Idempotency: SubscriptionPaymentEvent.paypal_event_id is unique; an INSERT conflict ⇒ already processed ⇒ ack 200 and no-op.
    • Fast ack + async work: return 200 immediately after persisting the raw event, then process in a Huey task (PayPal retries non-200, so cheap-ack avoids duplicate processing storms while idempotency covers genuine retries).
    • custom_id mapping: trust custom_id = member.id from the subscription, not payer email, to attribute events.

    10.5 Reconciliation¶

    Nightly Huey task queries PayPal for the status of all active/suspended subscriptions and corrects any drift from missed webhooks (sets expires_at/status to match PayPal). This is the safety net for webhook delivery gaps.

    11. Audit / Export Design¶

    • Audit trail = SubscriptionPaymentEvent (append-only, §4.3). Every state change — webhook, manual admin action, migration grant, comp — writes one row with source, created_by, and raw_payload. Register it read-only in Django admin with filters by event_type/source/date.
    • Member-facing history = GET /api/subscription/payments — the member sees only their own events (subset of columns; no raw_payload, no other members).
    • Treasurer export = §6.2 endpoint + Django admin action → CSV for a date range. The tax column and the per-payment receipt endpoint are implemented and VAT-aware (#158), driven by the vat_* / club_* settings on ConfigurableSettings; they default to a 0% no-op until the treasurer confirms the rate, inclusive/exclusive handling, and TRN.

    12. Rollout & Rollback¶

    • Kill-switch: subscription_gating_enabled (settings, default False). Enforcement everywhere checks it first. Rollback = flip it False — instant, no deploy; all expires_at data is retained and the paid_member shim keeps old clients working.
    • Reminders kill-switch: subscription_reminders_enabled.
    • Cutover order: §7.2.
    • Data rollback: the migration grant is recorded as events; if we must reverse, a counter-command can null expires_at, but with gating off there's rarely a need. The grant command is idempotent and re-runnable.
    • PayPal: run in sandbox first (PayPalConfiguration.sandbox_mode precedent) end-to-end before switching live credentials.

    13. Store Compliance (web-only payment)¶

    DECIDED. Payment is web-only — no in-app purchase on either platform — to avoid the 30% Apple/Google fee. The Flutter app is a neutral status + gating client; it never sells, prices, or links to a purchase. This is the Spotify/Netflix "reader-style" posture and is the lowest store-rejection risk provided the in-app copy follows the rules below.

    Binding rules for anything shipped in the app (iOS and Android): - ❌ No buy / subscribe / renew / upgrade-to-pay buttons or CTAs. - ❌ No links to PayPal or the renewal page (no deep links, no url_launcher to the payment page). - ❌ No prices, discounts, or "X AED / year" anywhere in the app. - ❌ No instructions that steer to an external purchase ("pay on ad4x4.com", "renew on our website"). - ✅ Allowed: state that a feature requires active membership; show the member's own status and expiry date (account info); show read-only payment history. - ✅ All purchase steering — CTA, link, price — lives in EMAIL and on the website, which Apple/Google do not govern. Email is the renewal channel (§9.4).

    Consequences already folded into this doc: §8.1 banner is informational (no button); §8.5 is a view-only status page (no subscribe/cancel UI in-app); §8.6 splits copy into compliant in-app text vs. full-CTA email; the existing logbook gate's "no payment links" comment becomes the rule, not an exception.

    Caveat to monitor: even mentioning that membership is purchased elsewhere can draw scrutiny under guideline 3.1.3 anti-steering. Keep in-app copy to "members-only feature" framing and let email do the selling. Re-check current App Store / Play policy at submission time, as anti-steering rules have been shifting.

    Remaining risks¶

    1. PayPal subscriptions are new surface area, not a tweak to the existing one-time flow. Budget for plan setup, webhook verification, and reconciliation. The subscribe/cancel flow is driven from the web front end (not the app).
    2. Webhook delivery gaps → mitigated by reconciliation (§10.5) and idempotency.
    3. Exempt-list mis-config could silently un-gate or over-gate large groups. Editing is permissioned and changes are visible; consider logging exempt-list edits.
    4. The web renewal front end is now load-bearing — it's the only purchase path. Confirm it exists / is in scope (the backend subscribe/cancel endpoints assume a web caller). If there's no web UI yet, that's a new work item outside both repos.

    15. Open Questions¶

    Q1. Migration scope — ✅ DECIDED¶

    Do paid_member=False members also get the free year, or only paid_member=True? DECISION: Currently paid members only (paid_member=True). Run grant_launch_subscriptions --scope=paid. Never-paid members start lapsed and subscribe via the web. (See §7.)

    Q2. Approved-while-lapsed upgrade requests — ✅ DECIDED¶

    If the board approves an upgrade after the applicant lapsed, does it take effect? DECISION: It applies (level changes) even if the applicant is currently lapsed. Gating is enforced only at upgrade-request creation; once a request exists, the board's verdict is sovereign and handle_upgrade_request_verdict() applies the level normally. No special-casing in the approve path. (See §6.6.)

    Q3. Cancellation semantics — ✅ DECIDED¶

    Cancel mid-period → access through expires_at or immediate cutoff? DECISION: Retain access through expires_at (cancel_at_period_end=True, no proration, no refund). The PayPal BILLING.SUBSCRIPTION.CANCELLED handler marks the subscription cancelled but leaves subscription_expires_at untouched. (See §10.3.)

    Q4. Exempt-group transitions mid-period — ✅ DECIDED¶

    Added to an exempt group while lapsed → instantly exempt? Removed from all exempt groups → what expires_at? DECISION (as proposed): Exemption is computed live from current group membership — adding a member to an exempt group makes them exempt immediately (no data write, no recompute job). Removing them from all exempt groups falls back to their stored subscription_expires_at, i.e. whenever their last payment was received. If that date is null or already past, they are immediately lapsed. No invented default expiry, no grace window (a comp would be a manual grant_months action).

    Q5. Permission for editing exempt-group list — ✅ DECIDED¶

    New permission or existing one? DECISION: No new permission. There is no client UI for subscription settings — the exempt-group list, annual price, plan IDs, and gating flag are managed in Django admin (already gated by Django's is_staff/superuser). Consequence: keep these new fields out of the editable API serializer (the subscribe/status endpoints don't need write access to them), or expose price/currency read-only if the web front end needs to display it. No EDIT_SUBSCRIPTION_SETTINGS action; CanEditGlobalSettings is untouched.

    Q6. PayPal webhook security¶

    Signature verification, idempotency, retries — designed in §10.4. No open decision; called out as a backend concern.

    Q7. Refund / dispute flow¶

    Out of scope v1. Policy assumption: no refunds; disputes/chargebacks handled manually in PayPal, and an admin can manually adjust expires_at (recorded as a refund/comp event) if needed. Confirm the no-refund policy.

    Q8. Flutter parity / shared contract¶

    The binding contract for Flutter is §3: the subscription_status field (active/lapsed/exempt), the subscription_required 403 code with expiresAt, and the exempt-group concept (client never recomputes — it trusts the server status). Flutter implementation is tracked in §8 and §14; it is out of scope for the backend session but unblocked by Phase 1.
