    Feedback System¶

    This document describes the feedback submission API. It lets authenticated members report bugs, request features, ask for help, or send general comments. Each submission is stored in the database and a notification is dispatched to administrators via the configured channels (Telegram / email / push).

    Overview¶
    Model Feedback (api/models/models_feedback.py)
    Serializer FeedbackSerializer (inline in api/views/views_feedback.py)
    Create endpoint POST /api/feedback/ (router-registered FeedbackCreateAPIView)
    List-by-member endpoint GET /api/members/{id}/feedback — no trailing slash
    Notification task send_feedback_notification — Huey @task, 2 retries, 5-minute delay

    Model Fields¶

    Wire field (camelCase) Internal (snake_case) Type Required on create Returned by the API Notes
    feedbackType feedback_type enum (see below) No — defaults to general Yes One of bug, feature, general, support
    message message string Yes Yes Free-form text; TextField with no enforced length limit
    image image file (image) No Yes (as an absolute URL, or null) Single image; see File Uploads
    (set server-side) user member FK n/a — auto-filled from the authenticated user not returned
    (set server-side) timestamp datetime n/a — auto_now_add not returned Used for default ordering (newest first)

    Feedback Types¶

    Value (wire + DB) Label (for UI display)
    bug Bug Report
    feature Feature Request
    general General Feedback (default if omitted)
    support Help / Support

    The API accepts and returns the code ("bug"), never the label. If your UI needs the human-readable label, map the code client-side — the label is not exposed by a /api/choices/ endpoint.

    1. Submit Feedback¶

    POST /api/feedback/
    Authentication Bearer JWT required
    Permission Any authenticated user
    Throttle 200 req/min per authenticated user — see Rate Limiting
    Content-Type application/json or multipart/form-data (use multipart only when attaching an image)

    Request body (JSON — no image)¶

    {
    "feedbackType": "bug",
    "message": "The trip registration button is unresponsive on iOS 17."
}

    Request body (multipart/form-data — with image)¶

    curl -X POST https://ap.ad4x4.com/api/feedback/ \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "feedbackType=bug" \
  -F "message=Registration button unresponsive on iOS 17" \
  -F "image=@screenshot.png"

    camelCase applies to multipart form fields, not just JSON. DRF's CamelCaseMultiPartParser and CamelCaseJSONParser (wired into DEFAULT_PARSER_CLASSES in ad4x4/settings.py) translate the wire-format feedbackType into the internal feedback_type for you. Do not send feedback_type in multipart — the parser will treat it as an unknown field and drop it, which leads to the default (general) being saved instead.

    Success response (201 Created)¶

    {
    "success": true,
    "message": {
        "feedbackType": "bug",
        "message": "The trip registration button is unresponsive on iOS 17.",
        "image": "https://ap.ad4x4.com/uploads/feedback_images/2026/04/screenshot_3f4a2b8c.png"
    }
}
    • image is null when the submission didn't include one.
    • user and timestamp are recorded on the server but deliberately not returned — the client already knows who submitted it, and the server time is not exposed.

    Error response (400 Bad Request — validation failure)¶

    {
    "success": false,
    "message": {
        "feedbackType": ["\"invalid\" is not a valid choice."],
        "message": ["This field is required."]
    }
}

    On validation failure, the message field holds DRF's standard error dict, keyed by the offending wire-format field name. Keys are camelCased.

    Error response (401 Unauthorized)¶

    {
    "success": false,
    "message": "authentication_credentials_were_not_provided"
}

    Returned when the Authorization header is missing, the access token has expired, or the refresh token backing the session has been blacklisted (for example after a logout or a password change — all outstanding sessions are invalidated on password change). See API Concepts → Authentication for the full invalidation semantics.

    2. List a Member's Feedback¶

    GET /api/members/{id}/feedback — no trailing slash
    Authentication Bearer JWT required
    Permission You may read your own feedback only ({id} must match your own member ID), unless you are a superuser — in which case any member's feedback is visible. Regular permission-matrix roles do not grant access.
    Response Paginated — uses the project-wide StandardResultsSetPagination

    Returns the feedback items submitted by the specified member, most recent first.

    Query parameters¶

    Parameter Type Default Description
    page integer 1 Page number to retrieve
    page_size integer 20 Items per page (max 500). Note: query-string parameters are not camelCase-converted — use the snake_case name here.

    Response (200 OK)¶

    This endpoint uses the standard DRF pagination envelope, not the {success, message} wrapper used by the create endpoint:

    {
    "count": 27,
    "next": "https://ap.ad4x4.com/api/members/42/feedback?page=2",
    "previous": null,
    "results": [
        {
            "feedbackType": "bug",
            "message": "Still broken on iOS 17",
            "image": null
        },
        {
            "feedbackType": "feature",
            "message": "Would love a dark mode option",
            "image": "https://ap.ad4x4.com/uploads/feedback_images/2026/04/mockup_8d2e1f0a.png"
        }
    ]
}

    Error responses¶

    • 401 Unauthorized — missing or invalid JWT (same shape as the create endpoint).
    • 403 Forbidden — authenticated, but trying to read another member's feedback without superuser privileges: json { "detail": "You do not have permission to perform this action." } (This endpoint emits DRF's default {"detail": ...} on 403, not the unified {success, message} envelope. Frontend code should handle both shapes.)
    • 404 Not Found — no member exists with the given {id}.

    File Uploads¶
    Wire field image (single file — the model has one ImageField, not a many-to-many relation)
    Content-Type multipart/form-data (required only when attaching an image; otherwise send JSON)
    Accepted formats Anything Pillow can decode — JPEG, PNG, WebP, GIF, BMP, TIFF. Django's ImageField verifies that the upload is a real image and rejects other file types with a 400.
    Size limit No size validation is performed in Django. The effective cap is 20 MB, imposed by nginx's client_max_body_size 20M (infra/nginx/secure/default.conf.template:66). Uploads larger than that will be rejected by nginx with a 413 Payload Too Large before the request reaches Django. Resize or recompress client-side for large screenshots.

    Storage path¶

    Uploaded files are stored inside the app container at:

    /app/uploads/feedback_images/{YYYY}/{MM}/{originalBasename}_{8-char-hex}{ext}
    • {YYYY}/{MM} is the upload month (server time, Asia/Dubai).
    • {originalBasename} is the filename the client sent, minus the extension.
    • {8-char-hex} is uuid.uuid4().hex[:8]. It uniquifies concurrent uploads that happen to share the same filename, but it is not cryptographically unpredictable — do not treat it as a secret.
    • The same file is served over HTTP at https://ap.ad4x4.com/uploads/feedback_images/... via a custom serve_media view (Whitenoise only serves the static assets under /static/; the /uploads/ path is handled separately so that authentication can be layered on later if needed).

    Example: a client upload of screenshot.png in April 2026 is stored as feedback_images/2026/04/screenshot_3f4a2b8c.png.

    Notifications¶

    After a feedback record is saved, FeedbackCreateAPIView.perform_create dispatches the Huey task background.send_feedback_notification(feedback_instance). The task assembles a notification with the feedback type, message, and (if present) the image URL, and delivers it to the administrators configured in ConfigurableSettings via the notification service — email, Telegram, and/or push, depending on which channels are enabled.
    Task name send_feedback_notification
    Defined in api/background.py
    Retries 2
    Retry delay 300 seconds (5 minutes)
    Runs in The huey Docker container (production) / synchronously (development)

    See Background Tasks and Notifications for the full notification pipeline.

    Practical Notes for Frontend Implementers¶

    • Two different response envelopes on this page. The create endpoint returns {success, message}; the list-by-member endpoint returns the standard DRF {count, next, previous, results} pagination envelope. Your client must handle both shapes — don't assume every endpoint uses the success wrapper.
    • Don't rely on timestamp in the response — it isn't returned. If you need to show "submitted X minutes ago" in the UI, use the local Date.now() at send time and cache it client-side, or fall back to refreshing the member-feedback list.
    • Default feedback type is general. Omitting feedbackType is valid and results in a "General Feedback" submission. If your UI forces the user to pick, this is a safe fallback for the "other" option.
    • Image URL is absolute. DRF builds the full https://... URL using the request host, so you can use it directly in an <img src> without extra prefixing.
    • Rate limiting applies. A burst of 200+ feedback submissions per minute from the same user will hit the DRF throttle and return 429 Too Many Requests.
