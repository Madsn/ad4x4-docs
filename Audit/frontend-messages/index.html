    Frontend Team Messages — Post-Audit Coordination¶

    Three ready-to-send messages for the Gallery, Web Portal, and Flutter teams covering everything that changed in the claude/magical-liskov-06b29d audit branch (PR #72).

    Each message below is self-contained — copy the section into an email / Slack / ticket for the respective team. The detailed finding IDs (F-NN) reference audit-report.md for anyone who wants to dig deeper.

    1. Gallery Service Team (media.ad4x4.com)¶

    Subject: AD4x4 backend audit — gallery webhook changes, no action required on your side

    Hi gallery team,

    The AD4x4 backend just completed a large quality/security audit. Several findings touched the gallery webhook integration, but none of our fixes require changes on your side. Sharing for visibility.

    What changed on our side¶

    What Before After
    Retry behavior on 4xx responses We raised RuntimeError on any non-200 from your webhooks. Huey retried up to 6 times (create) or 3 times (update/delete/restore) with 1-hour backoff, wasting your 4xx responses. We now differentiate: 4xx → log as permanent failure and stop retrying. 5xx / network errors / timeouts → raise and retry as before. You'll see fewer retry storms for bad-request-class failures.
    Idempotency guard If create_gallery_for_trip succeeded remotely but our local save failed, the retry would create a second gallery for the same trip. We now check if trip.gallery_id: return gallery_id before calling you. No duplicate galleries on retry.
    Error logging Our error paths sometimes logged the full response body, which could include Bearer tokens if your API echoed headers in error responses. We now log status codes and sanitized message bodies only — no more potential auth-header leakage in our logs.
    Timeout floor We trusted ConfigurableSettings.gallery_api_timeout blindly; a mis-set 0 would hang the worker forever. We enforce max(1, gallery_api_timeout) — minimum 1-second timeout regardless of config.
    Cancel trip cascade TripEditView.destroy only flipped approval_status to CANCELED; your webhook was called via signal but members weren't notified. destroy now also notifies every registered + waitlisted member. The gallery soft-delete webhook you already receive continues to fire via the same signal path — no traffic pattern change for you.

    What you'll see¶

    • Lower 4xx webhook retry volume from our side. If you were seeing repeated calls for rejected requests, those stop.
    • No duplicate trip/published calls for the same trip_id under retry conditions.
    • Everything else (payload shape, endpoints, auth, timing) is unchanged.

    What we'd like to discuss later (not urgent)¶

    Finding F-31 in our audit recommended adding an explicit Idempotency-Key request header on the webhook calls, so you can reject obvious duplicates even if our local trip.gallery_id guard fails. This is optional and would require a spec conversation — can we:

    1. Sync on whether your webhook endpoints support an Idempotency-Key: <uuid> header today (accept + dedupe / accept + ignore / reject unknown headers)?
    2. Agree on a semantic if we add one: reject duplicate keys as 409, or return the original response?

    If it's a non-trivial lift on your side, we're happy to stick with the current guard. No timeline pressure.

    Testing¶

    Your webhooks weren't exercised in our audit's pytest run (we can't hit a live gallery from CI). Once the audit branch merges to main, standard smoke tests on staging should confirm:

    • POST /api/webhooks/trip/published still works
    • POST /api/webhooks/trip/updated still works
    • POST /api/webhooks/trip/deleted still works (will see increased traffic when trip destroy cascade ships — every cancellation now triggers this + member notifications)

    References¶

    • PR: https://github.com/Madsn/ad4x4-backend/pull/72
    • Gallery-specific findings: F-29 (settings shadowing), F-30 (exception leakage), F-31 (idempotency), F-33 (retry taxonomy), F-82 (timeout floor) — all in docs/Audit/audit-report.md

    Thanks — AD4x4 backend team

    2. Web Portal Team (ap.ad4x4.com / ad4x4.com)¶

    Subject: AD4x4 backend audit — web client changes required

    Hi web team,

    The AD4x4 backend audit branch is ready for merge and includes several changes the web portal needs to be aware of. Below is a triaged list of everything that could affect a web client, ordered from "must fix before merge lands" to "informational."

    TL;DR coordination¶

    • One coordinated release: please ship client changes for F-12 and F-56 in the same window the backend merges.
    • ~2–3 days of work total, most of it testing across member directory, trip registration, and ClubNews surfaces.
    • No endpoint-path changes — only behavior / error-shape / permission tightenings. Your existing API client can keep its structure; you'll adjust error handling and a couple of endpoint choices.
    • Regenerate your OpenAPI client from the updated schema.yml (45 lines added, 28 removed — all backward-compatible refinements, no breaking types).

    Must coordinate before merge lands¶

    ID What changed What web needs to do
    F-12 GET /api/members/ now requires SEARCH_MEMBERS permission. Non-privileged authenticated users get 403. The endpoint was previously wide-open to any logged-in user. If the web portal uses the raw member list for dropdowns (e.g. trip lead picker, admin member browsing), switch to /api/members/search/ or /api/members/leadsearch/ which are already permissioned and return a scoped/searchable response. Verify no hidden reliance on GET /api/members/ for enumeration.
    F-56 ClubNewsViewSet read list/detail now filters by the viewer's level. Lower-level users see fewer items than before (only level-agnostic news + news gated to their level). Product impact: if the web portal has a public-facing news block or a "latest news" widget that expected the full list, it will now return a filtered set for authenticated users. Verify the widget's messaging makes sense ("news for your level" rather than "all news"). No code change if your current filter logic already assumes the backend will filter.
    F-09 /api/trips/<pk>/register no longer bypasses validation for permission holders. Admin-initiated overrides must use /api/trips/<pk>/forceregister. If the web portal has an admin trip-registration UI that relied on the silent bypass, switch those calls to /forceregister. Member-facing registration UI is unaffected.
    F-05 /api/upgraderequests/<pk>/approve may now return 409 Conflict with {"message": "applicant_already_at_or_above_target_level"} when approving would downgrade someone. Add error handling for 409 on the approve action — surface the message in the admin UI.

    Should handle (low-risk 400s, likely already covered)¶

    ID What changed
    F-50 Avatar uploads over 2.5 MB now return 400 at the API (previously silently truncated). If your upload UI already handles 400s with a file-size message, no change.
    F-52 /api/members/<id>/payments endpoint no longer crashes on JSON true/false — now properly validated.
    F-65 HERE Maps reverse-geocode errors return cleaner messages (no more raw exception strings or API key leakage in error responses). If you display the error text directly, nothing breaks — just gets cleaner.
    F-80 /api/notifications/ now paginates properly (was hard-sliced at 20). If your notification list UI expected exactly 20 items, it will now page via standard ?page=N params — uses the standard paginator shape you get elsewhere.
    F-37 Login now returns a single unified error message for bad credentials vs disabled accounts. If your login UI distinguished the two via error text, it becomes one error.
    F-63 /api/trips/<pk>/forceregister now returns 403 on permission denial (was silently returning 200 with success: false). Admin UIs should surface 403s rather than inspecting the response body.

    Web-portal-specific¶

    ID What changed
    F-88 *.sandbox.novita.ai removed from CORS_ALLOWED_ORIGIN_REGEXES in production — restricted to dev mode only. If the web portal uses any tooling hosted on Novita (Figma plugins, Storybook previews, design-review environments), that tooling will no longer reach the production API from those origins. Move to a dev/staging domain instead.
    F-35 SECURE_PROXY_SSL_HEADER is now only set in production. If the web portal runs behind a local dev TLS proxy that forwarded X-Forwarded-Proto: https, request.is_secure() may now return False in local dev (as intended). Verify dev environment still works.

    Informational — notification-delivery improvements¶

    Users may notice small behavior changes that do not require web-portal code updates:

    • F-06, F-24, F-26 — ClubNews and per-channel notifications now retry correctly on transient failures without duplicating delivery on success. Users should see fewer duplicate emails / push notifications.
    • F-75 — When an admin cancels a trip, registered and waitlisted members now receive the standard removed_from_trip_* notifications. Previously they got nothing. Customer support talking point: members may ask why they suddenly see cancellation notifications. Messaging is: "This is now working as intended."
    • F-04 — Huey tasks are now wrapped in transaction.on_commit universally. Some edge cases where notifications went out for rolled-back operations are now fixed. No code change for web.

    Regenerate your OpenAPI client¶

    schema.yml changed — key updates your client should pick up:

    • VehicleViewSet path params correctly typed as integer (was string)
    • send_club_news added to the PermissionMatrixAction enum
    • MarkNotificationLogAsReadView response is 200 (was 201)
    • Several LogbookMigrationRequest response fields now have proper object schemas instead of "string"

    None of these are breaking; regenerating should produce a cleaner client.

    Testing¶

    • A coordinated staging deploy + smoke test of member directory, trip registration (self + admin), ClubNews feed, upgrade approval, and notification flows would catch anything surprising
    • CI pytest on the backend branch has passed (262 tests) — backend is confident
    • Flutter is getting the same message separately

    References¶

    • PR: https://github.com/Madsn/ad4x4-backend/pull/72
    • Full finding detail: docs/Audit/audit-report.md
    • Frontend coordination index: docs/Audit/frontend-impact.md
    • Cumulative fix notes: docs/Audit/fix-status-2026-04-24.md

    Thanks — AD4x4 backend team

    3. Flutter Mobile App Team¶

    Subject: AD4x4 backend audit — Flutter client changes required, one coordinated release

    Hi mobile team,

    The backend audit is closing out. There are real changes Flutter needs to handle, but the overall surface is small — most of the audit was server-side hardening. Below is triaged from "must fix before backend merge" to "informational."

    TL;DR¶

    • ~2–3 days of Flutter work + one App Store / Play Store review cycle.
    • No endpoint paths changed. Your existing service layer can stay structurally.
    • One new 409 to handle (upgrade approve conflict).
    • One endpoint migration if the app uses raw /api/members/ for dropdowns — switch to /search/ or /leadsearch/.
    • Regenerate the OpenAPI client from the new schema.yml — all backward-compatible refinements.

    Must coordinate before merge lands¶

    ID What changed What Flutter needs to do
    F-12 GET /api/members/ now gates on SEARCH_MEMBERS permission. Non-privileged users get 403. If the app uses the member list for trip-lead pickers, deputy-lead selection, or similar dropdowns, switch to /api/members/search/ or /api/members/leadsearch/. Both are already permissioned and take a q param for fuzzy-search. The raw list endpoint is now locked down.
    F-09 Member-facing /api/trips/<pk>/register no longer silently bypasses validation for permission holders. Admin-registration flows must use /api/trips/<pk>/forceregister. If the marshal / admin UI has a "register member for trip" flow that relied on the silent bypass, point it at /forceregister. Plain member registration is unaffected.
    F-05 /api/upgraderequests/<pk>/approve may now return 409 with {"message": "applicant_already_at_or_above_target_level"} when approval would downgrade an already-promoted member. Add handling for 409 on the approve action — show the error message, don't retry. Typical scenario: a stale upgrade request sitting in the queue for a member who was already manually promoted.
    F-50 Avatar uploads over 2.5 MB now return 400 at the API. Previously the image was silently truncated. If the app compresses avatars client-side, no change. If it uploads originals, the user needs a clear message. The backend returns {"success": false, "message": "avatar must be smaller than 2.5MB"}.

    Should handle (likely already covered by generic 400/403 handlers)¶

    ID What changed
    F-01 /api/logbookskillreferences/ is now read-only via API (was accidentally writable). If the app only reads it, no change. If it writes, those calls now return 405/403.
    F-52 /api/members/<id>/payments no longer crashes on JSON true/false — properly validated. If the app was serializing booleans correctly, no change.
    F-63 /api/trips/<pk>/forceregister now returns 403 on permission denial (previously 200 with success: false). If error handling treats non-2xx as failure, no change. If it only checks success: false, it'll work but won't flag the 403 distinctly.
    F-65 HERE Maps reverse-geocode errors no longer leak raw exception strings or API keys. Error messages are cleaner.
    F-80 /api/notifications/ now paginates properly (was hard-sliced at 20). If the app already handles paginated responses, no change. If it expected exactly 20, switch to paginated fetching.
    F-37 Login returns a single unified error for "bad credentials" vs "disabled account." If the login UI distinguished them via error text, it's now one error.
    F-15 /api/upgraderequests/<pk>/... endpoints and /api/upgraderequestcomments/... now return 404 (was 500) on unknown IDs. Nothing to do — error handling just gets cleaner.

    Informational — notification behavior improvements¶

    • F-75 — trip cancellations now notify registered + waitlisted members. Previously, canceling a trip silently left members on the roster. Now they receive the standard removed_from_trip_registered or removed_from_trip_waitlist push/email/in-app notification payload — payload shape unchanged, so no Flutter code change. Just more of them. Support talking point: members may ask why they're suddenly seeing cancellation notifications; this is the intended new behavior.
    • F-06, F-24, F-26 — per-channel notification idempotency. Users should see fewer duplicate pushes on retries.
    • F-04 — transaction.on_commit is now universal. Edge cases where a rolled-back operation triggered a notification are gone.

    Regenerate the OpenAPI client¶

    schema.yml diff: +45 / −28 lines. Worth regenerating for:

    • VehicleViewSet path params correctly typed as integer (was inferred as string)
    • send_club_news added to the PermissionMatrixAction enum — if the app lets admins configure permissions, the new choice appears
    • MarkNotificationLogAsReadView returns 200 (was 201) — update expected status code if asserted
    • LogbookMigrationRequestSerializer response fields (member, target_level, skill_entries) now have proper object schemas — your generated models will be more precise

    None are breaking — regeneration produces a cleaner, better-typed client.

    Test checklist suggestion¶

    • Trip lead picker still populates with appropriate members (F-12 endpoint swap)
    • Admin registration flow routes through force-register (F-09)
    • Upgrade approve shows the 409 message correctly (F-05)
    • Avatar upload shows the size limit message on oversize files (F-50)
    • Notification list pagination works beyond 20 items (F-80)
    • Vehicle set-primary button still works (F-07 internal refactor — path preserved)

    Release coordination¶

    • Backend targets merge when Mikkel gives the final CI sign-off (expected soon)
    • Recommend: Flutter ships the coordinated release after the backend merge lands on production, not simultaneously — gives time for any backend rollback if needed
    • App Store / Play Store review lag means ~2–5 days from your submission to live; factor that into your release planning
    • No feature-flag coordination needed — all changes are backward-compatible for an older Flutter client (users on old app versions will keep working; the 403s they may now hit on /api/members/ are better than silent PII exposure)
