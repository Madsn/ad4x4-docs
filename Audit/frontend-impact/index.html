    Frontend Impact Analysis¶

    Companion document to audit-report.md. Breaks down which audit findings require coordination with the Flutter mobile app, the web portal, the admin panel, the gallery service, or any other external integration.

    Generated by filtering every finding in audit-report.md by its **Frontend impact:** tag.

    Numbers at a glance¶

    Of 119 distinct findings in the full audit:

    Frontend impact Count %
    none (pure server-side) 92 77%
    low (edge-case validation, transparent 400s) 18 15%
    medium (stricter permissions, tighter error semantics) 7 6%
    high (potential endpoint change) 1 1%
    depends (conditional on client usage) 1 1%

    Headline: 77% of fixes are pure backend work. The remaining 23% need varying degrees of client awareness, and only one finding could require an endpoint rename.

    Flutter mobile app¶

    Must coordinate — Flutter PR should ship alongside the backend¶

    Finding Severity What changes for Flutter
    F-07 high vehicles/<pk>/set_primary/ is currently wired via manual as_view(). Refactor to a proper @action should keep the URL the same, but verify after the fix lands. If the router reassigns a different path, mobile needs a release.
    F-12 high GET /api/members/ stops returning the full member directory to non-privileged users. If Flutter uses this for dropdowns (trip lead picker, deputy selection), switch to /api/members/search/ or /api/members/leadsearch/ — both are already permissioned.
    F-09 high Permission holders no longer silently bypass trip registration validation. If admin-initiated registrations rely on the skip, add an explicit force=true flag server-side and update Flutter admin UI accordingly.
    F-05 critical Upgrade approve/decline may return 409 Conflict (not 200) when approval would downgrade an already-higher-level member. Surface the error message.
    F-06 critical Users may temporarily see duplicate club-news notifications during rollout while idempotency guard lands. No Flutter code change — support talking point only.
    F-37 medium Login error messages unified — "invalid credentials" regardless of whether the account exists or is disabled. If Flutter currently shows different UI per error, it becomes one error.
    F-56 medium ClubNews feed may hide items from lower-level users that were previously visible (fix closes a per-level gate bypass). App behavior is correct but feed gets shorter for some members — customer-support talking point.

    Nice-to-handle — low impact, app should already handle 400s¶

    Finding What changes
    F-50 Avatars over 2.5 MB now return 400 at the API instead of silent truncation.
    F-52 /api/members/<id>/payments stops crashing on JSON true/false.
    F-65 HERE Maps reverse-geocode returns cleaner error responses (was leaking raw exception strings, potentially including the API key).
    F-80 /api/notifications/ now paginates properly (was hard-sliced to 20).
    F-01 LogbookSkillReferenceViewSet writes now require SIGN_LOGBOOK_SKILLS. Expected: Flutter only reads this ViewSet, so no change. If it writes, previously-allowed calls return 403.
    F-10 Capacity race fixed — concurrent registrations may now see a stricter 409/400 more often. Rare.
    F-11 Waitlist → registration now preserves the waitlist entry's vehicle. Response shape unchanged.
    F-15 Unknown upgrade-request ID no longer produces 500 — returns 404.
    F-17, F-18 Logbook skill references now preserve history across marshals — response shape unchanged, but reads may show more rows.
    F-21 Vote endpoint becomes atomic — behavior more consistent but shape unchanged.
    F-24 Notification delivery deduplicated on retry. Users may see fewer duplicate pushes.
    F-36 SessionsView.delete correctly rejects blacklisted keep_refresh tokens. Client should already treat this as "session invalid, re-login".
    F-49 Upgrade status transition guards prevent double-approval. Previously-allowed illegal transitions now return 400.
    F-51 LeadSearch missing level param now returns 400 cleanly instead of 500.
    F-53 /api/members/leadsearch and /api/members/activetripleads may return 403 for users without SEARCH_MEMBERS.
    F-55 ClubNewsNotificationAPIView now returns 403 instead of 200 for non-admins.
    F-63 ForceRegisterForTrip now returns 403 on permission denial instead of a silent 200.
    F-67 PATCH /api/auth/profile/notificationsettings semantics tightened — partial updates only modify specified fields.

    Estimated effort¶

    ~2–3 days of Flutter work — one coordinated PR with updated error handling + one endpoint switch. Biggest effort: testing that nothing regresses across the member-directory dropdowns used in trip registration and deputy-lead selection.

    Recommended Flutter test checklist¶

    • Trip lead picker still populates (use /search/ or /leadsearch/)
    • Upgrade approve flow surfaces 409 when applicable
    • Login error UI handles unified error message
    • Avatar upload shows 400 message on oversize files
    • Notification list pagination works beyond 20 items
    • Admin registration UI uses force=true if needed
    • Vehicle set-primary endpoint still resolves correctly

    Web portal (ap.ad4x4.com)¶

    Uses the same REST API as Flutter, so same findings and same coordination apply. Plus two web-specific items:

    Finding Severity Web-specific impact
    F-56 medium If the unauthenticated ClubNews list is embedded on a public landing page, it may hide level-gated news after the fix. Confirm the public page only shows news that was always intended for public view.
    F-88 low Novita AI sandbox removed from CORS_ALLOWED_ORIGIN_REGEXES. If any web tooling (Figma plugins, Storybook previews, design-review tools) runs on *.sandbox.novita.ai and calls the API, it breaks. Move to a proper dev domain or stage.

    Estimated effort¶

    Same as Flutter plus a quick audit of the public ClubNews surface and any Novita-hosted tooling.

    Admin panel (Django admin)¶

    No changes required. Django admin is server-rendered — it auto-adapts to model and view changes.

    Positives for admin users from the fixes: - F-03 closes CVE-2026-4292 and CVE-2026-4277, both admin-form forgery CVEs in Django 6.0.1–6.0.3. - F-04 (transaction.on_commit) makes admin-triggered notifications reliable — admin-initiated ClubNews, trip approvals, upgrade decisions no longer race a rollback. - Cosmetic improvements only (F-102, F-103, F-105).

    Gallery service (media.ad4x4.com)¶

    Minimal coordination required. One conditional item.

    Finding Severity Gallery-side requirement
    F-31 high If the fix adds an idempotency key (UUID in request header) to the create_gallery_for_trip webhook so retries don't create duplicate galleries, the gallery service must accept and honor that header. If it already supports idempotency keys or ignores unknown headers gracefully, no change needed.
    F-30, F-33 high Our error handling improves (stops treating 4xx as retryable, stops logging auth headers verbatim). Gallery sees identical traffic.
    F-32 high HERE Maps TTL fix — not gallery related despite similar-sounding "cache" terminology. HERE Maps is a separate third-party.
    F-78, F-79, F-92, F-93 low Cosmetic / internal — log message fixes, import-time capture fixes. No gallery-side impact.

    Recommended gallery-team action¶

    • One meeting / spec conversation: "Will you accept an Idempotency-Key: <uuid> header? If yes, how should it behave on duplicate keys — reject, return original, or merge?"
    • Zero work if we keep the current at-most-once-but-unsafe retry semantics (which is what F-31 explicitly flags as wrong).

    External services — nothing to do¶

    Service Audit findings touching it Impact on them
    Firebase / FCM F-23 (batching), F-24 (idempotency), F-89 (init deferral) None. FCM sees identical outbound traffic. Our worker uses their API more efficiently.
    HERE Maps F-32 (TTL bug), F-65 (error leakage) None. Our cache fix; HERE Maps API unaware.
    PayPal None directly. Existing gotchas in §15 about currency still apply. None.
    Telegram bot F-27 (dry-run PII leak into logs) None. Dry-run fix is log-level only. Outbound messages may reduce in volume once duplicate-send is fixed.
    Gmail SMTP F-24 (idempotency) None. Email volume may drop (idempotency prevents duplicates on retry).

    Release coordination summary¶

    Stakeholder Scope Effort
    Backend team All 119 findings 2–4 weeks depending on batch size
    Flutter team 7 medium + 1 high + ~11 low findings ~2–3 days, one coordinated PR
    Web team Same as Flutter + Novita CORS check ~2–3 days
    Gallery team Idempotency-Key header spec (only if F-31 is accepted) 1 meeting, maybe 0.5 day
    Admin users Nothing Get security improvements for free
    Mobile app store Flutter PR triggers App Store / Play Store review Add 1–3 days for review lag

    Recommended rollout order¶

    1. Week 1 — server-only fixes (F-02, F-04, F-03 CVE bumps, all the N+1s, transaction boundaries, logging cleanup). Zero client impact. Easy to ship incrementally.
    2. Week 2 — permission tightenings (F-01, F-12, F-53, F-55, F-56). Announce to Flutter/web teams 2 weeks ahead. Ship backend with feature flag if the SEARCH_MEMBERS gate is scary.
    3. Week 3 — coordinated client release. Flutter + web ship their PRs referencing the new API contract. Submit to stores. Monitor crash reports and 403 rates.
    4. Week 4 — remaining mediums + lows. Gallery idempotency conversation fits here if it's happening.

    Release risk¶

    • Lowest risk: CVE dep bumps (F-03, F-68). Drop-in patch releases.
    • Medium risk: Permission tightenings (F-01, F-12) — may surface clients we don't know about.
    • Highest risk: F-07 if the set_primary path changes under the feet of the Flutter client. Verify path is preserved during the refactor.

    Appendix: how to regenerate this table¶

    # From the repo root:
import re
content = open('docs/Audit/audit-report.md', 'r', encoding='utf-8').read()
blocks = re.split(r'^### (F-\d+|D-\d+):\s*', content, flags=re.MULTILINE)[1:]
findings = []
for i in range(0, len(blocks), 2):
    fid = blocks[i]
    body = blocks[i+1] if i+1 < len(blocks) else ''
    m_impact = re.search(r'\*\*Frontend impact:\*\*\s*(\w+)\s*[—-]?\s*(.*?)(?:\n|$)', body)
    if m_impact:
        findings.append((fid, m_impact.group(1).lower(), m_impact.group(2).strip()))

# Group by impact
from collections import Counter
print(Counter(f[1] for f in findings))
for impact in ('high', 'medium', 'low'):
    print(f'\n=== {impact} ===')
    for fid, i, note in findings:
        if i == impact:
            print(f'{fid}: {note[:120]}')

    Re-run this after every fix to see the frontend-impact distribution shrink.
