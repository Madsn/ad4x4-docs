    Step 4 — Migration Health¶

    Caveat¶

    mcp__django-ai-boost__list_migrations requires a DB connection; the dev DB dev doesn't exist in this environment, so applied-vs-unapplied state could not be verified. All findings below are based on file-level inspection.

    Raw counts¶

    • api/migrations/*.py (excluding __init__.py): 98 files
    • website/migrations/*.py (excluding __init__.py): 3 files
    • Total: 101 migration files

    CLAUDE.md §3 claims "98 migrations" — accurate for the api app, but doesn't mention the 3 website migrations. Minor doc drift.

    Latest migrations¶

    Data migrations (RunPython)¶

    Four migrations use RunPython — they move data around, not just schema:

    Migration What it does Risk
    api/0019_seed_global_config Seeds the ConfigurableSettings singleton Low — idempotent seed
    api/0068_alter_permissionmatrix_action Enum migration for PermissionMatrix.action Medium — affects auth if reverse is wrong
    api/0085_migrate_car_fields_to_vehicles Legacy car fields → Vehicle records High — one-way data move
    api/0094_migrate_deleted_to_canceled Rename enum values for trip-registration status Medium — depends on quality of the reverse

    Findings¶

    [medium / confidence low] Applied state not verified¶

    • Evidence: The audit environment has no DB to introspect.
    • Recommendation: Run python manage.py migrate --plan in production (read-only plan view) or showmigrations --list. Capture output and archive as part of release documentation.

    [medium / confidence high] Three website migrations are not mentioned in CLAUDE.md §3¶

    • Evidence: §3 says "98 migrations" — that's api/ only.
    • Recommendation: §3 says "98 migrations" under the api folder line. Fine as-is, but consider listing the website app separately (it has its own migration tree for PayPal config).

    [medium / confidence high] Four RunPython data migrations exist; at least two are one-way-ish¶

    • Evidence: 0085_migrate_car_fields_to_vehicles and 0094_migrate_deleted_to_canceled transform data in place. If reverse_code is migrations.RunPython.noop, rolling these back leaves DB in an inconsistent state.
    • Recommendation: Open each data migration and verify the reverse_code. For irreversible ones, document in CLAUDE.md §11 that rollback past those migrations requires a DB restore from backup (see infra/disaster-recovery/Disaster-README.md).

    [low / confidence medium] Migration sequence is long (98) — squash candidate eventually¶

    • Context: Django has no hard limit, but >80 migrations for a single app is a smell. Introduces startup overhead on migrate, and makes manage.py makemigrations harder to reason about.
    • Recommendation: Not urgent. Next time there's a planned downtime window, squash api/0001..0070 into a single initial snapshot. Keep 0071+ as-is. Verify the squash doesn't break any still-live replica.

    [low / confidence high] Index rename migration 0097_rename_... looks cosmetic¶

    • Evidence: Name literally contains rename_...idx_...idx_....
    • Why this matters: Renaming an index in Postgres is cheap but locks the table briefly. If the table is large (api_member), run this during a low-traffic window.
    • Recommendation: Confirm this migration has already been applied in production. If not, schedule it during maintenance.

    [low / confidence high] No merge_*.py migrations — clean merge history¶

    • Evidence: No merge_ prefix files in either app's migrations.
    • Interpretation: Branches have been rebased cleanly, no conflicting migration graphs merged. Good hygiene.

    Summary¶

    Area Status
    Total count 101 (98 api + 3 website)
    Applied state Not verified (no DB)
    Data migrations 4 (two one-way-ish — verify reverses)
    Merge migrations 0 (clean)
    Squash candidate Not urgent; api at 98 files is on the edge

    Follow-ups¶

    1. Confirm all data migrations have sensible reverse_code (not just noop).
    2. Next production migrate-dry-run output should be archived alongside the release artifacts.
    3. Optional: squash old api migrations into one initial baseline during the next maintenance window.
