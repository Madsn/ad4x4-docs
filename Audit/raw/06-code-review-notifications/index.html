    Code Review — Notifications Stack¶

    Audit date: 2026-04-22. Mode: READ-ONLY.

    Scope: api/views/views_clubnews.py, api/views/views_notificationsettings.py, api/views/views_pushnotification.py, api/services/notification_service.py, api/services/email_notifications.py, api/services/push_notifications.py, api/services/telegram_notifications.py, api/services/store_notifications.py.

    Referenced collaborators (read for context, not in audit scope): api/background.py, api/signals.py, api/models/models.py (ClubNews), api/services/trip_registration_service.py, api/views/views_trip.py, templates/emails/*.

    Findings¶

    F-01 [critical] [immutability] send_club_wide_news flips status to SENT inside the channel fan-out loop, so partial failures leave the record immutable-but-undelivered¶

    File: api/services/notification_service.py lines 125–134.

    def send_club_wide_news(self, data: ClubNews):
    logger.info(...)
    for channel in self.channels:
        try:
            channel.send_club_wide_news(data)
        except Exception as e:
            logger.error(...)
            logger.exception(e)
    data.status = ClubNewsStatus.SENT
    data.save()

    Two concrete problems flow from this block.

    1. Double-send on Huey retry. send_club_news is declared @task(retries=2, retry_delay=300) in api/background.py:80. Channel implementations (send_club_wide_news in each channel) are also @task()-decorated — they enqueue nested Huey tasks. If any channel raises synchronously (e.g., the queryset blows up before enqueuing), the manager swallows it, flips status to SENT, saves. But on transient errors before the final data.save(), the outer send_club_news task will retry — and because ClubNewsStatus.SENT is set only on the final pass, the retry fans out to every channel again, enqueuing a second batch of per-channel tasks. Members receive duplicate emails/pushes.
    2. Immutability trap on partial failure. The try/except inside the loop silently eats every exception from every channel, yet the manager still sets status=SENT unconditionally. If push succeeds but email fails, or vice-versa, the record is now immutable (ClubNews.save() raises ValidationError once status==SENT, §15) and cannot be resent or corrected. Admin has no way to retry just the failed channel short of DB surgery.

    Recommendation: move the data.status = SENT; data.save() into the successful branch of an all-channels-succeeded check, or drive status off an audit trail of per-channel delivery. At minimum, log a warning and skip the SENT flip if any channel raised.

    F-02 [critical] [on-commit] Notifications fire during add_users_from_waitlist inside an implicit transaction — rollback still pings users¶

    File: api/services/trip_registration_service.py lines 29–41.

    while trip.registered.count() < trip.capacity and len(waitlist_registrations) > 0:
    user = waitlist_registrations.pop(0).member
    trip.registered.add(user, through_defaults={'trip': trip})
    trip.waitlist.remove(user)
    send_registration_from_waitlist_notification(user, trip)

    send_registration_from_waitlist_notification is a Huey @task — in production it pushes a message to Redis immediately. If the request is wrapped in a transaction.atomic() block further up (DRF's ATOMIC_REQUESTS may or may not be on, but individual service flows like trip_registration_service.remove_from_registered can be called mid-transaction by upstream handlers) and that transaction rolls back, the waitlist moves are undone but the notification has already been enqueued — members get "you're registered" emails for trips they're no longer registered for.

    Same pattern in remove_from_registered (line 49) and remove_from_waitlist. Same pattern in views_trip.py:107,516,517,541 where send_trip_notification and send_trip_approval_notification are fired right after trip.save() without on_commit.

    Recommendation: wrap every send_* enqueue in transaction.on_commit(lambda: send_x(...)). This is a one-line fix per call site and is the standard Django idiom for Celery/Huey-adjacent code.

    Signal club_news_post_save at api/signals.py:89 has the same issue — post_save fires before the outer transaction commits, so on rollback the enqueued task runs against a row that no longer exists or still has the pre-save status.

    F-03 [high] [idempotency] Per-channel Huey tasks retry independently but have no delivery receipt — retries duplicate sends¶

    Every channel method (EmailNotificationChannel.send_new_trip_notification, PushNotificationChannel.send_new_trip_notification, etc.) is itself @task(). None of them is idempotent: there is no "already sent" marker, no dedup key, no NotificationLog.objects.get_or_create. Combined with the outer send_trip_notification task (retries=2), a transient SMTP timeout that Huey treats as a failed task will re-enqueue the email task, which will re-run the full DB query and email every matching user again.

    The StoreNotificationChannel.send_new_trip_notification task creates NotificationLog rows with no uniqueness constraint (store_notifications.py:30). A retry produces duplicate rows.

    Recommendation: Either (a) introduce a compound unique constraint on NotificationLog (member, type, related_object_id, related_object_type) with get_or_create semantics, or (b) gate each channel task on a per-task idempotency key (e.g., trip_id + channel_name) stored in a NotificationDispatch audit table.

    F-04 [high] [on-commit] ClubNewsNotificationAPIView.post enqueues send_club_news(validated_data) with raw dict, not persisted ClubNews¶

    File: api/views/views_pushnotification.py lines 26–30.

    def post(self, request, *args, **kwargs):
    serializer = self.get_serializer(data=request.data)
    serializer.is_valid(raise_exception=True)
    send_club_news(serializer.validated_data)
    return Response(...)

    send_club_news(data) in background.py:81 expects a ClubNews model instance (it calls notification_manager.send_club_wide_news(data), which ends with data.status = ClubNewsStatus.SENT; data.save()). Here it is handed serializer.validated_data, which is a plain dict. The .save() call on a dict will raise AttributeError inside Huey — which will then retry the task twice (retries=2). Two retries of something that can never succeed, three failures logged per admin push.

    Additionally, CustomPushNotificationSerializer is a plain serializers.Serializer, not a ModelSerializer — validated_data will not contain the correct ClubNews fields (title, content, levels, status) in a shape the downstream consumer expects. The fan-out in email/push channels reads data.levels.count(), data.title, data.content — those only work on a model instance.

    This endpoint looks broken as shipped, or it is dead code. Either way, it warrants verification.

    F-05 [high] [error-handling] Swallowed exceptions in NotificationManager hide channel failures from Huey's retry logic¶

    File: api/services/notification_service.py lines 71–192.

    Every send_* method on NotificationManager wraps its per-channel dispatch in try/except Exception + logger.error + logger.exception, and then continues. Outcomes:

    • A real failure never propagates, so Huey's @task(retries=2, retry_delay=300) wrappers in background.py never see it and never retry.
    • logger.exception(e) called twice per failure (once as error, once as exception) produces two tracebacks in Sentry/logs per event, inflating noise.
    • Operators cannot distinguish "one channel down, rest delivered" from "all channels down" via alerting.

    Recommendation: drop the try/except or re-raise after logging the first one. Let Huey retries handle transient failures. Use logger.exception(...) once — it already prints the message plus traceback; the extra logger.error(...) line before it is redundant.

    The per-method logging also has the typo notificiation (lines 77, 86 at minimum) — minor, but search-unfriendly.

    F-06 [high] [pii] Dry-run logs dump full HTML bodies, addresses, and Telegram payloads at INFO level¶

    File: api/services/email_notifications.py lines 37, 169, 206, 239; api/services/telegram_notifications.py line 171.

    logger.info(f'Dry run: Email sent to {msg.to} with subject {msg.subject} and content {html_content}')

    In dry-run mode, the full rendered HTML (including recipient name, phone, email, feedback body, trip details) is written to logs at INFO. Similarly telegram_notifications.py:171 logs the formatted feedback message — which contains email, phone, and the first 200 chars of the user's feedback. These logs stream to Sentry breadcrumbs and any aggregation backend.

    Given dry-run is the default in dev (NotificationSettings default notification_dry_run=True, models_util.py:69) and the same logging path is hit every test run, this is GDPR-relevant PII in every dev/CI log stream.

    Recommendation: log subject + recipient count in dry-run mode, not the full body. If full-body dry-run is required for template debugging, gate it behind DEBUG=True or a separate flag and redact email addresses/phone numbers.

    F-07 [high] [pii] Phone number and email always logged by TelegramNotificationChannel._format_feedback_message when sent for real¶

    File: api/services/telegram_notifications.py lines 148–156, 171.

    The formatted feedback message includes user.email and user.phone, and line 171 logs the entire formatted message before sending. Even outside dry-run, every feedback produces an INFO log containing email + phone + first 200 chars of message. This is production PII in logs.

    Recommendation: log only feedback.id and feedback.user.username at INFO; keep the full formatted message local to the bot.send_message call.

    F-08 [high] [template-injection] Feedback email template renders user-supplied message without escaping, and uses raw HTML body¶

    File: templates/emails/feedback_received.html + api/services/email_notifications.py:149–172.

    <p>{{ context.message }}</p>

    Django templates autoescape by default, so < becomes &lt; in HTML context — that's safe. However: the EmailMultiAlternatives object in send_feedback_notification is constructed with html_content as the plaintext body (positional arg 2 of EmailMultiAlternatives, which is body). Then msg.attach_alternative(html_content, "text/html") attaches the same HTML as the HTML alternative. Result: the plaintext part of the email is literal HTML markup (not user-readable), and the HTML part relies entirely on the template engine's autoescape.

    feedback_received.html does not use |safe, so Django's autoescape saves the day here. But this same pattern is used by _send_email (line 20) for every template. If anyone ever adds {{ context.message|safe }} or a custom admin-controlled template with HTML, feedback messages, trip titles, and trip lead display names become an HTML-injection vector that lands in an admin or member's inbox.

    Recommendation: (a) render a real plain-text body via a .txt template and pass it as the positional body arg, with the HTML going into attach_alternative. (b) document in CLAUDE.md §14 that notification templates must never use |safe on user-controlled fields.

    Related: trip.title is rendered into push notification body and Telegram markdown. Push body is plain text and safe. Telegram uses escape_markdown(..., version=2) consistently except _format_trip_message line 49 — which does escape — so Telegram is OK. Email/HTML remains the risk surface.

    F-09 [high] [batching] FCM devices fetched without .only() / .select_related() and iterated instead of batched where possible¶

    File: api/services/push_notifications.py.

    • _send_msg_to_devices calls devices.send_message(...) on a QuerySet — that is fcm_django's batched bulk API. Good. But before sending it calls devices.count() (a separate SQL COUNT), then send_message re-evaluates the queryset — at minimum one redundant round trip. For larger sends this is two full queryset scans.
    • send_new_trip_notification (line 85) uses len(users) on a values_list queryset, which forces evaluation into a Python list; then subscribed_user_devices = FCMDevice.objects.filter(user__in=users, active=True) re-queries. Given users is already evaluated, passing it as a list is fine, but the pattern differs from .exists() / .count() elsewhere.
    • send_club_wide_news line 182: if data.levels.count() == 0 and data.levels.count() == 0: — duplicated condition; the second clause is a copy-paste bug. data.levels.count() is also called three times in a row — one cached call would suffice. Same duplication in store_notifications.py:134 and email_notifications.py:115.
    • send_club_wide_news queries NotificationSettings without checking last_user_activity filtering that store_notifications.py does apply (60-day activity threshold) — inconsistent audience between channels. Email and push go to everyone who opted in; store goes to active users only. Dormant users get emails/push but no in-app notification entry.

    Recommendation: consolidate audience resolution into a helper so all three channels share the same query. Collapse the duplicated .count() check. Decide whether inactive users should receive any channel.

    F-10 [medium] [error-handling] _send_email sleeps inside the send loop with no bulk send, no chunking, no async¶

    File: api/services/email_notifications.py lines 19–40.

    for user in users:
    msg.to = [user.email]
    msg.attach_alternative(html_content, "text/html")
    ...
    time.sleep(conf_settings.email_sleep_period_ms/1000)

    Two issues.

    1. Reusing the same EmailMultiAlternatives object across iterations: msg.attach_alternative(html_content, "text/html") appends a new alternative each iteration. By the Nth user, the message has N identical HTML alternatives attached. SMTP servers may reject or most clients render only the first, but the outgoing payload grows linearly — wasted bandwidth.
    2. time.sleep(...) blocks the Huey worker thread. For a 1000-user club-wide news send at 100ms sleep, that's 100 seconds of blocked worker. Huey workers are a finite pool; other tasks back up. Use @task() per email with the sleep replaced by Huey's delay= scheduling, or batch via an SMTP-level rate limiter.

    Recommendation: instantiate EmailMultiAlternatives per-user inside the loop, or use send_mass_mail / a real transactional email service.

    F-11 [medium] [perms] ClubNewsNotificationAPIView does not check PermissionMatrix — falls back to Django is_superuser¶

    File: api/views/views_pushnotification.py line 20.

    permission_classes = (IsAdminUserOrReadOnly,) which in permissions.py:394 checks request.user.is_superuser. Per CLAUDE.md §8: "Do not use Django model-level permissions (is_staff, is_superuser) for business logic; those are admin-panel shortcuts only. […] every protected view must add a PermissionMatrix check." Sending a club-wide push is a protected action. Add a PermissionMatrix.has_permission(request.user, ActionChoice.<SEND_CLUB_NEWS_OR_SIMILAR>) check.

    F-12 [medium] [perms] MarkNotificationLogAsReadView uses a CreateAPIView for an update action¶

    File: api/views/views_pushnotification.py lines 33–58.

    A mark-as-read operation is not a create — it mutates existing rows. Using CreateAPIView with an unbound queryset = NotificationLog.objects.all() exposes all notification logs via DRF's generic introspection (e.g., OPTIONS), which a non-admin can call. The actual post method correctly filters by member=request.user, so the data path is safe, but the view shape is misleading.

    Minor: notifications.count() != len(notification_ids) treats duplicates in the input as errors (count of distinct matches vs count of input IDs). [1, 1, 2] with two existing rows returns 400 because count=2 vs len=3. Deduplicate the input first or use set(notification_ids).

    Recommendation: use APIView with PATCH semantics, or at minimum an explicit @action(detail=False, methods=['post']) on NotificationLogViewSet.

    F-13 [medium] [style] NotificationLogViewSet.get_queryset hard-codes [:20]¶

    File: api/views/views_pushnotification.py lines 65–67.

    Returning the latest 20 notifications bypasses DRF pagination (StandardResultsSetPagination) because slicing a queryset prevents it from being paginated by DRF. Clients cannot retrieve older notifications. Given NotificationLog is purged at 60 days, this is a soft-limit of 20 latest in a 60-day window. Prefer real pagination; if a "last 20" view is really wanted, expose it as a distinct action and keep the default listing paginated.

    F-14 [medium] [immutability] ClubNewsViewSet is read-only but list filters only status='SENT'¶

    File: api/views/views_clubnews.py lines 8–15.

    queryset = ClubNews.objects.filter(status='SENT') uses a hard-coded string rather than ClubNewsStatus.SENT. ClubNewsStatus is an enum (used elsewhere). Use the enum constant to avoid drift if the value is renamed.

    Also: the ViewSet is ReadOnlyModelViewSet and permissions.AllowAny, so anonymous users can read all SENT club news. Per §6 documented endpoints this appears intentional, but given some news is level-gated (levels M2M), an anonymous client sees news intended only for specific levels — the level filter is only applied at send time, not at read time. If that's the intent, document it; if not, add a queryset filter tied to request.user.level.

    F-15 [medium] [style] NotificationSettingsApiView.patch delegates to put — partial semantics correct but misleading¶

    File: api/views/views_notificationsettings.py lines 24–34.

    Both put and patch use partial=True, which is correct for PATCH but wrong for PUT — PUT should require the full representation. Tests and clients can therefore omit required fields and still get 200 from a PUT. Either enforce partial=False on PUT or collapse into a single PATCH-only view (DRF has UpdateAPIView with GET+PATCH support).

    get_or_create(member_id=self.request.user.id) runs on every GET — creating a row on read is a side effect that makes GET /profile/notificationsettings non-idempotent. Prefer get_or_create in a signal on Member creation (or lazy-create on first PATCH only).

    F-16 [low] [style] ConfigurableSettings.objects.first() called without None guard in multiple places¶

    Files: api/services/push_notifications.py:18,41,58; api/services/email_notifications.py:220.

    Per CLAUDE.md §15: "ConfigurableSettings.objects.first() can return None. […] Always guard: check for None before accessing fields, or use the global_settings.py service which handles this." Email code already uses get_global_settings() in _send_email but the two account-deletion paths use the raw .first() (line 220 in email). Push code always uses raw .first(). In test/dev if the settings row is missing, every push enqueue raises AttributeError inside the Huey worker, which then silently retries.

    F-17 [low] [style] Unused variable and redundant level_name¶

    File: api/services/push_notifications.py lines 87, 20.

    Line 87: level_name = trip.level.name is assigned but never used. Line 20: NotificationType imported but also used via store_notifications.py:10 — fine, but the unused local at line 87 is dead code. Same in store_notifications.py:19 (level_name = trip.level.name never read).

    F-18 [low] [style] send_upgrade_request_created wrapped per-channel reveals applicant rather than using cached username lookup¶

    File: api/services/email_notifications.py lines 94–98.

    username = upgrade_request.applicant_str
try:
    username = upgrade_request.applicant.username
except AttributeError:
    pass

    Replace with username = upgrade_request.applicant.username if upgrade_request.applicant else upgrade_request.applicant_str — clearer and avoids using exception flow for regular logic.

    F-19 [nit] [style] Docstrings and logging typos¶

    • notificiation misspelled in notification_service.py lines 77, 86, 95, 104, 113.
    • send_club_wide_news duplicated condition data.levels.count() == 0 and data.levels.count() == 0 in three files.
    • email_notifications.py:153 f-string with no interpolation: f'templates/emails/feedback_received.html'.

    Non-findings (checked, not an issue)¶

    • Telegram escaping uses escape_markdown(..., version=2) consistently; no Markdown injection via user content.
    • ClubNews.save() does enforce immutability once status=SENT (models.py:155–161), so direct DB writes are safe. The risk in F-01 is the application flow producing a SENT record when the send was partial, not the model check itself.
    • Push notifications already use fcm_django's batched send_message on a QuerySet rather than per-device iteration — batching works correctly.

    Severity Count

    Highest-leverage fixes: add transaction.on_commit wrappers at every send_* call site (F-02), and restructure send_club_wide_news so SENT is only set on all-success (F-01).
