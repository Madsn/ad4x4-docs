    Step 1 — Django System Checks¶

    Ran run_check (regular) and run_check --deploy via MCP.

    Regular check (dev mode)¶

    • Total issues: 1 warning, 0 errors
    • staticfiles.W004 — STATICFILES_DIRS references staticfiles/ directory that doesn't exist.

    Deploy check (also in dev mode — see caveat)¶

    • Total issues: 16 warnings (0 errors, 0 critical)
    • Expected dev-mode artifacts:
    • security.W018 — DEBUG=True
    • security.W004 — SECURE_HSTS_SECONDS not set
    • security.W008 — SECURE_SSL_REDIRECT not True
    • security.W012 — SESSION_COOKIE_SECURE not True
    • security.W016 — CSRF_COOKIE_SECURE not True
    • security.W009 — SECRET_KEY is the insecure dev default

    Caveat: These are all correctly handled in ad4x4/settings.py lines 84–92, which sets the production-safe values inside if not DEV:. The deploy check sees the dev state because the MCP server runs in dev mode. No action needed on these six for production (verified in source).

    Real findings¶

    [low / confidence high] staticfiles directory missing¶

    • File: ad4x4/settings.py — STATICFILES_DIRS referenced but staticfiles/ folder absent
    • Category: config
    • Evidence: Reported by both regular and deploy check
    • Recommendation: Either create an empty staticfiles/ at project root with a .gitkeep, or remove the entry from STATICFILES_DIRS. The Docker image probably populates it at build — verify by inspecting Dockerapp.

    [low / confidence high] Dev SECRET_KEY hardcoded in source¶

    • File: ad4x4/settings.py:74
    • Evidence: SECRET_KEY = 'dev-secret-key-123463sdf12349erwh2837h'
    • Category: security (dev-only)
    • Recommendation: Not exploitable (dev mode only) but publishing the string in public source is bad hygiene — move to os.getenv('DJANGO_DEV_SECRET_KEY', '<random default generated each boot>') so anyone cloning the repo doesn't get the same key.

    [low / confidence high] Stale from django.conf.global_settings import SECRET_KEY¶

    • File: ad4x4/settings.py:19
    • Evidence: Line 19 imports SECRET_KEY from Django globals; lines 70/74 immediately shadow it.
    • Recommendation: Remove line 19 — dead import. Linter would flag it.

    [medium / confidence high] Schema generation warnings for LogbookMigrationRequest serializers¶

    • File: api/serializers/serializers_migration.py
    • Evidence: 6 drf_spectacular.W001 warnings — get_member, get_target_level, get_skill_entries return types not annotated on both LogbookMigrationRequestListSerializer and LogbookMigrationRequestSerializer
    • Category: openapi-drift
    • Recommendation: Add @extend_schema_field(MemberBaseSerializer) (or equivalent) decorators, or type hint -> dict on each get_* method. Otherwise Swagger clients see these fields as plain strings.

    [medium / confidence high] VehicleViewSet queryset resolution fails in schema gen¶

    • File: api/views/views_vehicle.py
    • Evidence: drf_spectacular.W001 — failed to obtain model through view's queryset (AnonymousUser passed to Field('id')). Path parameter id also untyped.
    • Category: openapi-drift
    • Recommendation: Two fixes needed:
    • Add queryset = Vehicle.objects.none() on the ViewSet or guard get_queryset() with if getattr(self, 'swagger_fake_view', False): return Vehicle.objects.none()
    • In urls.py or via lookup_value_regex, type the path parameter as int so Swagger stops guessing.

    [medium / confidence high] StatusBc4Enum collision in OpenAPI schema¶

    • Evidence: Warning: enum naming encountered a non-optimally resolvable collision for fields named "status"
    • Category: openapi-drift
    • Recommendation: Add entries in SPECTACULAR_SETTINGS['ENUM_NAME_OVERRIDES'] for the specific status fields (e.g., TripApprovalStatusEnum, UpgradeRequestStatusEnum, ClubNewsStatusEnum, LogbookMigrationStatusEnum, WebsitePaymentStatusEnum) to give each a distinct name. Clients currently see a StatusBc4Enum which is meaningless.

    [low / confidence medium] ALLOWED_HOSTS includes a hardcoded IP and a port-qualified host¶

    • File: ad4x4/settings.py:81
    • Evidence: ALLOWED_HOSTS = ['0.0.0.0', 'localhost', '127.0.0.1', 'ap.ad4x4.com', '78.47.162.184', 'localhost:50891']
    • Category: config-smell
    • Recommendation: 78.47.162.184 is the Hetzner IP — acceptable but brittle if IP changes. Move to env var. localhost:50891 is very suspicious — ports aren't allowed in ALLOWED_HOSTS (Django strips them anyway), so this entry does nothing. Remove it or convert to comment.

    [low / confidence high] Settings import ordering / Firebase init at module load¶

    • File: ad4x4/settings.py:16–36
    • Evidence: Firebase Admin SDK is initialized at settings.py import time. This means every manage.py command (including check, makemigrations, tests) runs a network-capable SDK init.
    • Recommendation: Move Firebase init into an AppConfig.ready() method, or lazy-init on first use. Side benefit: tests and check run faster and don't need FCM creds.

    Production-branch verification (settings.py:84–92)¶

    Manually confirmed the production branch sets all six security headers correctly:

    if not DEV:
    SECURE_SSL_REDIRECT = True
    SECURE_HSTS_SECONDS = 31536000
    SECURE_HSTS_INCLUDE_SUBDOMAINS = True
    SECURE_HSTS_PRELOAD = True
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
    SECURE_CONTENT_TYPE_NOSNIFF = True
    SECURE_BROWSER_XSS_FILTER = True

    This is correct. The deploy-check warnings for those six are dev-mode noise.
