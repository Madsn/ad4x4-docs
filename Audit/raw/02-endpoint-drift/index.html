    Findings¶

    [high / confidence high] Duplicate URL registrations for three auth endpoints¶

    • Files: ad4x4/urls.py
    • Evidence: list_urls reports each of these URLs twice with different view handlers:
    • api/auth/login/ → api.views.views_auth.LoginView AND rest_registration.api.views.login.LoginView
    • api/auth/logout/ → api.views.views_auth.LogoutView AND rest_registration.api.views.login.LogoutView
    • api/auth/change-password/ → api.views.views_auth.CustomChangePasswordView AND rest_registration.api.views.change_password.ChangePasswordView
    • Category: routing fragility
    • Why this matters: Django uses the first matching URL pattern. CLAUDE.md §7 explicitly says the custom LoginView is mounted before rest_registration's include so it "shadows" them. That works today, but a future refactor that reorders includes silently changes behavior — the rest_registration views don't honor the login/username/email case-insensitive lookup or the password-change-blacklists-all-tokens rule (§15). A regression here is silent.
    • Recommendation: Either (a) exclude those three routes from the rest_registration include using its include_urls config, or (b) add a test_urls.py assertion that resolve('/api/auth/login/') returns views_auth.LoginView. Prefer (a).

    [medium / confidence high] Undocumented register-email / verify-email endpoints¶

    • Evidence: list_urls shows:
    • api/auth/register-email/ → rest_registration.api.views.register_email.RegisterEmailView
    • api/auth/verify-email/ → rest_registration.api.views.register_email.VerifyEmailView
    • CLAUDE.md §6 documents only register/, verify-registration/, reset-password/, send-reset-password-link/, change-password/.
    • Category: doc-drift
    • Why this matters: Email change flow is exposed to clients but undocumented. If these are intentional, doc them. If unintentional (e.g. from default rest_registration URL include), disable them.
    • Recommendation: Decide: either remove from URL conf or add to CLAUDE.md §6 with semantics (what body shape, what effect). Ask Mikkel (ADMINS) whether change-email flow is a supported product feature.

    [medium / confidence high] api/vehicles/<int:pk>/set_primary/ is wired manually, not as ViewSet @action¶

    • File: ad4x4/urls.py:205 (per member-flow review agent finding)
    • Evidence: list_urls shows api/vehicles/<int:pk>/set_primary/ routed to VehicleViewSet but NOT through the router — it's a manual as_view() call in urls.py.
    • Category: framework-smell
    • Consequence: DRF @action decorators on the method are dead; @extend_schema on the method doesn't attach to the Swagger spec; permissions/throttles from the ViewSet may not apply correctly. The schema generation warning drf_spectacular.W001 about VehicleViewSet (see raw/01-system-check.md) is a downstream symptom.
    • Recommendation: Convert to a proper @action(detail=True, methods=['post']) method and let the router wire it. Alternatively turn it into a standalone APIView.

    [low / confidence high] Separate TripCreateView / TripEditView outside the TripViewSet router¶

    • File: ad4x4/urls.py + api/views/views_trip.py
    • Evidence:
    • api/trips → TripCreateView (note: no trailing slash)
    • api/trips/<int:pk> → TripEditView (also no trailing slash)
    • api/trips/ → TripViewSet list/retrieve/destroy (from router, with trailing slash)
    • Category: convention-drift
    • Why this matters: CLAUDE.md §6 lists Trips (/api/trips/) as "Standard CRUD" via ViewSet. In reality create and update go to dedicated views (hence the slashless variant). Trailing-slash sensitivity means a client that hits POST /api/trips/ might not reach TripCreateView — depends on APPEND_SLASH middleware behavior.
    • Recommendation: Either merge TripCreateView / TripEditView logic back into TripViewSet.create / update (DRY and consistent), OR document this split in CLAUDE.md §6 with a clear rationale. Also audit client calls — does the Flutter app hit /api/trips (no slash) or /api/trips/?

    [low / confidence high] Router regex patterns leak into URL conf (^clubnews/$ etc.)¶

    • Evidence: All router-generated URLs are prefixed with ^ (regex start anchor) because the routers are presumably being include()d with re_path instead of path. Visually obvious in every list_urls entry starting with ^.
    • Category: style / hygiene
    • Why this matters: Works fine functionally but is unusual — Django 6 prefers path + include. Router's ^ prefix appearing in user-visible URL names is a smell.
    • Recommendation: In ad4x4/urls.py, ensure router includes use path('api/', include(router.urls)), not re_path(r'^api/', include(router.urls)). Cosmetic but aligns with the rest of the codebase.

    [low / confidence medium] NotificationLogViewSet only exposes list, not detail¶

    • Evidence: Only api/^notifications/$ pattern, no (?P<pk>...) variant.
    • Category: rest-surface
    • Why this matters: If the client ever wants to retrieve a specific NotificationLog by ID (e.g. for deep-linking), it can't. mark-as-read handles one ID at a time but it's a write endpoint.
    • Recommendation: Either confirm the product decision (list-only is intentional) and document in CLAUDE.md §6, or expose retrieve.
