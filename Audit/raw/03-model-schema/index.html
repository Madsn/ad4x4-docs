    Cross-reference of mcp__django-ai-boost__list_models output vs CLAUDE.md §5 vs api/models/*.py source.

    Caveat¶

    mcp__django-ai-boost__database_schema failed (dev DB dev doesn't exist). This step relies on Django ORM model introspection only — custom indexes/constraints added via raw SQL in migrations would not be detected. Recommended follow-up: create a throwaway DB, run migrations, re-run database_schema to catch any migration-level schema that bypasses ORM declaration.

    [high / confidence high] TripRegistrationCancellationReason is a cancellation audit table with no documentation¶

    • Fields: trip, member, removed_by (nullable FK, for admin removals), removal_date, reason (TextField)
    • Why it matters: This model persists every cancellation/removal. It's the audit log for who removed whom and why. Critical for disputes, but currently has no mention in §5, no admin note in CLAUDE.md §11, and the trip-flow agent found async tasks whose signature expects this model (see raw/06-code-review-trip-flow.md and raw/08-async-tasks.md — the call sites pass (user, trip) where the task expects a TripRegistrationCancellationReason instance).
    • Recommendation: Add to §5. Also verify retention policy — does this get purged, ever?

    [medium / confidence high] Member.token_version still present — cleanup PR still pending¶

    • Field: Member.token_version (PositiveIntegerField)
    • Evidence: list_models confirms the column is still on the model. Per CLAUDE.md §7 and §15, this is "legacy, unused" — session invalidation now flows through simplejwt's token_blacklist.
    • Auth review agent (a90998f56c9ac802c) confirmed nothing in views_auth.py, permissions.py, or util.py reads or writes it.
    • Recommendation: Create the follow-up PR mentioned in §15 — drop the column in a migration. Until it's gone, each Member row carries an unused 4-byte int.

    [medium / confidence medium] Member.gender max_length=3 for single-char codes (M/F/O)¶

    • Field: gender = CharField(max_length=3)
    • Rationale unclear: single-char codes need only max_length=1. 3 might be legacy or intentional extensibility (e.g. for future codes). No CLAUDE.md §5 comment explains.
    • Recommendation: Either (a) shorten to max_length=1 in a tiny migration, or (b) document the 3-char reservation in §5 (e.g. for future non-binary codes).

    [medium / confidence high] Vehicle.brand max_length=8 — might clip new brands¶

    • Field: brand = CharField(max_length=8)
    • Evidence: Doc §5 says "74 CarBrand choices". Brand codes are stored as short tokens, so 8 is likely enough, but the enum is in api/choices.py. Any future brand with a longer code fails silently at write time.
    • Recommendation: Grep api/choices.py for the longest CarBrand token; if 8 is hit, bump to 16 proactively.

    [low / confidence high] Vehicle.name exists but not in §5¶

    • CLAUDE.md §5 lists brand, model, year, color, image, is_primary for Vehicle. Actual model also has name (CharField, nullable).
    • Recommendation: Add name to §5.

    [low / confidence high] UpgradeRequest.applicant_reason uses max_length=1500 on a TextField¶

    • Evidence: TextField ignores max_length at the DB level. It only constrains form rendering.
    • Impact: A malicious or buggy client can submit 1 MB of applicant_reason and the DB will accept it; DRF validates only up to max_length if the serializer is a CharField(style='textarea', max_length=1500). Verify the serializer enforces it.
    • Recommendation: Add an explicit check in the serializer (validate_applicant_reason), or convert to CharField(max_length=1500) since the length is bounded.

    [medium / confidence high] LogbookSkillReference has no unique constraint on (member, trip, logbook_skill)¶

    • Evidence: list_models shows the three FKs but no UniqueConstraint. Cross-reference with logbook review agent (raw/06-code-review-logbook.md finding F3/F4): the service layer mitigates by deleting-and-reinserting, but that wipes data if two marshals write entries for the same trip.
    • Recommendation: Add in a migration: python class Meta: constraints = [ models.UniqueConstraint( fields=['member', 'trip', 'logbook_skill'], name='uniq_logbook_skill_ref_per_trip', ), ] Then replace the delete-reinsert in _manage_logbook_skill_references with update_or_create.

    [low / confidence medium] Explicit db_index=True is used on hot paths but coverage may be uneven¶

    • Files with explicit db_index=True: models_trip.py (starttime, endtime, approvalstatus, TripRegistration member/trip/checkedin), models_member.py (Meta indexes), models_upgraderequest.py (Meta indexes), models_vehicle.py, models_sponsors.py, models_geocoding_cache.py.
    • Not explicitly indexed but likely filtered:
    • NotificationLog.timestamp (purged after 60 days — purge scan benefits from index)
    • NotificationLog.is_read (mark-as-read queries)
    • TripRegistration.registration_date
    • UpgradeRequest.verdict_date (sorting)
    • LogbookEntry.created_at (listing)
    • ClubNews.submit_date (ordering)
    • Recommendation: Spot-check with a real query profile. For each of the above, if it's used in filter / order_by in more than a couple of places, add db_index=True or a Meta.indexes = [models.Index(fields=['...'])]. Not urgent until traffic grows.

    [low / confidence high] ConfigurableSettings.email_sleep_period_ms naming suggests milliseconds but CLAUDE.md §5 says "email sleep period"¶

    • Field: email_sleep_period_ms = PositiveSmallIntegerField(...)
    • Observation: PositiveSmallIntegerField max = 32,767. If the suffix really means ms, max sleep is ~33 seconds — fine for batch pacing. Not a bug but §5 should note the unit.
    • Notifications-review agent (raw/06-code-review-notifications.md) also noted time.sleep usage blocking Huey workers — worth cross-reference.
    • Recommendation: Clarify the doc: "between-email sleep in ms" and verify email_notifications.py converts to seconds for time.sleep.

    [low / confidence high] ConfigurableSettings.notification_dry_run is the actual field name¶

    • CLAUDE.md §5 says "notification dry-run toggle" but doesn't give the exact field name.
    • Notifications-review agent found the toggle exists but may not be respected by all channels.
    • Recommendation: §5 already uses a prose description; confirm all 4 channels honor notification_dry_run (see raw/06-code-review-notifications.md).

    [low / confidence high] ConfigurableSettings.vehicle_limit_per_member exists (good)¶

    • Confirms CLAUDE.md §5 claim. The member-flow agent found a TOCTOU in enforcement (raw/06-code-review-member-flow.md).
