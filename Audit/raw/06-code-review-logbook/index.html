    Code Review — Logbook (api/views/views_logbook.py)¶

    Scope: api/views/views_logbook.py only. Supporting files (models, permissions, service helper) read for context but not in scope.

    Authoritative PermissionMatrix actions expected in this module: CREATE_LOGBOOK_ENTRIES, SIGN_LOGBOOK_SKILLS, CREATE_LOGBOOK_ENTRIES_SUPERUSER, APPROVE_LOGBOOK_MIGRATION. The file does not implement approval-migration or count-requirement endpoints, so those topics are addressed as coverage gaps.

    Findings¶

    F1 — LogbookEntryViewSet list/detail suffers classic N+1 on M2M + FKs¶

    • Severity: high
    • File:line: api/views/views_logbook.py:33
    • Confidence: high
    • Category: n+1
    • Evidence: queryset = LogbookEntry.objects.all().order_by('id') with LogbookEntrySerializer using fields = '__all__' (see api/serializers/serializers_other.py:55-58). LogbookEntry has three FKs (trip, member, signed_by) and one M2M (skills_verified). DRF's ModelSerializer will hit a separate query per instance for each FK and per-instance for the M2M. With default pagesize=10, listing costs roughly 1 + 10*(3 FKs) + 10*(1 M2M) = 41 queries; at pagesize=500 it balloons to 2000+.
    • Recommendation: Override get_queryset() to attach select_related('trip', 'member', 'signed_by') and prefetch_related('skills_verified'). Same treatment for LogbookSkillReferenceViewSet.queryset (line 27) which has five FKs (logbook_skill, member, trip, signed_by, entered_by) and is similarly unprotected.

    F2 — _manage_logbook_skill_references is itself N+1 in the skill-loop¶

    • Severity: high
    • File:line: api/views/views_logbook.py:136-158
    • Confidence: high
    • Category: n+1
    • Evidence: A LogbookSkill.objects.get(id=skill_id) call sits inside the for skill_id in skills_verified: loop, followed by a single-row LogbookSkillReference.objects.create(...). For N verified skills this runs 2N queries (1 lookup + 1 insert), plus the single .delete() up front. It also silently ignores unknown skill IDs with a logger.warning — the client gets a 201 even though some skills were not recorded, which is a data-integrity hazard.
    • Recommendation: Batch: skills = LogbookSkill.objects.in_bulk(skill_ids); validate len(skills) == len(skill_ids) and raise ValidationError('one_or_more_skills_not_found') if not; then LogbookSkillReference.objects.bulk_create([... for skill in skills.values()]). This mirrors what TripLogbookEntryCreateView already does at line 309-312 and makes the behaviours consistent.

    F3 — No uniqueness guard on LogbookSkillReference (member, trip, logbook_skill)¶

    • Severity: high
    • File:line: api/views/views_logbook.py:139-156; also api/models/models_logbook.py:24-30
    • Confidence: high
    • Category: dup-prevention
    • Evidence: The model has no unique_together / UniqueConstraint covering (member, trip, logbook_skill). The view tries to enforce uniqueness by deleting every row for (member, trip) and recreating on every perform_create/perform_update. Any path that creates a LogbookSkillReference directly (admin, shell, other views, migrations) bypasses this. Worse, the delete-then-recreate pattern destroys entered_at, entered_by, and signed_by history on every edit — a marshal's original sign-off timestamp is silently overwritten.
    • Recommendation: Add a UniqueConstraint(fields=['member', 'trip', 'logbook_skill'], name='uniq_skillref_per_trip_member') and use update_or_create (or bulk_create(..., ignore_conflicts=True) plus targeted updates) so existing signatures are preserved when a marshal edits an entry.

    F4 — _manage_logbook_skill_references deletes across all logbook entries for (member, trip)¶

    • Severity: high
    • File:line: api/views/views_logbook.py:139-142
    • Confidence: high
    • Category: data-integrity
    • Evidence: The filter is LogbookSkillReference.objects.filter(member=member, trip=trip).delete() — it does not scope by logbook_entry or signed_by. If two marshals each wrote a LogbookEntry for the same (member, trip) — possible because there is no uniqueness constraint on LogbookEntry either — saving or updating the second entry wipes the first marshal's skill references. The M2M LogbookEntry.skills_verified relation is not similarly clobbered, so the two stores go out of sync.
    • Recommendation: Either (a) enforce one LogbookEntry per (member, trip) at the model layer so the assumption is valid, or (b) scope deletes to the specific entry by storing logbook_entry FK on LogbookSkillReference. Option (a) is the cheaper fix and matches current intent.

    F5 — LogbookSkillReferenceViewSet has no PermissionMatrix check¶

    • Severity: critical
    • File:line: api/views/views_logbook.py:26-29
    • Confidence: high
    • Category: perms
    • Evidence: permission_classes = (permissions.IsAuthenticatedOrReadOnly,). Any authenticated member can POST / PUT / PATCH / DELETE LogbookSkillReference rows, setting member, trip, signed_by, entered_by to arbitrary values. This bypasses the entire CREATE_LOGBOOK_ENTRIES / SIGN_LOGBOOK_SKILLS gate enforced on the entry side — a rank-and-file member can sign themselves off for any skill on any trip. This directly contradicts CLAUDE.md §8 ("every protected view must add a PermissionMatrix check").
    • Recommendation: Either disable write methods (ReadOnlyModelViewSet) or apply a permission that verifies SIGN_LOGBOOK_SKILLS against the target trip's level and forces signed_by=request.user. Given the entry viewset owns the write path, ReadOnlyModelViewSet is the safer default.

    F6 — LogbookEntryViewSet does not force signed_by on update¶

    • Severity: high
    • File:line: api/views/views_logbook.py:199-216
    • Confidence: high
    • Category: data-integrity / perms
    • Evidence: perform_create at line 190 does serializer.validated_data['signed_by'] = self.request.user, but perform_update has no such line. A client can PATCH signed_by to an arbitrary member ID (the serializer uses fields = '__all__'), and the request user gets credited under someone else's name. Worse, _manage_logbook_skill_references is still called with signed_by_user=self.request.user (line 216) — so the marshal history on LogbookSkillReference drifts out of sync with LogbookEntry.signed_by.
    • Recommendation: Set serializer.validated_data['signed_by'] = self.request.user in perform_update too, or mark signed_by as read_only in the serializer and inject it server-side. Consider a custom LogbookEntrySerializer (not fields='__all__') with signed_by and member read-only after creation.

    F7 — perform_update does not revalidate check-in status¶

    • Severity: medium
    • File:line: api/views/views_logbook.py:199-216
    • Confidence: high
    • Category: data-integrity
    • Evidence: perform_create enforces "member must be registered and checked in" at line 178-187. perform_update skips this — a PATCH that swaps trip or member on an existing entry never rechecks. Combined with the fields='__all__' serializer, a user with edit permission can redirect an entry to a different trip the member never attended.
    • Recommendation: Either make trip and member read-only after creation in the serializer (recommended — entries are an audit record), or repeat the TripRegistration.objects.get(trip=..., member=..., checked_in=True) check in perform_update.

    F8 — Outer try/except Exception swallows errors with generic 400¶

    • Severity: medium
    • File:line: api/views/views_logbook.py:70-72, 107-109, 132-134
    • Confidence: high
    • Category: style / other
    • Evidence: Three identical except Exception as e: blocks return {'message': str(e)} at HTTP 400. This masks IntegrityError, ValidationError, database timeouts, and programming bugs behind a single "bad request" response and leaks internal error strings to clients. It also prevents Sentry from properly grouping unrelated failures.
    • Recommendation: Remove the broad except (DRF's exception handler already returns uniform error responses) or narrow to ValidationError + IntegrityError. Let unexpected exceptions propagate so sentry_sdk captures the stack trace. The unified envelope can be applied via a custom exception handler instead.

    F9 — perform_create transaction does not wrap the check-in lookup¶

    • Severity: low
    • File:line: api/views/views_logbook.py:177-197
    • Confidence: medium
    • Category: tx
    • Evidence: The TripRegistration.objects.get(...) at line 179 happens outside transaction.atomic(). A concurrent unregister + checkout (that flips checked_in off and deletes the registration) between the check and the save could produce orphaned logbook entries. Because LogbookEntry.trip/member are FKs to Trip/Member (not TripRegistration), the orphan is silent.
    • Recommendation: Move the entire body (check-in lookup + save + skill refs) inside the with transaction.atomic(): block and use select_for_update() on the TripRegistration row if concurrent unregister is a realistic race. Low severity — concurrent unregister during marshal sign-off is unusual.

    F10 — TripLogbookEntryCreateView bypasses LogbookSkillReference entirely¶

    • Severity: high
    • File:line: api/views/views_logbook.py:264-326
    • Confidence: high
    • Category: data-integrity
    • Evidence: This view creates a LogbookEntry with entry.skills_verified.set(skills_qs) (line 321) but never creates any LogbookSkillReference rows. That contradicts the data model described in CLAUDE.md §5 (LogbookSkillReference = "granular join: member earned a specific skill on a specific trip"). Entries created through this endpoint will be missing from every LogbookSkillReference-based report (including upgrade eligibility and auto-upgrade checks in api/services/).
    • Recommendation: Call _manage_logbook_skill_references (or an equivalent service function) so both sides stay in sync, or delete this duplicate view and keep only LogbookEntryViewSet.create.

    F11 — TripLogbookEntryCreateView is not wrapped in a transaction¶

    • Severity: medium
    • File:line: api/views/views_logbook.py:314-321
    • Confidence: high
    • Category: tx
    • Evidence: LogbookEntry.objects.create(...) then entry.skills_verified.set(skills_qs) run as two separate commits. A failure between them (connection drop, constraint error on the M2M) leaves an entry with zero skills and returns 500 — the client has no signal it should retry and no way to distinguish partial from full success.
    • Recommendation: Wrap the block in transaction.atomic(), matching the pattern used in perform_create.

    F12 — try/except Trip.DoesNotExist after get_object() is dead code¶

    • Severity: nit
    • File:line: api/views/views_logbook.py:270-273
    • Confidence: high
    • Category: style
    • Evidence: generics.CreateAPIView.get_object() raises Http404, not Trip.DoesNotExist. The except block will never fire — a missing trip returns a DRF 404 before reaching the custom response. DRF permission class IsAuthenticated is also redundant with the project default in settings.py.
    • Recommendation: Drop the try/except and rely on DRF's built-in 404, or use get_object_or_404(Trip, pk=kwargs['pk']) explicitly with a custom message.

    F13 — skills_verified serializer field is ListField(IntegerField) — accepts unknown IDs by default¶

    • Severity: medium
    • File:line: api/views/views_logbook.py:275-281; api/serializers/serializers_logbook.py:34-37
    • Confidence: high
    • Category: data-integrity
    • Evidence: SignLogbookEntrySerializer uses serializers.ListField(child=serializers.IntegerField()). Validation of skill existence is done post-hoc at line 309-312 by counting. That works for this view but leaves check_logbook_entry_permissions at line 284 being called with skills_ids as raw ints — the helper may iterate them differently than when called from LogbookEntryViewSet where skills_ids are the validated PKs from a PrimaryKeyRelatedField. Any inconsistency between these paths will silently diverge permission behaviour.
    • Recommendation: Switch to PrimaryKeyRelatedField(many=True, queryset=LogbookSkill.objects.filter(active=True)) — DRF validates existence/activity and returns 400 at parse time, eliminating the count check at line 310 and unifying the data shape.

    F14 — LogbookSkill.count_requirement is never checked in this module¶

    • Severity: medium
    • File:line: api/views/views_logbook.py (absent)
    • Confidence: high
    • Category: data-integrity / other
    • Evidence: The audit brief flags count_requirement as an expected enforcement point. This file contains no reference to it. If upgrade eligibility must confirm a member has signed the skill N times, that logic must live elsewhere (api/services/upgrade_eligibility.py is the likely home per §9). Verify and document — if the check does not exist anywhere, level upgrades can be granted below the configured threshold.
    • Recommendation: Out of file scope, but surface this for audit 07 (services) or 08 (upgrade flow). Mark in the findings doc so reviewers know it was not confirmed here.

    F15 — LogbookMigrationRequest endpoints are absent from this file¶

    • Severity: low
    • File:line: api/views/views_logbook.py (absent)
    • Confidence: high
    • Category: other
    • Evidence: The audit brief asks about migration-request approval, double-upgrade protection, and uploaded_pdf size / content-type checks. None of this is in views_logbook.py. CLAUDE.md §6 lists /api/logbook-migrations/ so the endpoint exists somewhere — possibly its own module or a separate ViewSet file.
    • Recommendation: Out of scope for this file. Flag for the reviewer running the migration-request audit. Confirm APPROVE_LOGBOOK_MIGRATION permission is enforced and that uploaded_pdf has FileExtensionValidator(['pdf']) plus a size limit in its serializer, and that status transitions guard against re-applying an already-APPROVED request.

    F16 — LogbookSkillSerializer exposes all fields but active¶

    • Severity: nit
    • File:line: api/views/views_logbook.py:252-261 (re-exports serializer behaviour); api/serializers/serializers_other.py:60-63
    • Confidence: medium
    • Category: style
    • Evidence: Cached list endpoint returns level_requirement as a bare ID and category as a bare ID with no nested names — clients have to resolve them separately, which defeats the 10-minute cache benefit on mobile. Not a correctness bug.
    • Recommendation: Consider depth = 1 or nested serializers if the mobile app does separate lookups. Verify with the client team before changing — breaking shape without coordination is worse than the current shape.

    F17 — Imports from api.models are not using select_related-friendly managers¶

    • Severity: nit
    • File:line: api/views/views_logbook.py:15
    • Confidence: low
    • Category: style
    • Evidence: Member is imported but never used in this module (only type-hinted usage via data['member']).
    • Recommendation: Drop unused import. Linter hygiene.

    Coverage gaps (for other audits)¶

    • count_requirement enforcement path — check api/services/upgrade_eligibility.py and api/services/auto_upgrade_service.py.
    • Migration request approval + uploaded_pdf validation — check the serializer and view for /api/logbook-migrations/.
    • LogbookSkillReference writes via admin — verify api/admin.py enforces matching permissions or is limited to superusers.
    • Bulk sign-off flows on the Trip viewset (/api/trips/<pk>/logbook-entries, /api/trips/<pk>/viewlogbooks) — not in this file.
