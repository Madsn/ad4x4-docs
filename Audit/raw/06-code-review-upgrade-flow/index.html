    Code Review: Upgrade Flow¶

    Audit of api/views/views_upgrade.py, api/views/views_upgraderequest.py, api/services/upgrade_eligibility.py, and api/services/auto_upgrade_service.py.

    Focus areas: race conditions in voting, transaction atomicity in approval, N+1 queries, permission-matrix coverage, verdict reason handling, auto-upgrade vs manual-upgrade conflicts, applicant_str backup, idempotency on logbook completion, and timezone.now() vs datetime.datetime.now() under USE_TZ=False.

    Findings¶

    F1 — Approve/Decline path is not atomic (missing transaction.atomic)¶

    • Severity: critical
    • Confidence: high
    • Category: tx
    • File: api/views/views_upgraderequest.py:106-127
    • Evidence: handle_upgrade_request_verdict() performs four distinct writes — upgrade_request.save() (status/finalapprover/verdictdate), applicant.level = target_level, applicant.groups.add(auto_group), applicant.save() — followed by send_upgrade_request_handled_notification(...). None of this is wrapped in transaction.atomic. A DB error or process crash between steps leaves the system in a corrupt state: request marked APPROVED but member still at old level, or member promoted to new level without the auto_group assignment (which governs PermissionMatrix checks elsewhere). The notification is also fired from inside the view — if the preceding save succeeded but a later save raises, the member is notified of a half-applied upgrade.
    • Recommendation: Wrap the mutation block in transaction.atomic(), then fire send_upgrade_request_handled_notification only after the transaction commits (use transaction.on_commit(...)). The Huey task should be enqueued post-commit to avoid the classic "task runs before row is visible" race.

    F2 — Voting endpoint has a TOCTOU race on status¶

    • Severity: high
    • Confidence: high
    • Category: race
    • File: api/views/views_upgraderequest.py:232-257
    • Evidence: UpgradeRequestVoteView.post() reads upgrade_request.status at line 234, then does M2M adds/removes (lines 239-250), then unconditionally re-assigns status=IN_PROGRESS and calls .save() (lines 254-256). Two simultaneous requests (one voter, one approver pressing approve/decline) can race: approver transitions status to APPROVED, voter then silently overwrites to IN_PROGRESS because the voter loaded a stale instance. Result: an approved upgrade appears back "in progress" and the applicant has already been upgraded. Also, because .save() writes the whole row, any other field mutated concurrently is clobbered.
    • Recommendation: Use select_for_update() inside transaction.atomic when fetching upgrade_request, re-check the status guard after lock, and .save(update_fields=['status']) to narrow the write. Better yet, do the M2M mutations after the status guard is re-verified.

    F3 — Vote is not atomic across three M2M operations¶

    • Severity: high
    • Confidence: high
    • Category: race
    • File: api/views/views_upgraderequest.py:239-250
    • Evidence: Each vote branch does add() to one list and remove() from two others as three separate queries. A failure (connection drop, timeout) after add() but before remove() leaves a user counted in two vote buckets simultaneously. The annotated counts on the queryset (yes_voters_count, no_voters_count, defer_voters_count, line 26-30) will then double-count that voter, skewing the verdict view.
    • Recommendation: Wrap the three M2M operations in transaction.atomic. Consider a single vote field on a through-model with a UniqueConstraint(fields=['upgrade_request', 'member']) — this makes vote-change an update/upsert rather than three independent writes.

    F4 — Auto-upgrade has no lock and can race with manual approval¶

    • Severity: high
    • Confidence: high
    • Category: race
    • File: api/services/auto_upgrade_service.py:30-49
    • Evidence: handle_logbook_entry_created reads member.level_id, compares to source_level.id, then writes member.level = target_level and member.save(). No lock, no transaction.atomic, no guard against a concurrent manual approval that is also writing applicant.level. Two simultaneous triggers (e.g., marshal signs a logbook entry while an approver clicks approve) can produce: (a) double-group-add (benign but noisy), (b) partial rollback of the manual upgrade's group change, or (c) member.save() clobbering unrelated fields the other request just wrote. The guard on member.level_id != source_level.id at line 33 is the only idempotency check — it is effective only if both paths see the same "before" state.
    • Recommendation: Wrap the whole routine in transaction.atomic and fetch the member under select_for_update(). Also use .save(update_fields=['level']) instead of a full-row save.

    F5 — Auto-downgrade race when logbook entry is deleted¶

    • Severity: high
    • Confidence: high
    • Category: race
    • File: api/services/auto_upgrade_service.py:77-94
    • Evidence: handle_logbook_entry_deleted does remaining_entries = LogbookEntry.objects.filter(member=member).count() and only downgrades if remaining_entries == 0. The post_delete signal fires after the deletion, but two concurrent deletes of the last two entries can both see remaining_entries == 0 and both run the downgrade. More subtly, a new logbook entry being created concurrently may not yet be visible to the counting query, and the member will be downgraded despite having a fresh entry.
    • Recommendation: Lock the member row (select_for_update) inside a transaction, re-count inside the lock, only then demote. Again, use update_fields=['level'] to avoid full-row writes.

    F6 — verdict_date uses datetime.datetime.now() instead of timezone.now()¶

    • Severity: medium
    • Confidence: high
    • Category: other
    • File: api/models/models_upgraderequest.py:50
    • Evidence: self.verdict_date = datetime.datetime.now() in UpgradeRequest.save(). The import is from django.db.models.functions import datetime, which is not Python's datetime module — it is Django's database-function namespace. This is almost certainly broken at runtime and relies on accidentally working because django.db.models.functions.datetime re-exports Python's datetime. CLAUDE.md §15 explicitly calls out: "Never use datetime.datetime.now() — use django.utils.timezone.now()." The view at views_upgraderequest.py:115 correctly uses timezone.now(); the model then overwrites it with datetime.datetime.now() during save(). If the project ever enables USE_TZ=True, this becomes a naive/aware mismatch bug.
    • Recommendation: Import from django.utils import timezone and use timezone.now().

    F7 — N+1 on recent-trips serialization in eligibility check¶

    • Severity: medium
    • Confidence: high
    • Category: n+1
    • File: api/services/upgrade_eligibility.py:74-82
    • Evidence: recent_trips = trips_at_current_level_qs.order_by(...)[:limit] then the for-loop reads trip.lead.id, trip.lead.username, trip.level.id, trip.level.name, trip.level.numeric_level. Each access fires a SELECT on Member and Level. For N trips this is 2N extra queries per eligibility call. This endpoint is hit on upgrade-request creation (line 46 of views_upgraderequest.py) and by UpgradeEligibilityView.get().
    • Recommendation: Add .select_related('lead', 'level') to trips_at_current_level_qs.

    F8 — N+1 on logbook skill requirements¶

    • Severity: medium
    • Confidence: high
    • Category: n+1
    • File: api/services/upgrade_eligibility.py:99-130
    • Evidence: For each required_skill, the code runs LogbookEntry.objects.filter(...) (N queries), then .count() (N queries), then iterates entries reading entry.trip.id, entry.trip.start_time, entry.signed_by.id, entry.signed_by.username (2 queries per entry). Total: O(skills × entries) database round-trips for a single eligibility lookup.
    • Recommendation: Prefetch all skill entries at once with LogbookEntry.objects.filter(member=target_member, skills_verified__in=required_skills).select_related('trip', 'signed_by'), then group in Python. Or annotate per-skill counts via Count with filter=Q(skills_verified=skill) in a single aggregate.

    F9 — Permission inconsistency: list has no superuser fast-path¶

    • Severity: medium
    • Confidence: medium
    • Category: perms
    • File: api/views/views_upgraderequest.py:88-90
    • Evidence: list and retrieve use HasViewUpgradeRequestPermission, which calls permission_matrix_exists_or_user_is_superuser — that helper does permit superusers. retrieve however goes through HasViewUpgradeRequestPermission which ignores the per-request target level, so a user with VIEW_UPGRADE_REQ scoped to specific levels via PermissionMatrix.levels can still list and retrieve requests for levels they were not granted. Contrast with HasEditUpgradeRequestPermission which does pass the target level (via check_upgrade_request_permission_against_perm_matrix). This is either an intentional coarser-read/finer-write split or a bug.
    • Recommendation: If level-scoped view is intended, switch retrieve to check_upgrade_request_permission_against_perm_matrix(..., VIEW_UPGRADE_REQ).

    F10 — Applicant eligibility is not re-checked at approval time¶

    • Severity: medium
    • Confidence: high
    • Category: other
    • File: api/views/views_upgraderequest.py:106-127
    • Evidence: Eligibility is checked only at creation time (lines 46-65). Between creation and approval, the applicant may have been demoted, had logbook entries deleted, or already been promoted by another flow (e.g., auto-upgrade). The approve path blindly sets applicant.level = upgrade_request.target_level, which can downgrade a member who is already at a higher level than target_level.
    • Recommendation: At approval time, re-run eligibility and guard against applicant.level.numeric_level >= target_level.numeric_level.

    F11 — applicant.save() full-row write can overwrite unrelated fields¶

    • Severity: medium
    • Confidence: high
    • Category: race
    • File: api/views/views_upgraderequest.py:124 and api/services/auto_upgrade_service.py:41, 88
    • Evidence: applicant.save() writes every field, including last_visited (touched by LastVisitedMiddleware), trip_count, profile fields, etc. A concurrent request updating any of those will race. Particularly nasty given LastVisitedMiddleware writes last_visited on every authenticated request.
    • Recommendation: Use .save(update_fields=['level']) throughout the upgrade paths.

    F12 — verdict_reason applied before permission check (rejected requests)¶

    • Severity: medium
    • Confidence: high
    • Category: perms
    • File: api/views/views_upgraderequest.py:154-162
    • Evidence: UpgradeRequestDeclineView.post sets upgrade_request.verdict_reason = request.data.get('verdict_reason') before handle_upgrade_request_verdict runs the permission check. If the permission check fails, the in-memory object has already been mutated; while .save() is only called inside the handler on the permitted path, returning a 403 here means the field was temporarily set on the instance, which is confusing and fragile. Additionally, the verdict_reason has no sanitisation — the field accepts raw text up to 500 chars (per model), but the serializer here accepts max_length=500 which matches — fine, but no escaping when rendered in emails. Check upgrade_request_voters.html for context injection.
    • Recommendation: Validate via the UpgradeRequestRejectSerializer (serializer.is_valid(raise_exception=True)) before touching the model. Treat verdict_reason as untrusted when rendering templates (Django templates auto-escape, but confirm no |safe filter is used).

    F13 — Duplicate-request check only covers applicant=request.user¶

    • Severity: medium
    • Confidence: high
    • Category: other
    • File: api/views/views_upgraderequest.py:73-76
    • Evidence: The "duplicate_request" guard filters applicant=request.user, but the create serializer accepts an arbitrary applicant (line 44: serializer.validated_data['applicant']). A user with CREATE_UPGRADE_REQ_FOR_OTHERS could open a second upgrade request for another member (the duplicate check misses because request.user is not the applicant).
    • Recommendation: Filter on applicant=applicant_member (the validated applicant), not on request.user.

    F14 — ActionChoice.VIEW_UPGRADE_REQ / EDIT_UPGRADE_REQ /¶

    DELETE_UPGRADE_REQ / CREATE_COMMENT_UPGRADE_REQ not listed in CLAUDE.md §8 - Severity: low - Confidence: high - Category: perms - Evidence: CLAUDE.md §8 enumerates CREATE_UPGRADE_REQ_FOR_SELF, CREATE_UPGRADE_REQ_FOR_OTHERS, APPROVE_UPGRADE_REQ, VOTE_UPGRADE_REQ only. The code references VIEW_UPGRADE_REQ, EDIT_UPGRADE_REQ, DELETE_UPGRADE_REQ, CREATE_COMMENT_UPGRADE_REQ, DELETE_COMMENT_UPGRADE_REQ in permissions.py. - Recommendation: Trigger the CLAUDE.md self-update protocol to document these actions (this is a documentation gap, not a bug).

    F15 — Status transition accepts NEW→APPROVED without intermediate votes¶

    • Severity: low
    • Confidence: medium
    • Category: other
    • File: api/views/views_upgraderequest.py:113
    • Evidence: handle_upgrade_request_verdict accepts any status in (APPROVED, DECLINED) regardless of the current status. An already APPROVED request can be re-approved (re-firing the notification, re-adding group, resetting verdict_date). A DECLINED request can be flipped to APPROVED without trace, and an APPROVED member's group membership won't be rolled back if it's changed to DECLINED.
    • Recommendation: Guard the transition: only allow status in (NEW, IN_PROGRESS) before applying a verdict. Record the transition in an audit table or log.

    F16 — .order_by('id') on UpgradeRequestApproveView queryset is misleading¶

    • Severity: nit
    • Confidence: high
    • Category: style
    • File: api/views/views_upgraderequest.py:131, 147, 225
    • Evidence: generics.CreateAPIView does not paginate, and get_object fetches by pk; .order_by('id') adds an unused ORDER BY to SELECT ... WHERE id=... queries.
    • Recommendation: Drop .order_by('id').

    F17 — UpgradeRequestCommentViewSet.get_queryset() uses unqualified select_related()¶

    • Severity: nit
    • Confidence: high
    • Category: n+1
    • File: api/views/views_upgraderequest.py:169
    • Evidence: .select_related() with no arguments follows all non-null FKs — future-proof, but opaque. It also does not include the upgrade_request.applicant chain used by get_queryset() filter at line 197 (that filter hits the DB anyway), nor does the list path annotate anything.
    • Recommendation: Make joins explicit: .select_related('author', 'upgrade_request__applicant').

    F18 — Empty-M2M semantics conflict: "no voters" unclear in verdict math¶

    • Severity: low
    • Confidence: medium
    • Category: other
    • Evidence: There is no quorum / threshold check anywhere. Approval and decline are pure admin actions; voter counts are displayed but not enforced. If product intent is "approver can verdict any time", this is fine — but worth calling out given the VOTE_UPGRADE_REQ ceremony and per-request voter counts.
    • Recommendation: Confirm with product: is voting advisory or mandatory? If mandatory, add a quorum guard in handle_upgrade_request_verdict.

    F19 — applicant_str is set in save() but not preserved if applicant is deleted then re-linked¶

    • Severity: nit
    • Confidence: medium
    • Category: other
    • File: api/models/models_upgraderequest.py:46-47
    • Evidence: The backup is populated correctly on every save, but applicant = models.ForeignKey(..., on_delete=models.SET_NULL) means that when the applicant is deleted, the FK becomes null and applicant_str retains the old username — good. However, the model never calls save() after the FK is SET_NULL'd by cascade, so applicant_str is in fact preserved by virtue of not being touched, not by defensive code. This is the correct outcome, but fragile: any future migration or data fix that calls .save() on applicant-less rows would need to guard if self.applicant: (which it already does). Confirmed correct.
    • Recommendation: None — noted for documentation.

    F20 — send_upgrade_request_handled_notification called outside transaction¶

    • Severity: low
    • Confidence: high
    • Category: tx
    • File: api/views/views_upgraderequest.py:126
    • Evidence: Related to F1. Even if F1 is fixed with transaction.atomic, the Huey enqueue must use transaction.on_commit(lambda: send_upgrade_request_handled_notification(ur)) or the worker can pick up the task before the row is visible. Same applies to the post_save signal for upgrade_request_post_save in signals.py:63-66 which fires send_upgrade_request_created_notification.
    • Recommendation: Wrap Huey enqueues in transaction.on_commit.

    Quick-win recommendations (do these first)¶

    1. Replace datetime.datetime.now() with timezone.now() in models_upgraderequest.py:50 (F6). One-line fix, matches CLAUDE.md §15.
    2. Wrap handle_upgrade_request_verdict and AutoUpgradeService.* in transaction.atomic + select_for_update() on Member and UpgradeRequest (F1, F4, F5). This closes the worst races in one sweep.
    3. Use .save(update_fields=[...]) everywhere on Member and UpgradeRequest in these paths (F11).
    4. Add .select_related('lead', 'level') on the recent-trips queryset and prefetch skill entries (F7, F8).
    5. Guard status transitions: only NEW/IN_PROGRESS can be verdicted (F15).
