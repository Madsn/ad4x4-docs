    Code Review — Misc Services¶

    Scope: api/services/gallery_webhook.py, api/services/global_settings.py, api/services/here_maps_service.py, api/services/permission_service.py. Read-only audit.

    Findings¶

    1. Local settings variable shadows django.conf.settings¶

    • Severity: high
    • File:line: api/services/gallery_webhook.py:51, :119, :195, :249 (every method body)
    • Confidence: high
    • Category: style
    • Evidence: Module imports from django.conf import settings at line 9, then each method rebinds the name: settings = get_global_settings(). A future maintainer adding settings.DEBUG or settings.GALLERY_API_TOKEN inside these methods will silently read the ConfigurableSettings row and either raise AttributeError or — worse — read an unrelated attribute. This is exactly the class of bug that causes production incidents.
    • Recommendation: rename the local to config (or conf) everywhere in the file; keep the imported django.conf.settings name untouched.

    2. raise Exception(response) wraps a requests.Response object as an exception¶

    • Severity: high
    • File:line: api/services/gallery_webhook.py:98, :166, :228, :282
    • Confidence: high
    • Category: retry
    • Evidence: Non-200 responses raise Exception(response). This has two problems: (a) Exception is too broad and forces callers/Huey to treat every failure as a transient retry — a 400/404 from the gallery API will be retried 6 times over 6 hours before giving up (§10 lists 6 retries, 1-hour delay for create_gallery_for_trip_task, etc.); (b) the raised object is a Response, not an Exception subclass, but Python accepts arbitrary objects in Exception(...) — when Huey tries to repr/pickle this for the retry queue the response body and Authorization header (see finding 3) may be serialised into task metadata.
    • Recommendation: define a custom GalleryAPIError(Exception) that stores status_code and a sanitised message. Classify: 4xx (except 408/429) → permanent, don't retry; 5xx, 408, 429, Timeout, ConnectionError → transient, retry. Use response.raise_for_status() or an explicit status check, never raise Exception(response).

    3. Potential secret leak in error logs¶

    • Severity: high
    • File:line: api/services/gallery_webhook.py:96, :164, :226, :280; api/services/here_maps_service.py:187
    • Confidence: medium
    • Category: secret-leak
    • Evidence: Gallery error paths log response.text verbatim. If the Gallery API ever echoes back the Authorization: Bearer <GALLERY_API_TOKEN> header in an error payload (many frameworks do in 401/403/500 responses), the bearer token lands in ad4x4-web logs. Similarly, here_maps_service.py:187 returns f'HERE Maps API error: {str(e)}' as part of the API response body; requests.RequestException messages from requests can contain the full URL including apiKey query param if the exception is raised from inside a redirect or SSL handshake.
    • Recommendation: log response.status_code and a truncated body (first 200 chars) with any Bearer / apiKey= tokens scrubbed via a helper. Never include the raw exception string in a client-facing response; log internally, return a generic message.

    4. HERE Maps API key passed as query-string parameter is logged by upstream proxies¶

    • Severity: medium
    • File:line: api/services/here_maps_service.py:131-138
    • Confidence: high
    • Category: secret-leak
    • Evidence: apiKey is sent as a GET query parameter. This is how HERE Maps authenticates, so not a code bug per se, but nginx access logs, Sentry breadcrumbs, and any intermediate proxy will record the full URL with the key. If request.Request is logged in Sentry via the default requests integration, the key ends up in error reports.
    • Recommendation: confirm SENTRY_DSN integration is configured with send_default_pii=False (it is by default) and that the requests integration is not adding the URL with secrets to breadcrumbs. Consider placing the key in a custom header Authorization: apiKey <key> if HERE supports it; at minimum, document this in §15 gotchas.

    5. Cache key precision / collision risk in HERE Maps¶

    • Severity: medium
    • File:line: api/services/here_maps_service.py:78-82
    • Confidence: high
    • Category: cache
    • Evidence: Cache key built as f'geocode_{lat_rounded}_{lon_rounded}'. Values like lat=1.2, lon=34.56789 and lat=1.23456, lon=789 produce different keys here, but floats without leading zeros and with variable precision can collide under edge cases (e.g. -0.0 vs 0.0, trailing zero stripping). Round-tripping float(latitude) accepts strings that GeocodingCache.objects.get(...) may not accept with the same Decimal precision if the DB column is DecimalField. A mismatched round between memory cache write and DB lookup means the DB row is never hit and the API is called every time for certain coords.
    • Recommendation: normalise to a fixed-width string with explicit sign, e.g. f'geocode_{lat_rounded:+.6f}_{lon_rounded:+.6f}', and use the same normalised value when constructing the GeocodingCache query. Verify GeocodingCache.latitude/longitude column type and match its precision.

    6. Inconsistent cache TTL units between memory and DB cache¶

    • Severity: medium
    • File:line: api/services/here_maps_service.py:115 vs :169
    • Confidence: high
    • Category: cache
    • Evidence: Two different TTLs for the same cache key:
    • Line 115 (DB-cache hit path): cache.set(cache_key, result, config.here_maps_cache_duration * 60) — treating here_maps_cache_duration as minutes.
    • Line 169 (API fetch path): cache.set(cache_key, result, config.here_maps_cache_duration * 86400) — treating it as days.
    • Line 150-152: timedelta(days=config.here_maps_cache_duration) — also treats it as days for DB expiry.

    The field's verbose_name in ConfigurableSettings (models_util.py:82) says "HERE Maps Cache duration in minutes" (default 1440). So the DB-cache-hit path is correct (*60 = minutes to seconds), and both the API-fetch path and expires_at are wrong: 1440 days is 4 years of memory caching and DB expiry, not 1 day. - Recommendation: decide on a unit (minutes is stated), then apply consistently: cache.set(..., config.here_maps_cache_duration * 60) in both paths, and timedelta(minutes=config.here_maps_cache_duration) for the DB expires_at. This is a real behavioural bug in production once HERE Maps is enabled.

    7. get_global_settings creates a singleton during a GET-style call¶

    • Severity: medium
    • File:line: api/services/global_settings.py:17-23
    • Confidence: high
    • Category: null-ref
    • Evidence: When the cache misses and the DB row is missing, get_global_settings writes a new ConfigurableSettings with whatever Group.objects.first() and the lowest-numeric Level happen to be. This is nominally what §15 warns about ("service handles this") but:
    • Group.objects.first() and Level.objects.order_by('numeric_level').first() can themselves be None on a truly empty DB. ConfigurableSettings.default_user_group and default_user_level fields are FKs; the model allows them to be null? Verify. If they're non-null, creation crashes mid-request with IntegrityError.
    • Any read-only request (e.g. GET /api/auth/profile/ during middleware) will spontaneously write to the DB on a cold cache, producing surprising behaviour and write load during read traffic surges after a Redis flush.
    • The settings.save() on line 22 is redundant — objects.create already saved the row.
    • Recommendation: fail loud when the singleton row is absent in production (raise ImproperlyConfigured); provide a management command seed_global_settings or a data migration. If keeping the auto-create path, wrap in transaction.atomic() and handle IntegrityError/None FKs gracefully.

    8. cache.get('global_settings') falsy check is wrong for cached model instance¶

    • Severity: low
    • File:line: api/services/global_settings.py:16
    • Confidence: high
    • Category: cache
    • Evidence: if not settings: — for a Django model instance this evaluates __bool__ which is True for any model; a cached None (Django's cache backend will store None if explicitly set) would retrigger the fetch. This happens to work but is subtly wrong.
    • Recommendation: use a sentinel. settings = cache.get('global_settings', SENTINEL); if settings is SENTINEL: .... Minor but idiomatic.

    9. Caching a live model instance across requests¶

    • Severity: medium
    • File:line: api/services/global_settings.py:23
    • Confidence: high
    • Category: cache
    • Evidence: A pickled ConfigurableSettings instance goes into Redis for 5 minutes. Stale instances may retain stale relations (default_user_group), and the invalidation signal at line 28 is registered on post_save. That misses: direct UPDATE SQL, admin bulk actions that bypass save(), signals disconnected during tests, and cache eviction unreliability. Worse, the cached instance carries old M2M/FK caches, so settings.default_user_level.name may point at stale data. In production with USE_TZ=False, staleness bugs tend to manifest as "why did that email just get sent from the old address".
    • Recommendation: cache a plain dict of the handful of fields the callers actually use, not the full model. Or cache by field with cache.get_or_set per field. Alternatively, accept the staleness and document it in §15.

    10. requests.get/requests.post timeout defaults from DB — no fallback¶

    • Severity: low
    • File:line: api/services/here_maps_service.py:137; api/services/gallery_webhook.py:78, :146, :216, :270
    • Confidence: high
    • Category: timeout
    • Evidence: Timeouts come from config.here_maps_request_timeout / settings.gallery_api_timeout. If an admin accidentally sets 0 in Django admin, requests interprets timeout=0 as "no timeout" on some platforms, hanging Gunicorn worker indefinitely and blocking Huey tasks for the full retry window (1 hour × 6 = 6 hours per stuck trip). No lower bound validation on the model field.
    • Recommendation: add validators=[MinValueValidator(1), MaxValueValidator(120)] on the IntegerField definitions, and clamp at read time: timeout = max(1, min(120, config.gallery_api_timeout)). Also set a hard ceiling in code regardless of config.

    11. Gallery webhook: no idempotency, retries may create duplicate galleries¶

    • Severity: high
    • File:line: api/services/gallery_webhook.py:33-108
    • Confidence: medium
    • Category: idempotency
    • Evidence: create_gallery_for_trip is called from a Huey task that retries 6 times. The payload contains trip_id, but if the request succeeds remotely and the response times out or is lost on the way back, the retry creates a second gallery. The caller stores the returned gallery_id on the Trip; if the first-call response was lost, the second call's id overwrites the first, leaving an orphan gallery on the remote. Nothing in the payload is an idempotency key.
    • Recommendation: add an idempotency_key (UUID deterministic from trip_id + created_at) to every webhook payload; have the Gallery API return the existing gallery when the key matches. Alternatively, have the Gallery API treat trip_id as a unique constraint and return the existing record on duplicate POST.

    12. update_gallery_for_trip runs even when trip.gallery_id is missing¶

    • Severity: medium
    • File:line: api/services/gallery_webhook.py:111-176
    • Confidence: high
    • Category: idempotency
    • Evidence: delete_gallery_for_trip early-returns when trip.gallery_id is falsy (line 200). update_gallery_for_trip has no such guard: if a trip never had a gallery created (e.g. auto_create_trip_gallery=False), every edit still POSTs to /trip/updated. Either the remote errors (wastes 6 retries) or silently no-ops (creates an orphan expectation).
    • Recommendation: mirror the delete guard — early return when not trip.gallery_id.

    13. Error log message says "creating gallery" in the update / delete / restore paths¶

    • Severity: low
    • File:line: api/services/gallery_webhook.py:163, :169, :172, :175 (update_gallery_for_trip)
    • Confidence: high
    • Category: style
    • Evidence: Copy-paste from create_gallery_for_trip: every error log in update_gallery_for_trip says "creating gallery" — "Failed to create gallery for trip …" on an update path, "Gallery API timeout when creating gallery" on update timeout, "Network error creating gallery" on update network error. Hard to debug production incidents when the operation is mislabelled.
    • Recommendation: replace "creating" with the correct verb per method.

    14. creator_avatar attribute access will crash if profile has no avatar_url¶

    • Severity: low
    • File:line: api/services/gallery_webhook.py:68, :136
    • Confidence: medium
    • Category: null-ref
    • Evidence: trip.lead.profile.avatar_url if trip.lead and hasattr(trip.lead, 'profile') else None. hasattr checks that trip.lead has a profile attribute, but accessing .profile.avatar_url will raise AttributeError if the profile object doesn't have avatar_url, which hasattr didn't guard. Also, Member in this codebase is itself AUTH_USER_MODEL with an avatar field on it — the profile relation is worth re-examining (may be a legacy attribute).
    • Recommendation: getattr(getattr(trip.lead, 'profile', None), 'avatar_url', None). Or just pull from trip.lead.avatar (Member.avatar ImageField exists per §5) and skip the intermediate model.

    15. permission_service.superuser_or_has_permission duplicates permission_matrix_exists_or_user_is_superuser¶

    • Severity: medium
    • File:line: api/services/permission_service.py:5-14 vs api/permissions.py:15-30
    • Confidence: high
    • Category: perms-drift
    • Evidence: Two near-identical functions exist with different signatures:
    • permissions.permission_matrix_exists_or_user_is_superuser(user, action, level=None) — the canonical, widely-used helper (40+ call sites per grep above).
    • services.permission_service.superuser_or_has_permission(level, request_user, action) — same logic, different argument order, used in three spots in views_trip.py.

    The semantic mismatch with PermissionMatrix.has_permission is worse: the model method (api/models/models.py:77) takes (user, action, member=None, trip=None, require_trip_lead=False) and has special-case handling for CREATE_LOGBOOK_ENTRIES_SUPERUSER and member-level resolution. None of the service-layer helpers honour that. §8 of CLAUDE.md says: "PermissionMatrix.has_permission(user, action, member, trip, require_trip_lead) is the single authoritative check". These helpers violate that rule. - Recommendation: delete superuser_or_has_permission; migrate the three views_trip.py call sites to permission_matrix_exists_or_user_is_superuser (already imported elsewhere). Over the medium term, consolidate that function into PermissionMatrix.has_permission so drift is impossible.

    16. check_logbook_entry_permissions returns stale decisions¶

    • Severity: medium
    • File:line: api/services/permission_service.py:17-64
    • Confidence: medium
    • Category: perms-drift
    • Evidence: The function has five code paths and returns (False, False) early on line 52 only after computing can_create_logbook_entry. If the user is editing their own logbook (user == member) and is NOT a superuser, the function returns (False, False) even when the user IS lead/deputy for the trip. It's unclear whether self-editing is forbidden for leads (I'd expect leads to be able to sign their own skills), but the flow suggests yes. The logic is hard to follow and the check at line 51 runs after the expensive DB lookups on lines 42-49, wasting queries when the answer is predetermined.
    • Recommendation: restructure with early returns. Add a docstring with a decision table (user role × self vs other × skills present). Consider a unit test that enumerates the 8 combinations explicitly.

    17. PermissionMatrix queries inside loops (N+1)¶

    • Severity: low
    • File:line: api/services/permission_service.py:7-12, api/services/permission_service.py:43-49
    • Confidence: high
    • Category: other
    • Evidence: superuser_or_has_permission does up to two sequential PermissionMatrix.objects.filter(...).exists() queries per call. check_logbook_entry_permissions calls it multiple times per request (CREATE_LOGBOOK_ENTRIES_SUPERUSER, CREATE_LOGBOOK_ENTRIES, SIGN_LOGBOOK_SKILLS), plus a TripRegistration.objects.get(...) per logbook entry. In bulk logbook-entry endpoints this is 4-5 queries per member. The permission matrix is small and near-static — it should be cached.
    • Recommendation: cache a per-user (or per-group) permission summary in memory/Redis for 60 seconds; invalidate on PermissionMatrix / Group.user_set change via signals.

    18. HERE Maps service returns raw exception strings in API response¶

    • Severity: medium
    • File:line: api/services/here_maps_service.py:185-195
    • Confidence: high
    • Category: secret-leak
    • Evidence: return {'success': False, 'error': f'HERE Maps API error: {str(e)}', ...} and f'Internal error: {str(e)}' return internal exception messages to the API client. requests.RequestException can include the full URL with apiKey=... query string. Also leaks internal stack trace hints. The generic except Exception on line 190 is a catch-all that will mask bugs.
    • Recommendation: log internally with logger.exception(...), return a generic 'Reverse geocoding failed' to the client. Drop the broad except Exception or narrow it to specific anticipated failure modes.

    19. _extract_fields swallows exceptions silently¶

    • Severity: low
    • File:line: api/services/here_maps_service.py:233-235
    • Confidence: high
    • Category: other
    • Evidence: except Exception as e: logger.error(f'Error extracting fields: {e}'); return {}. An empty dict is then written to the DB cache as a valid geocoding result, meaning any malformed HERE Maps response poisons the cache with empties for that lat/lon for here_maps_cache_duration minutes (which, per finding 6, could be 4 years).
    • Recommendation: on parse failure, re-raise so the outer handler treats it as a transient error; do NOT cache the empty result.

    20. Module-level getattr(settings, 'GALLERY_API_TOKEN', '') is evaluated once at import¶

    • Severity: low
    • File:line: api/services/gallery_webhook.py:19
    • Confidence: high
    • Category: style
    • Evidence: Captured at import time. If the token is rotated and settings are reloaded (e.g. via django-constance or env refresh), the service keeps the old value until process restart.
    • Recommendation: read inside _get_headers() via settings.GALLERY_API_TOKEN, and keep from django.conf import settings (note the collision with finding 1 — rename the local settings first).

    Summary¶

    Highest-impact fixes, in priority order: 1. Rename the settings local in gallery_webhook.py (finding 1) — trivial, prevents a whole class of bugs. 2. Fix the HERE Maps cache TTL unit inconsistency (finding 6) — behavioural bug. 3. Replace raise Exception(response) + classify transient vs permanent errors (finding 2) — cuts retry storms. 4. Sanitise error logs and response bodies (findings 3, 4, 18) — secret-leak surface. 5. Unify permission helpers around PermissionMatrix.has_permission (finding 15) — per CLAUDE.md §8 this is a documented architectural rule.

    None of the findings require schema changes beyond minor model validators (finding 10). All are in-service refactors.
