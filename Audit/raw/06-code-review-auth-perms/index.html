    Code Review — Auth + Permissions¶

    Scope: api/views/views_auth.py, api/permissions.py, api/util.py (JWT subclass only). Mode: READ-ONLY audit.

    Findings¶

    F-01 — SessionsView.delete treats empty keep_refresh as "keep nothing"; edge-case token reuse path¶

    • Severity: medium
    • File: api/views/views_auth.py:224-253
    • Confidence: high
    • Category: token-lifecycle
    • Evidence: In SessionsView.delete, when the payload omits keep_refresh or sends "", keep_refresh_raw = '' is falsy so keep_jti stays None and the code blacklists every outstanding token. CLAUDE.md §6 says: "Without keep_refresh it behaves like logout-all." Matches. However, when a valid keep_refresh is supplied, RefreshToken(keep_refresh_raw) is constructed purely for payload inspection — it is not blacklisted. That's correct for this flow, but note: simplejwt's RefreshToken(token) constructor only runs signature+exp checks; it does not verify the refresh is not already blacklisted. A user could therefore pass a blacklisted-but-not-yet-expired refresh token as keep_refresh and the view would accept it and use its JTI as the "keep" target, leaving that (dead) session untouched while killing the rest. The dead session remains dead, so no real privilege escalation — but the kept_jti returned to the client is misleading.
    • Recommendation: after decoding keep_refresh, also verify BlacklistedToken.objects.filter(token__jti=keep_jti).exists() is False before honoring it. If blacklisted, fall through to the "blacklist all" path so the response accurately reflects reality.

    F-02 — SessionsView.delete calls serializer.is_valid() twice¶

    • Severity: low
    • File: api/views/views_auth.py:225-226
    • Confidence: high
    • Category: style
    • Evidence: serializer.is_valid(raise_exception=False) keep_refresh_raw = serializer.validated_data.get('keep_refresh', '') if serializer.is_valid() else '' is_valid() is called twice (the second call re-runs validation). Harmless today (serializer has only one optional field), but the pattern is fragile.
    • Recommendation: capture is_valid() once: ok = serializer.is_valid(raise_exception=False); keep_refresh_raw = serializer.validated_data.get('keep_refresh', '') if ok else ''.

    F-03 — LoginView returns distinct error strings for "bad credentials" vs "disabled account"¶

    • Severity: medium
    • File: api/views/views_auth.py:122-126
    • Confidence: high
    • Category: info-leak
    • Evidence: The view returns invalid_credentials when _resolve_login_user fails and account_disabled when the user exists but is inactive. An attacker can therefore distinguish "this username/email exists but is deactivated" from "this username/email does not exist or password is wrong." This is a mild account-enumeration vector, especially relevant here because anonymize_data() deactivates accounts on GDPR deletion — it would leak that a specific email was previously a member.
    • Recommendation: return invalid_credentials for both cases. If the backend still needs to log the distinction, log it server-side; do not expose it over the wire.

    F-04 — _resolve_login_user swallows MultipleObjectsReturned silently¶

    • Severity: low
    • File: api/views/views_auth.py:63-66
    • Confidence: high
    • Category: other
    • Evidence: email__iexact can legitimately match multiple rows if two members have emails differing only by case (e.g. alice@x.com, Alice@x.com). The Member.email field is declared unique=True at case-sensitive DB level, so this can happen if historical data pre-dates case-insensitive handling. Today the login silently fails with invalid_credentials, which is a genuinely confusing user-support scenario.
    • Recommendation: either (a) add a case-insensitive DB constraint / UniqueConstraint(Lower('email')) on Member.email and enforce it during registration, or (b) at minimum log a warning when MultipleObjectsReturned fires so support can intervene.

    F-05 — SQL injection check: all lookups are safe¶

    • Severity: low (no issue — positive finding)
    • File: api/views/views_auth.py:64, api/util.py:60-64
    • Confidence: high
    • Category: sql-injection
    • Evidence: User.objects.get(email__iexact=login_value) and get_user_by_lookup_dict({db_fn: value}, ...) both parameterize via the Django ORM. db_fn values come from a whitelist ('username__iexact', 'email__iexact') set in code, not from user input. No raw SQL, no .extra(), no .raw(). Safe.
    • Recommendation: none — keep it this way. Do not refactor these paths to dynamic filter(**{...}) where the key is attacker-controlled.

    F-06 — Member.token_version field still present (documented as legacy)¶

    • Severity: nit
    • File: api/models/models_member.py:82
    • Confidence: high
    • Category: token-lifecycle
    • Evidence: token_version field survives on the model. Grep confirms nothing in views_auth.py, permissions.py, or util.py reads or writes it — so the files under audit are clean on this point. Only migration files and the model definition reference it. CLAUDE.md §7 / §15 mark it as legacy/unused and scheduled for removal.
    • Recommendation: out-of-scope for this audit; flagged for a follow-up cleanup PR (drop field + migration).

    F-07 — JWTAuthentication.get_user creates NotificationSettings on every authenticated request¶

    • Severity: medium
    • File: api/util.py:31-36
    • Confidence: high
    • Category: other (performance)
    • Evidence: obj, _created = NotificationSettings.objects.get_or_create(member=user) obj.save() Every single authenticated request performs a SELECT … OR INSERT … and then an unconditional UPDATE. The comment says "update the last_user_activity field … by triggering a save" — but save() with no changed fields still writes every column. At throttle ceiling (200 req/min per user) this is 200 unnecessary UPDATEs per user per minute. Also: LastVisitedMiddleware already updates Member.last_visited at 1/hr (per §4). The two mechanisms overlap.
    • Recommendation: (a) only call obj.save(update_fields=['last_user_activity']) to reduce write amplification, and (b) throttle the same way LastVisitedMiddleware does (skip if updated within the last hour). Ideally consolidate both into LastVisitedMiddleware and drop this side-effect from get_user.

    F-08 — HasCreateUpgradeRequestForOtherPermission can raise on unknown level¶

    • Severity: high
    • File: api/permissions.py:245-251
    • Confidence: high
    • Category: perms
    • Evidence: level_id = request.data.get('target_level') if level_id == None: return False level = Level.objects.get(id=level_id) # <-- DoesNotExist is NOT caught A client posting {"target_level": 99999} (or any invalid level id) will crash the permission check with Level.DoesNotExist → DRF converts it into a 500 Internal Server Error (not 403/400). Compare with HasCreateUpgradeRequestForSelfPermission which does catch DoesNotExist (line 241). Inconsistent.
    • Recommendation: wrap in try/except Level.DoesNotExist: return False to mirror the sibling class. Also replace == None with is None while here.

    F-09 — HasViewUpgradeRequestCommentPermission and HasCreateUpgradeRequestCommentPermission raise on missing upgrade request¶

    • Severity: high
    • File: api/permissions.py:261-275
    • Confidence: high
    • Category: perms
    • Evidence: Line 264 does UpgradeRequest.objects.get(pk=upgrade_request_id) with no exception handling — if the pk is missing/invalid it bubbles UpgradeRequest.DoesNotExist → 500. Line 272 uses .filter(...).first() so that variant is safe, but both are defensive about the applicant check only for the found case.
    • Recommendation: change line 264 to .filter(pk=upgrade_request_id).first() plus a None guard, consistent with the adjacent class.

    F-10 — HasDeleteUpgradeRequestCommentPermission uses .get(...) or None¶

    • Severity: nit
    • File: api/permissions.py:281
    • Confidence: high
    • Category: style
    • Evidence: upgrade_request_comment = UpgradeRequestComment.objects.get(pk=comment_id) or None — .get() never returns None; it returns the row or raises DoesNotExist. The or None is dead code.
    • Recommendation: remove the or None; the existing try/except DoesNotExist already handles the missing case correctly.

    F-11 — CanEditOrDeleteTripBasePermission has duplicated block¶

    • Severity: low
    • File: api/permissions.py:170-176
    • Confidence: high
    • Category: style
    • Evidence: ``` settings = getglobalsettings() cutoffminutes = settings.tripeditdeletecutoffminutes cutofftime = trip.starttime - timedelta(minutes=cutoffminutes)

    settings = getglobalsettings() cutoffminutes = settings.tripeditdeletecutoffminutes cutofftime = trip.starttime - timedelta(minutes=cutoffminutes) ``` Three lines are literally duplicated. Functionally harmless, but each call triggers a DB hit for the singleton. At permission-check frequency (every trip edit attempt) this doubles ORM load for the settings row. - Recommendation: delete the duplicate three lines.

    F-12 — permission_matrix_exists_or_user_is_superuser — empty-levels semantics correct¶

    • Severity: low (positive finding)
    • File: api/permissions.py:15-30
    • Confidence: high
    • Category: perms
    • Evidence: The function first queries with levels__isnull=True. This is the raw M2M isnull filter — when a PermissionMatrix row has no related Level rows in the M2M, isnull=True on the related table returns True. Semantically: "no level restrictions → applies to every level." This matches CLAUDE.md §15: "An empty levels M2M in PermissionMatrix means the permission applies to members of any level." Correct. Caveat: if the row has any level attached, it is still matched by the second query only when level is passed in. If a caller forgets to pass level, a "restricted-to-specific-levels" permission is silently ignored. The current codebase generally does pass a level where appropriate, but the asymmetry is worth a docstring.
    • Recommendation: add a docstring note: "If level=None and the matrix row restricts to specific levels, the row is treated as non-matching. Pass the relevant level whenever the action is level-scoped."

    F-13 — HasViewUpgradeRequestPermissionOrIsForSelf compares pk (int) with URL kwarg (str)¶

    • Severity: medium
    • File: api/permissions.py:331-336
    • Confidence: high
    • Category: perms
    • Evidence: if request.user.pk == view.kwargs.get('pk'): return True view.kwargs['pk'] is a string (URL path segment), request.user.pk is an int. 1 == "1" is False in Python. The "is for self" shortcut therefore never fires, and users are forced down the matrix-permission branch. In practice users who should have the "self" shortcut succeed only because they also have the matrix permission — but users who lack both get a silent denial where the self-path was supposed to let them through.
    • Recommendation: coerce: str(request.user.pk) == view.kwargs.get('pk') or int(view.kwargs['pk']) == request.user.pk with a try/except ValueError.

    F-14 — is_staff / is_superuser in business logic¶

    • Severity: medium
    • File: api/permissions.py (multiple) + api/views/views_auth.py (none)
    • Confidence: high
    • Category: perms
    • Evidence: CLAUDE.md §8 explicitly says "Do not use Django model-level permissions (is_staff, is_superuser) for business logic." Grep shows no is_staff usage in these files (good). But is_superuser is used as a bypass in many places: permission_matrix_exists_or_user_is_superuser, check_upgrade_request_permission_against_perm_matrix, check_trip_permission_against_perm_matrix*, IsTripLeadOrDeputy, IsFeedbackOwnerOrSuperuser, IsOwnerOrReadOnly, IsCreatorOrReadOnly, IsAdminUserOrReadOnly, IsSameUserAllowEditOrReadOnly, IsEditingOwnProfileOrAdmin, CanEditOrDeleteTripBasePermission, HasViewTripsAsLeadPermission. CLAUDE.md §8 primarily warns against using them instead of matrix checks. A superuser-as-break-glass bypass is an accepted pattern, but it is very widely sprinkled here. Specifically in HasEditMembershipPaymentsPermission (line 302-303) there is no is_superuser short-circuit — inconsistent with neighbours.
    • Recommendation: (a) document explicitly that "superuser bypass" is a project convention and accepted, (b) pick one place to check it — the helper permission_matrix_exists_or_user_is_superuser already does — and remove the redundant checks from the callers that pre-check before calling it, (c) audit every new permission class for the same bypass during review.

    F-15 — LogoutAllView has no refresh-token input but blacklists all; acceptable but asymmetric¶

    • Severity: nit
    • File: api/views/views_auth.py:164-179
    • Confidence: high
    • Category: token-lifecycle
    • Evidence: LogoutAllView relies solely on the access token (from IsAuthenticated) to identify the user, then blacklists all outstanding refresh tokens for that user. That's correct and matches §7. Note that the current session's access token is not invalidated — simplejwt has no access-token blacklist by default. An attacker holding a stolen access token can continue to use it until its exp (up to 24h per ACCESS_TOKEN_MINUTES=1440). Same is true of LogoutView and CustomChangePasswordView.
    • Recommendation: this is a known simplejwt limitation and the 24h lifetime is the mitigation. Consider shortening ACCESS_TOKEN_MINUTES to e.g. 15-60 if not already under consideration; 24h is generous for a platform with membership/trip data. Out-of-scope for code-level changes — flagging for architecture review.

    F-16 — _blacklist_all_user_tokens issues N+1 queries¶

    • Severity: low
    • File: api/views/views_auth.py:27-42
    • Confidence: high
    • Category: other (performance)
    • Evidence: The loop runs BlacklistedToken.objects.filter(token=ot).exists() once per outstanding token, then BlacklistedToken.objects.create(token=ot). For a user with many historical sessions this is O(n) queries. Same pattern in SessionsView.delete (line 243-247).
    • Recommendation: batch via already_blacklisted = set(BlacklistedToken.objects.filter(token__in=outstanding).values_list('token_id', flat=True)) then BlacklistedToken.objects.bulk_create([BlacklistedToken(token=ot) for ot in outstanding if ot.id not in already_blacklisted]). One read + one write instead of 2n.

    F-17 — Case-insensitive login: authenticate(username=…) path¶

    • Severity: low (positive finding)
    • File: api/views/views_auth.py:57
    • Confidence: high
    • Category: sql-injection
    • Evidence: authenticate(username=login_value, …) delegates to MyUserManager.get_by_natural_key (per CLAUDE.md §7), which Django uses with ORM filters — no raw SQL. The email fallback uses email__iexact, which PostgreSQL translates to UPPER(email) = UPPER(%s) via a parameterized query. Safe from SQL injection.
    • Recommendation: none.

    F-18 — UnifiedTokenObtainPairView drops simplejwt's structured error body¶

    • Severity: low
    • File: api/views/views_auth.py:269-273
    • Confidence: high
    • Category: info-leak (minor)
    • Evidence: On failure, super().post() returns a DRF response with response.data being a dict like {"detail": "No active account found with the given credentials", "code": "authorization_failed"}. The wrapper re-emits that under message, so clients see a human-readable English string mentioning "active account" — which, like F-03, leaks whether an account is disabled vs missing.
    • Recommendation: consider normalizing the error message to a neutral invalid_credentials string, matching LoginView. If preserved for client compatibility, document it in §7.

    Summary¶

    Severity Count
    critical 0
    high 2 (F-08, F-09)
    medium 5 (F-01, F-03, F-07, F-13, F-14)
    low 6
    nit 3

    Hotspots worth addressing first: 1. F-08 / F-09 — unhandled DoesNotExist in permission classes can cause 500s from attacker-controlled input. Quick fix, real impact. 2. F-13 — self-shortcut never fires due to str/int mismatch; a latent bug masking real authorization outcomes. 3. F-03 / F-18 — small account-enumeration leaks worth tightening. 4. F-07 — unnecessary DB writes on every authenticated request.

    Token-lifecycle invariants from CLAUDE.md §7 hold: logout single-session, logout-all, session-list + selective revocation, password-change cascading blacklist, and refresh-token rotation are all implemented correctly. token_version is not referenced by any of the three audited files. No SQL-injection vectors found. PermissionMatrix.has_permission()'s empty-levels semantics match the §15 gotcha.
