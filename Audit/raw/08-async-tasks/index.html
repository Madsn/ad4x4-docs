    Findings¶

    [CRITICAL] TypeError at runtime — remove_from_registered / remove_from_waitlist pass the wrong arguments¶

    • File: api/services/trip_registration_service.py:49, 58
    • Task: send_removed_from_trip_registered_notification, send_removed_from_trip_waitlist_notification
    • Confidence: high
    • Category: args
    • Evidence: python # trip_registration_service.py send_removed_from_trip_registered_notification(user, trip) # 2 positional args send_removed_from_trip_waitlist_notification(user, trip) # 2 positional args But the task signatures in api/background.py:32, 37 declare a single cancellation: TripRegistrationCancellationReason argument, and the downstream NotificationManager.send_removed_from_trip_registered(cancellation) (notification_service.py:136) reads cancellation.member, cancellation.trip, cancellation.id. An identical 2-arg call also exists in api/views/views_trip.py:436, 439 (CancelTripRegistration).
    • Recommendation: Either (a) update callers to build a TripRegistrationCancellationReason and pass it (views/views_trip.py:399-414 already demonstrates the correct pattern), or (b) refactor the task to accept (member_id, trip_id, reason_id_or_none) and resolve DB-side. Option (a) is least invasive; option (b) is more correct for Celery/Huey best practice. In either case, add a test that actually executes the task — it will fail fast.

    [HIGH] Model instances passed to every task instead of IDs¶

    • File: api/background.py:18, 22, 27, 32, 37, 42, 47, 81, 86, 163
    • Task: all notification tasks except the four *_gallery_for_trip_task tasks
    • Confidence: high
    • Category: args
    • Evidence: Signatures like def send_trip_notification(trip: Trip), def send_club_news(data: ClubNews), def send_feedback_notification(data: Feedback) receive Django model instances, which Huey pickles into Redis. Pickled instances are (1) fragile across schema changes, (2) can reference stale data by the time the worker runs, and (3) break send_club_news when the view at views_pushnotification.py:29 calls send_club_news(serializer.validated_data) — that passes a dict, not a ClubNews, yet the task ultimately calls data.status = ClubNewsStatus.SENT; data.save() (notification_service.py:133-134). Second runtime bug.
    • Recommendation: Switch every notification task to accept a primary key (e.g. send_trip_notification(trip_id: int)) and do Trip.objects.get(pk=trip_id) at the top. Apply the gallery-task pattern uniformly. Fix ClubNewsNotificationAPIView to create/save the ClubNews row first, then enqueue send_club_news(news.id).

    [HIGH] No transaction.on_commit wrapper at any enqueue site¶

    • File: api/signals.py (post_save receivers), api/views/views_trip.py, api/views/views_upgraderequest.py:126, api/views/views_feedback.py:34, api/services/trip_registration_service.py
    • Task: every async task
    • Confidence: high
    • Category: on-commit
    • Evidence: Grepping the whole worktree for on_commit returns zero matches. Yet tasks are enqueued from inside post_save signals (signals.py:66, 92, 161, 178, 184, 189, 195) and from DRF views wrapped by ATOMIC_REQUESTS/serializer saves. If the surrounding transaction rolls back (e.g. an error after perform_create but before response), the worker still picks up the job and either (a) .get() raises DoesNotExist because the row was never committed, or (b) reads partially-committed state. create_gallery_for_trip_task is especially exposed — it calls GalleryWebhookService which hits an external API, so a rollback means the remote gallery still gets created.
    • Recommendation: Wrap every enqueue that depends on committed DB state: python from django.db import transaction transaction.on_commit(lambda: create_gallery_for_trip_task(trip.id)) Highest priority: the signal handlers in signals.py and views_feedback.py:34 (serializer.save() returns before commit finishes when inside ATOMIC_REQUESTS). The NotificationLog.objects.bulk_create side of things is fine because it runs inside the worker, but any fresh read of Trip/UpgradeRequest/ClubNews must be on-commit.

    [HIGH] Gallery tasks swallow Trip.DoesNotExist — no retry on genuine race¶

    • File: api/background.py:107-110, 122-126, 138-142, 154-158
    • Task: create_gallery_for_trip_task, update_gallery_for_trip_task, delete_gallery_for_trip_task, restore_gallery_for_trip_task
    • Confidence: high
    • Category: error-path
    • Evidence: python except Trip.DoesNotExist: logger.error(f"Trip {trip_id} not found when creating gallery") except Exception as e: logger.error(...) # no re-raise in create_gallery_for_trip_task create_gallery_for_trip_task logs-and-returns for both error paths, so Huey never retries even when the write hasn't committed yet (Trip.DoesNotExist is exactly the symptom of missing on_commit). The three other gallery tasks do raise Exception(...) but that wraps and loses the original traceback, and still log-only on DoesNotExist. A "trip not yet committed" race therefore never recovers — you get a permanent log entry, no gallery.
    • Recommendation: Re-raise in create_gallery_for_trip_task so retries kick in. For DoesNotExist, raise a RetryException on the first few attempts and only swallow after a retry budget. Stop wrapping exceptions in raise Exception(str(e)) — that strips the traceback; just raise bare to propagate.

    [MEDIUM] Idempotency gap — gallery creation can double up¶

    • File: api/background.py:96-103
    • Task: create_gallery_for_trip_task
    • Confidence: medium
    • Category: idempotency
    • Evidence: The task always calls GalleryWebhookService.create_gallery_for_trip(trip). There is no guard such as if trip.gallery_id: return at the top. If the remote call succeeds but the local trip.save(update_fields=['gallery_id']) fails (e.g. DB hiccup), the next retry creates a second gallery on the remote side.
    • Recommendation: python trip = Trip.objects.get(id=trip_id) if trip.gallery_id: logger.info(f"Trip {trip_id} already has gallery_id={trip.gallery_id}, skipping") return Apply the mirror guard in delete_gallery_for_trip_task (skip if gallery_id is already None) and in restore_gallery_for_trip_task.

    [MEDIUM] Idempotency gap — club_news marked SENT by side-effect inside a retryable task¶

    • File: api/services/notification_service.py:133-134, called from api/background.py:81 via send_club_wide_news
    • Task: send_club_news
    • Confidence: medium
    • Category: idempotency
    • Evidence: send_club_wide_news iterates channels (email + FCM + Telegram), then unconditionally does data.status = ClubNewsStatus.SENT; data.save(). If any channel raises after a partial fan-out (say, 500 of 1000 members got the email and then FCM 5xx'd), Huey retries — but on the next run every channel re-sends to everyone. Combined with ClubNews.save() being immutable once SENT (CLAUDE.md §15), a retry after the status flipped will actually raise a ValidationError from the save side, permanently blocking the retry.
    • Recommendation: Record per-channel success in a set (e.g. on a ClubNewsDelivery row or on NotificationLog) and skip already-delivered channels on retry. Flip the status to SENT only after all channels report success.

    [MEDIUM] process_account_deletion_requests is not idempotent and not transactional¶

    • File: api/background.py:167-174
    • Task: process_account_deletion_requests
    • Confidence: medium
    • Category: idempotency + error-path
    • Evidence: python for request in requests: request.member.anonymize_data() request.delete() If anonymize_data() raises mid-loop (one member out of many), the loop aborts, the request row is not deleted, and the next-day run re-anonymizes everyone already processed. anonymize_data() deactivates + wipes PII, which on a re-run is a no-op-ish, but Vehicle deletions would already be gone and the loop will still blow up on the same failing member forever.
    • Recommendation: Per-request try/except with logger.exception, so one bad row doesn't block the rest. Wrap anonymize_data() + request.delete() in an atomic() block so partial anonymization doesn't leave a half-deleted member.

    [MEDIUM] periodic_purge_old_notifications uses .count() then .delete() — two roundtrips, races¶

    • File: api/background.py:59-64
    • Task: periodic_purge_old_notifications
    • Confidence: low
    • Category: other
    • Evidence: The .count() log line runs a separate query from .delete(), and at 04:00 the window is wide enough that a new row can slip in between them. Not a correctness bug (the .delete() re-evaluates the filter) but the logged count is misleading.
    • Recommendation: Use the tuple returned by .delete(): deleted, _ = qs.delete(); logger.info(f'Deleted {deleted} ...'). The cleanup-token tasks at 184-190 and 194-202 already do this correctly — apply the same pattern.

    [LOW] Two token-cleanup tasks scheduled 15 min apart — race with long tx¶

    • File: api/background.py:183-203
    • Task: cleanup_blacklisted_tokens, cleanup_expired_outstanding_tokens
    • Confidence: low
    • Category: tz
    • Evidence: Blacklist (04:30) must complete before outstanding (04:45), otherwise the FK cascade from OutstandingToken.delete() will wipe blacklist rows the first task hadn't touched yet. In practice 15 minutes is generous, but there's no ordering guarantee encoded in code — it's crontab-order only.
    • Recommendation: Make cleanup_expired_outstanding_tokens chain off the end of cleanup_blacklisted_tokens instead of relying on crontab timing. Or merge them into one task since the second subsumes the first (cascade removes blacklist rows anyway).

    [LOW] create_gallery_for_trip_task calls trip.save(), re-triggering trip_post_save signal¶

    • File: api/background.py:101-103
    • Task: create_gallery_for_trip_task
    • Confidence: medium
    • Category: other
    • Evidence: trip.save(update_fields=['gallery_id']) fires pre_save / post_save signals. trip_post_save in signals.py checks _original_approval_status and may re-enqueue update_gallery_for_trip_task(instance.id) at line 189 because the trip is APPROVED and now has a gallery_id. That probably doesn't loop because update_gallery_for_trip_task just PATCHes remote state, but it is an unintended second API call on every fresh gallery create.
    • Recommendation: Use Trip.objects.filter(pk=trip.id).update(gallery_id=gallery_id) to bypass signals, matching the pattern already used in signals.py:158 and 170.

    [LOW] Huey logger name is ad4x4-worker but some tasks import from code that logs to ad4x4-web¶

    • File: api/background.py:14, cross-reference api/signals.py:17, api/services/trip_registration_service.py:9
    • Task: n/a (observability)
    • Confidence: high
    • Category: obs
    • Evidence: Tasks log to ad4x4-worker, but they call service functions that log to ad4x4-web (signals) or other contexts. Correlating a task's full log trail requires joining on the task ID, which is never logged.
    • Recommendation: Log task start/end in each task body: logger.info(f'send_trip_notification start trip={trip_id}') + logger.info('...end'). Add the Huey task ID (huey.api.Task.id is available on the task object via execute_ignore_result=False context or a decorator wrapper).

    [LOW] from ... import AccountDeletionRequest mid-file at line 161¶

    • File: api/background.py:161
    • Task: n/a (code hygiene)
    • Confidence: high
    • Category: other
    • Evidence: The import is wedged between restore_gallery_for_trip_task and send_new_trip_comment_notification_task, suggesting it was added to avoid a top-of-file circular import. No actual circular exists today — AccountDeletionRequest can safely be imported from api.models.models_member at the top.
    • Recommendation: Move to the header. Same for the late from api.models.models_geocoding_cache import GeocodingCache at line 178 — both should sit at the top.

    CLAUDE.md §10 drift¶

    Tasks in code not in docs: - cleanup_blacklisted_tokens — documented correctly (daily 04:30). OK. - cleanup_expired_outstanding_tokens — documented correctly (daily 04:45). OK. - cleanup_expired_geocoding_cache — documented correctly (daily 01:00). OK.

    After cross-reference, every code-side task appears in CLAUDE.md §10 tables.

    Tasks in docs not in code: none. All 14 async and 8 periodic tasks listed in §10 match the decorated functions in api/background.py.

    Minor drift worth noting: - CLAUDE.md §10 lists send_removed_from_trip_registered_notification and send_removed_from_trip_waitlist_notification with retry_delay 15 min (= 900s) — matches code. - CLAUDE.md §10 Gallery tasks: create/update 6 retries / 1 hr, delete/restore 3 retries / 1 hr — matches code. - The task-count discrepancy in CLAUDE.md §3 ("14 async tasks") is consistent with the code count (14 @task-decorated functions).

    No doc-drift corrections needed in CLAUDE.md §10. Main documentation gap is §15 — the transaction.on_commit gotcha is mentioned in the audit framing but not currently called out as a repo-wide gotcha. If the fixes in this audit are applied, §15 should gain an entry:

    Always enqueue Huey tasks from transaction.on_commit. Every enqueue site in views, serializers, and signals that runs inside a DB transaction must wrap the call in transaction.on_commit(lambda: my_task(pk)), otherwise the worker races the writer and reads rolled-back state.

    Summary of severity¶

    • CRITICAL (1): 2-arg vs 1-arg mismatch in trip_registration_service and views_trip.CancelTripRegistration — runtime TypeError on every real cancel flow that goes through these paths.
    • HIGH (3): Instances instead of IDs, no on_commit anywhere, gallery tasks swallow errors.
    • MEDIUM (3): Gallery double-create, club_news partial retry, account-deletion non-idempotency.
    • LOW (4): Two-query purge, token cleanup ordering, signal re-fire, logger naming / late imports.

    No task-scheduling timezone issue — HUEY['utc']=False + TIME_ZONE='Asia/Dubai' is correct and CLAUDE.md §15's USE_TZ gotcha is respected throughout (all periodic tasks use timezone.now()).
