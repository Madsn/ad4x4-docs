    Step 11 — Dependency Audit (pip-audit)¶

    Ran pip-audit against both requirements.txt and requirements-dev.txt in the project venv.

    Summary¶

    • requirements.txt: 104 packages scanned, 24 known vulnerabilities in 9 packages
    • requirements-dev.txt: No known vulnerabilities

    Critical block — Django 13 CVEs¶

    Current version: django==6.0.1 · Recommended: upgrade to 6.0.4 minimum (drop-in patch release)

    The 13 CVEs in Django ordered by exploit potential against AD4x4:

    CVE Severity Fix Relevance to AD4x4
    CVE-2026-1312 — SQL injection in QuerySet.order_by() via column aliases with periods Critical 6.0.2 Very likely exploitable. AD4x4 has several endpoints that accept an order_by query param (trip search, member search, upgrade request listings). If any reach user-controlled alias values, this is an SQL injection vector.
    CVE-2026-1287 — SQL injection in FilteredRelation column aliases via control characters Critical 6.0.2 Possibly exploitable if FilteredRelation is used; grep to confirm.
    CVE-2026-1207 — SQL injection in RasterField (PostGIS only) High 6.0.2 Not applicable — no PostGIS usage.
    CVE-2026-4292 — Admin list_editable forgery allows instance creation via forged POST High 6.0.4 Admin-only but significant. Staff with admin access can be tricked via CSRF? Needs review of admin pages that use list_editable.
    CVE-2026-4277 — Add-permission bypass on GenericInlineModelAdmin via forged POST High 6.0.4 Same as above — admin panel risk.
    CVE-2026-3902 — ASGIRequest header spoofing via ambiguous header mapping High 6.0.4 The AD4x4 backend is WSGI via Gunicorn (per CLAUDE.md §11), so ASGI is not active. Low practical risk; still worth the upgrade.
    CVE-2026-33034 — ASGI Content-Length bypass of DATA_UPLOAD_MAX_MEMORY_SIZE High 6.0.4 Same — WSGI not affected.
    CVE-2026-33033 — MultiPartParser perf degradation via Content-Transfer-Encoding Medium 6.0.4 Applies to multipart upload paths (avatar, trip image, logbook migration PDF, feedback image).
    CVE-2026-25674 — Race in file-system storage / file-based cache Medium 6.0.3 AD4x4 uses filesystem MEDIA_ROOT = /app/uploads (prod) and LocMem cache (dev) — low risk for cache side; some risk for uploads if concurrent writes hit identical filenames. Django's default FileSystemStorage.get_available_name handles this but the CVE implies edge cases.
    CVE-2026-25673 — URLField.to_python() NFKC normalization on Windows Medium 6.0.3 Production runs Linux (Docker) — not affected. Dev on Windows technically affected but dev-only.
    CVE-2025-14550 — ASGIRequest DoS via multiple headers Medium 6.0.2 WSGI — not affected.
    CVE-2026-1285 — Truncator.chars/.words XSS via crafted HTML with html=True Low 6.0.2 Grep Truncator and truncatechars_html in codebase; likely unused.
    CVE-2025-13473 — mod_wsgi check_password() auth via untrusted input Low 6.0.2 Not applicable — AD4x4 uses Gunicorn, not mod_wsgi.

    Other vulnerable packages¶

    cryptography==46.0.4 → 46.0.7 (3 CVEs)¶

    CVE Fix Relevance
    CVE-2026-39892 46.0.7 Buffer overflow in Hash.update() with non-contiguous Python buffers. Relevant to any code that hashes user-supplied bytes (file upload hashing, JWT signing internals via pyjwt). High severity — upgrade.
    CVE-2026-34073 46.0.6 DNS name constraints only validated against SANs, not peer name. Relevant for any cert-validated outbound TLS: HERE Maps, Gallery API, FCM. Upgrade.
    CVE-2026-26007 46.0.5 load_der_public_key/load_pem_public_key issue. Not invoked by AD4x4 code directly (JWT uses HS256 = symmetric, not asymmetric key loading). Low practical risk, but free with the upgrade.

    pyjwt==2.11.0 → 2.12.0 (1 CVE) — JWT-relevant¶

    • CVE-2026-32597 — PyJWT does not validate the crit (Critical) Header Parameter (RFC 7515 §4.1.11). A JWS with an unknown crit claim is accepted instead of rejected as required. Directly relevant to AD4x4 auth (SIMPLE_JWT.ALGORITHM=HS256). A crafted token with a crit header listing a spec extension the token fails to satisfy would be wrongly accepted. Exploitability depends on whether any attacker-controlled path produces such tokens — not trivially exploitable since AD4x4 signs with a server-only secret, but the defense-in-depth upgrade is cheap.

    pillow==12.1.0 → 12.2.0 (2 CVEs) — image upload paths affected¶

    • CVE-2026-25990 (fix 12.1.1) — out-of-bounds write on crafted PSD image. AD4x4 accepts avatar, trip image, logbook migration PDF (PDF not PIL), feedback image, trip report images, sponsor images. If any of these reach Pillow and a user uploads a .psd, the worker process could crash or worse.
    • CVE-2026-40192 (fix 12.2.0) — FITS decompression bomb (scientific image format, extremely unlikely in this codebase).
    • Recommendation: Upgrade to 12.2.0 and add an explicit content-type allow-list in image-upload validators (JPEG/PNG/WebP only — no PSD/FITS/TIFF unless specifically needed).

    requests==2.32.5 → 2.33.0 (1 CVE)¶

    • CVE-2026-25645 — predictable filename in extract_zipped_paths(). AD4x4 does not use that function (grep confirms). Still, upgrade for hygiene.

    pyasn1==0.6.2 → 0.6.3 (1 CVE, DoS via deep recursion)¶

    • CVE-2026-30922. pyasn1 is a transitive dep (likely via cryptography/OIDC). DoS only. DOS is excluded from this audit's severity reporting per policy; upgrade with the batch anyway.

    pygments==2.19.2 → 2.20.0 (1 CVE)¶

    • CVE-2026-4539 — ReDoS in AdlLexer. Transitive (likely via docs or drf-spectacular). DOS-class, low real impact.

    pytest==9.0.2 → 9.0.3 (1 CVE, dev-only)¶

    • CVE-2025-71176 — /tmp/pytest-of-{user} naming allows local user to cause DoS/priv-esc. Dev-only (pytest is in requirements-dev.txt, not requirements.txt). But pip-audit found it in requirements.txt too — verify where pytest is declared. Upgrade.

    python-dotenv==1.2.1 → 1.2.2 (1 CVE)¶

    • CVE-2026-28684 — set_key()/unset_key() follow symlinks. Only relevant if AD4x4 or its tooling calls those write functions on an attacker-writable path. Production doesn't rewrite .env, so this is effectively dev-only. Upgrade with the batch.

    Findings¶

    [critical / confidence high] Django 6.0.1 exposes the backend to multiple SQL-injection CVEs¶

    • Category: cve-dep
    • Evidence: pip-audit output above; CVE-2026-1312 in particular allows SQL injection via QuerySet.order_by() — a query param commonly passed from the mobile app and web portal (trip/member search endpoints).
    • Exploit scenario: Attacker sends GET /api/trips/search/?order_by=<crafted_sql> (or similar). If the view passes that param directly into .order_by(), database contents are exposed or modified.
    • Recommendation: Upgrade Django==6.0.4 in requirements.txt today. Regression-test with pytest. No API breakage expected (patch-level release).

    [high / confidence high] PyJWT 2.11.0 accepts tokens with unknown crit headers¶

    • Category: auth-lib-cve
    • Evidence: CVE-2026-32597. AD4x4 uses simplejwt which uses PyJWT internally.
    • Recommendation: Upgrade PyJWT>=2.12.0. Low risk of breakage (defensive fix; tokens signed by the server's own secret won't contain hostile crit headers unless the attacker can forge signatures — which they can't).

    [high / confidence high] Cryptography 46.0.4 has a buffer-overflow in Hash.update()¶

    • Category: mem-cve
    • Evidence: CVE-2026-39892. Buffer overflow on non-contiguous buffers passed to hash functions.
    • Exploit scenario: Any code path hashing user-supplied bytes. Limited surface in AD4x4 but cryptography is a transitive dep of everything TLS.
    • Recommendation: Upgrade cryptography>=46.0.7.

    [high / confidence high] Pillow 12.1.0 out-of-bounds write on crafted PSD image¶

    • Category: img-cve
    • Evidence: CVE-2026-25990.
    • Exploit scenario: Attacker uploads a .psd as avatar/feedback image/trip image. Worker process memory corruption.
    • Recommendation: Upgrade Pillow>=12.2.0 AND add an image-format allow-list in every file-upload serializer (MemberSerializer.validate_avatar, TripSerializer.validate_image, feedback/trip-report serializers).

    [medium / confidence high] 5 more Django CVEs fixed in 6.0.4 relevant to admin + multipart¶

    • Category: cve-dep
    • Evidence: CVE-2026-4292, CVE-2026-4277, CVE-2026-33033, CVE-2026-33034, CVE-2026-3902, CVE-2026-25674, CVE-2026-25673, CVE-2026-1285, CVE-2025-14550, CVE-2025-13473.
    • Recommendation: Single upgrade Django==6.0.4 closes all 13 Django CVEs at once.

    [medium / confidence medium] Minor dep upgrades bundled¶

    • Category: cve-dep
    • Recommendation: Batch upgrade: text Django==6.0.4 cryptography==46.0.7 pyjwt==2.12.0 pillow==12.2.0 requests==2.33.0 pyasn1==0.6.3 pygments==2.20.0 pytest==9.0.3 python-dotenv==1.2.2 Test the full suite before shipping. python manage.py check --deploy should be clean.

    Positives¶

    • requirements-dev.txt: no vulnerabilities.
    • No end-of-life dependencies.
    • django-oidc-provider 0.9.0 — no known CVEs, but per CLAUDE.md §2/§15, its Django 6 compatibility is worth re-testing after any Django upgrade.

    Follow-ups¶

    1. Create a single PR that bumps all 9 packages to their fix versions.
    2. Run full test suite and manage.py check --deploy.
    3. Regenerate schema.yml and compare — Django patch releases shouldn't change schema, but verify.
    4. Grep for order_by( call sites that read from request.query_params/request.GET and add an allow-list of column names.
    5. Add explicit image-format validators to every ImageField serializer.
    6. After upgrade, add pip-audit to the CI pipeline (fails the build on new CVEs).
