    Step 7 — Performance Probes¶

    Caveat¶

    mcp__django-ai-boost__query_model requires a DB connection; the dev DB dev doesn't exist in this environment, so no live aggregate probes were run. This step falls back to static analysis: pattern grep + cross-reference with Step 6 code-review findings.

    Follow-up for the team: stand up a realistic dev DB or connect the MCP to staging to get actual row-count distributions and query plans. The findings below identify suspects; live probes would confirm hit rates.

    Static metrics¶

    Metric Count
    Files in api/views/ 30
    Total potentially-expensive query patterns (.all() / .filter().first() / for x in .objects. / related_set.all()) 62 occurrences across 16 files
    select_related/prefetch_related uses in api/ (views + services + migrations) 18 occurrences across 6 files
    Views with any query-optimization call 5 of 30 (views_member, views_trip, views_triprequest, views_tripreport, views_upgraderequest)

    Interpretation: five views have thought about N+1; the other 25 haven't. Many of those 25 are small resource-level ViewSets where the default DRF generic behaviour is OK (single retrieve), but several — e.g. views_logbook.py, views_clubnews.py, views_upgraderequest.py listings, views_pushnotification.py — serialize FK-heavy data and almost certainly have N+1 on list endpoints.

    Hotspots flagged (cross-reference with Step 6)¶

    [high / confidence high] TripExportRegistrantsView — confirmed N+1¶

    • File: api/views/views_trip.py:709 — has select_related but partial
    • Source: Trip-flow review agent (raw/06-code-review-trip-flow.md)
    • Evidence: The select_related on TripRegistration is incomplete relative to what the CSV serializer accesses (vehicle, member details).
    • Recommendation: Expand to .select_related('member__level', 'vehicle') and profile.

    [high / confidence high] TripViewLogbookView — prefetch defeated by .filter(...).first() pattern¶

    • File: api/views/views_trip.py
    • Source: Trip-flow agent
    • Evidence: The view prefetches logbook skills, then accesses via .filter().first() on the prefetched M2M — which issues a fresh query, bypassing prefetch cache.
    • Recommendation: Use the Prefetch object with to_attr and index into the list instead of calling .filter() on the related manager.

    [high / confidence high] MemberViewSet.list — no select_related('level') or prefetch_related('groups')¶

    • File: api/views/views_member.py
    • Source: Member-flow agent
    • Evidence: Bare Member.objects.all() used while serializer renders level.name and (via permission middleware) user groups.
    • Recommendation: Add a get_queryset override.

    [medium / confidence high] Six copy-pasted Vehicle.objects.filter(member=..., id=...).first() calls in views_trip.py¶

    • Files: views_trip.py:99, 277, 306, 336, 360, 506
    • Source: Trip-flow agent (DRY violation)
    • Evidence: Each of the 6 register/force-register/checkin endpoints re-implements the vehicle resolve.
    • Recommendation: Extract to a helper on Vehicle.manager or a service function. The repeated query itself is cheap (PK + FK indexed), so the perf hit is low — this is more about maintainability.

    [medium / confidence high] NotificationLogViewSet uses [:20] hard slice¶

    • File: api/views/views_pushnotification.py
    • Source: Notifications review agent
    • Evidence: Hard-coded [:20] bypasses pagination. If a user has 1000s of unread notifications the front-end can't page through them.
    • Recommendation: Remove the slice; let DRF pagination handle it.

    [medium / confidence high] N+1 in upgrade_eligibility.py on trip lead/level and per-skill logbook counts¶

    • Source: Upgrade-flow agent
    • Evidence: Per-trip and per-skill loop issues one query each.
    • Recommendation: Annotate with counts or use prefetch_related('...').

    [medium / confidence medium] LogbookEntryViewSet likely N+1 (not prefetched)¶

    • File: api/views/views_logbook.py — no select_related/prefetch_related
    • Inference: LogbookEntry has FKs to trip, member, signed_by plus M2M to skills_verified, and the serializer likely renders nested names. Logbook list endpoint for power users (marshals viewing all entries) would amplify.
    • Recommendation: Add .select_related('trip', 'member', 'signed_by').prefetch_related('skills_verified') to get_queryset.

    [medium / confidence medium] UpgradeRequestViewSet list endpoints likely N+1¶

    • File: api/views/views_upgraderequest.py
    • Inference: The serializer renders applicant.username, target_level.name, and counts of 4 voter M2Ms. Without annotation and prefetch, that's 5+ queries per row.
    • Recommendation: Annotate counts via Count, prefetch applicant + target_level.

    [medium / confidence high] Missing index suspects (per raw/03-model-schema.md)¶

    • NotificationLog.timestamp — nightly purge benefits from index.
    • NotificationLog.is_read — mark-as-read heavy reads.
    • TripRegistration.registration_date — ordering common.
    • UpgradeRequest.verdict_date — listings.
    • LogbookEntry.created_at — history listings.

    [low / confidence high] TripRequest.objects.select_related('level') already present in triprequests aggregate/export — good¶

    • File: views_triprequest.py:192, 277
    • Positive finding — the aggregate endpoint has been optimized.

    [low / confidence medium] Cache: dev is LocMemCache; prod Redis¶

    • Observation: CACHES branches on REDIS_HOST env var (see raw/05-settings-middleware.md). Per-process LocMemCache in dev means if a dev spawns two workers they'll have inconsistent cache state. Not user-facing, but worth noting.
    • Recommendation: None — accepted dev-vs-prod drift.

    [info / confidence high] HERE Maps cache has TTL unit inconsistency (from misc-services agent)¶

    • See raw/06-code-review-misc-services.md finding F-M6. Worth cross-referencing because a "4-year cache" would permanently store stale geocoding rows.

    Probe plan (for later, once DB is available)¶

    # Row counts per hot model
query_model Member    — total count, count(is_active=True), count(paid_member=True)
query_model Trip       — total, by approval_status, upcoming (start_time > now)
query_model TripRegistration — total, count per trip (distribution)
query_model LogbookEntry — total, per member distribution, orphaned (trip deleted)
query_model LogbookSkillReference — total, dupes on (member, trip, logbook_skill)
query_model UpgradeRequest — total, by status, oldest IN_PROGRESS
query_model NotificationLog — total, oldest timestamp (purge health)
query_model GeocodingCache — total, count where expires_at < now() (cleanup lag)

# Data-integrity checks
orphan TripRegistration rows (trip deleted) — should be 0 due to CASCADE but verify
orphan LogbookEntry rows — same
Member rows with level=NULL — should be 0
Trip.lead=NULL rows — only allowed transiently

    Summary¶

    • No live profiling possible in this environment.
    • Static analysis confirms Step 6 agents' findings — several confirmed N+1s, one defeated prefetch, and widespread inconsistency in query optimization across views.
    • Roughly 5/30 views use query optimization. Remaining 25 are either simple enough not to need it or have latent N+1.
    • Recommend seeding dev DB from staging (anonymized) and re-running this step with live query_model probes.
