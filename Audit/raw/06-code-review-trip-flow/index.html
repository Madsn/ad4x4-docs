    Files reviewed¶

    Findings¶

    [critical] CancelTripRegistration calls notification helpers with wrong signature¶

    • File: api/views/views_trip.py:436,439
    • Confidence: high
    • Category: error-handling / correctness
    • Evidence: python send_removed_from_trip_registered_notification(user, trip) ... send_removed_from_trip_waitlist_notification(user, trip) Every other caller (e.g. RemoveMemberFromTripRegistration at line 405/409 and TripRegistrationService.remove_from_registered/remove_from_waitlist) passes a single cancellation/TripRegistrationCancellationReason object. Since send_* are Huey tasks (@db_task), any argument-shape mismatch will only surface when the task executes, producing silent background failures. Users will see trip_registration_cancelled success, but no notification is sent and the task retries 2x then dies.
    • Recommendation: Route through the service: TripRegistrationService.remove_from_registered(user, trip) / remove_from_waitlist(user, trip), and create a TripRegistrationCancellationReason row (even with a default reason like SELF_CANCELLED) so the notification task has a consistent argument. Verify the task signature in api/background.py and align all call sites.

    [critical] trip.cut_off < datetime.datetime.now() violates USE_TZ=False convention¶

    • File: api/views/views_trip.py:294, 370
    • Confidence: high
    • Category: other (timezone gotcha, §15)
    • Evidence: python if trip.cut_off < datetime.datetime.now(): CLAUDE.md §15 explicitly warns: "Never use datetime.datetime.now() — use django.utils.timezone.now()." With USE_TZ=False the two happen to coincide in naive Asia/Dubai time today, but any future migration to TZ-aware datetimes will silently break cutoff checks, and the project convention is already violated.
    • Recommendation: from django.utils import timezone and replace with timezone.now(). Remove the bare import datetime at the top of the file if no longer needed.

    [high] RegisterForTrip has contradictory permission branching — permission holders skip all validation¶

    • File: api/views/views_trip.py:273-281
    • Confidence: high
    • Category: perms
    • Evidence: python if permission_matrix_exists_or_user_is_superuser(user, ActionChoice.EDIT_TRIP_REGISTRATIONS): ... msg = add_to_registered(user, trip, vehicle=vehicle) return Response(...) Users with EDIT_TRIP_REGISTRATIONS skip every sanity check below: trip-approval status, level-requirement, cutoff, capacity, duplicate registration. That may be intentional for admin-driven registration, but this endpoint is /api/trips/<pk>/register (member-initiated). Admin force-registration is supposed to flow through ForceRegisterForTrip. Bypassing trip_already_registered and trip_full silently is a footgun — capacity can be over-run without any audit trail.
    • Recommendation: Either document the bypass explicitly, or remove the early branch and let permissioned users go through the normal flow (with a separate bypass_capacity flag on ForceRegisterForTrip for the admin path). At minimum, keep the trip_already_registered check above the permission branch.

    [high] N+1 in TripExportRegistrantsView for trip-count-per-level computation¶

    • File: api/views/views_trip.py:742-754
    • Confidence: high
    • Category: n+1
    • Evidence: python for registration in registrations: member = registration.member trip_counts_by_level = {} member_trip_registrations = TripRegistration.objects.filter( member=member, checked_in=True ).select_related('trip__level') for trip_reg in member_trip_registrations: ... For every registrant we fire a fresh query loading all of that member's check-ins across the entire history, then aggregate in Python. For a 50-member trip this is 50 extra queries and potentially thousands of rows materialised.
    • Recommendation: Aggregate once in SQL: python counts = (TripRegistration.objects .filter(member__in=[r.member_id for r in registrations], checked_in=True) .values('member_id', 'trip__level__name') .annotate(n=Count('id'))) Build a {(member_id, level_name): n} dict and look up per row. One query instead of N.

    [high] N+1 in TripViewLogbookView per-member logbook lookup¶

    • File: api/views/views_trip.py:824-833
    • Confidence: high
    • Category: n+1
    • Evidence: python .prefetch_related('member__logbook_entry_member') ... for registration in checked_in_registrations: member = registration.member logbook_entry = member.logbook_entry_member.filter(trip=trip).first() prefetch_related('member__logbook_entry_member') caches all logbook entries per member, but then .filter(trip=trip).first() triggers a new query, defeating the prefetch entirely and re-loading per member.
    • Recommendation: Use a Prefetch with a filtered queryset bound to this trip: python from django.db.models import Prefetch qs = TripRegistration.objects.filter(trip=trip, checked_in=True)\ .select_related('member')\ .prefetch_related(Prefetch( 'member__logbook_entry_member', queryset=LogbookEntry.objects.filter(trip=trip).select_related('signed_by'), to_attr='trip_logbook_entries')) Then registration.member.trip_logbook_entries[0] if ... else None with no extra query.

    [high] Missing transaction boundaries around multi-row mutations¶

    • File: api/views/views_trip.py:93-107, 169-178, 400-415, 510-519; api/services/trip_registration_service.py:14-26, 29-41
    • Confidence: high
    • Category: tx
    • Evidence: TripCreateView.create does serializer.save(), then add_to_registered (add-to-M2M + remove-from-waitlist + trip.save), then TripRegistration...update(checked_in=True), then queues a Huey notification — all unwrapped. TripApproveView.post likewise mutates approval_status, approved_by, adds a deputy, registers the user, flips checked_in, and fires two notifications, again without transaction.atomic. RemoveMemberFromTripRegistration.post builds an unsaved TripRegistrationCancellationReason, mutates M2M, fires a Huey task, then saves the cancellation and the trip. If any step fails mid-flight you get partial state (member added but not checked in, trip approved but notification never queued, cancellation notified but cancellation row never persisted).
    • Recommendation: Wrap each multi-row endpoint in with transaction.atomic(): and use transaction.on_commit(lambda: send_*) for Huey enqueues so notifications never fire for rolled-back transactions. This matters more once Huey is production-async.

    [high] Race condition in add_to_registered + capacity check¶

    • File: api/views/views_trip.py:300-301, api/services/trip_registration_service.py:14-26
    • Confidence: medium
    • Category: tx
    • Evidence: Capacity check if trip.registered.count() >= trip.capacity in the view is followed by a non-atomic add_to_registered in the service. Two concurrent requests both see count == capacity - 1, both succeed. TripRegistrationService.add_users_from_waitlist also loops while trip.registered.count() < trip.capacity with no lock.
    • Recommendation: Use select_for_update() on the trip row inside an atomic block, or add a database UniqueConstraint/CheckConstraint on capacity. At minimum, re-check capacity inside the service under lock.

    [high] add_users_from_waitlist drops the waitlist entry's vehicle¶

    • File: api/services/trip_registration_service.py:39
    • Confidence: high
    • Category: other (data loss)
    • Evidence: python trip.registered.add(user, through_defaults={'trip': trip}) No vehicle is forwarded from TripWaitlist.vehicle, so members promoted from the waitlist lose their previously-selected vehicle. Contrast with AcceptMemberFromWaitlist.post (line 479-483), which correctly reads waitlist_entry.vehicle. The automatic promoter and the manual accept behave inconsistently.
    • Recommendation: python entry = waitlist_registrations.pop(0) through_defaults = {'trip': trip} if entry.vehicle_id: through_defaults['vehicle'] = entry.vehicle trip.registered.add(entry.member, through_defaults=through_defaults)

    [high] Business logic leakage — views own trip-registration rules¶

    • File: api/views/views_trip.py:93-107, 170-178, 256-257, 269-311, 324-346, 353-378, 389-416, 449-485, 488-519
    • Confidence: high
    • Category: style (§14 violation)
    • Evidence: TripCreateView.create performs force-waitlist check, vehicle resolution, registration and check-in of the lead, and notification enqueue. TripEditView.update strips ineligible deputy leads and re-checks-in the new lead. RegisterForTrip.post has six guard conditions inline. TripApproveView.post mutates four fields, adds a deputy, registers + checks in, and fires two notifications. Per CLAUDE.md §14: "Business logic goes to services/ — views are thin". The thin shim add_to_registered = TripRegistrationService.add_to_registered confirms the intent; the rest of the flow just didn't follow.
    • Recommendation: Push into TripRegistrationService:
    • register_lead_to_trip(trip, lead, vehicle_id) — vehicle resolution + add + auto-check-in.
    • register_member_to_trip(trip, user, vehicle_id) — all six guards return structured error codes.
    • approve_trip(trip, approver, vehicle_id) — mutation + notifications.
    • decline_trip(trip, approver).
    • handle_lead_change(trip, old_lead, new_lead). Views become 10-line controllers that map service result to HTTP status.

    [medium] Vehicle-resolution pattern repeated 6 times¶

    • File: api/views/views_trip.py:96-101, 274-279, 334-338, 357-362, 503-508; also AcceptMemberFromWaitlist 479-481
    • Confidence: high
    • Category: style (DRY)
    • Evidence: python vehicle = None if vehicle_id: vehicle = Vehicle.objects.filter(member=x, id=vehicle_id).first() if not vehicle: vehicle = x.vehicles.filter(is_primary=True).first() is copy-pasted in 6 places. Behaviour changes require 6 edits, invariably drift.
    • Recommendation: Add resolve_member_vehicle(member, vehicle_id=None) -> Optional[Vehicle] helper in trip_registration_service.py (or a new api/services/vehicle_service.py). Use .filter(...).only('id', 'brand', ...).first() if serializers don't need full object.

    [medium] TripViewSet.get_queryset prefetches half the tree, list serializer still triggers N+1¶

    • File: api/views/views_trip.py:243-248
    • Confidence: medium
    • Category: n+1
    • Evidence: select_related('lead', 'level', 'meeting_point') covers FKs, and prefetch_related('tripregistration_set__member', 'tripwaitlist_set__member') covers through-tables. But ListTripSerializer likely also reads trip.deputy_leads.all() and lead.level / lead.avatar. Without prefetch_related('deputy_leads', 'deputy_leads__level') and select_related('lead__level'), each list page still fires one query per trip for deputies.
    • Recommendation: Audit ListTripSerializer for accessed fields, then: python Trip.objects.select_related('lead__level', 'level', 'meeting_point')\ .prefetch_related( 'deputy_leads__level', Prefetch('tripregistration_set', queryset=TripRegistration.objects.select_related('member', 'vehicle')), Prefetch('tripwaitlist_set', queryset=TripWaitlist.objects.select_related('member', 'vehicle')), ) Add assertNumQueries regression tests.

    [medium] _serialize_updated_trip re-fetches on every mutation response¶

    • File: api/views/views_trip.py:39-48
    • Confidence: medium
    • Category: other (perf)
    • Evidence: Every register/unregister/waitlist/force/remove endpoint calls _serialize_updated_trip(trip, request), which does a fresh DB fetch with full prefetch tree. Most callers already have a live trip object in memory — they just need to invalidate prefetch caches.
    • Recommendation: Accept the existing trip and call trip.refresh_from_db(); trip._prefetched_objects_cache = {} or return a lightweight response without the full prefetch tree. Clients that need the new state can poll /api/trips/<pk>/.

    [medium] TripSearch.list returns unpaginated response when page is None¶

    • File: api/views/views_trip.py:1000-1006
    • Confidence: high
    • Category: error-handling
    • Evidence: python page = self.paginate_queryset(queryset) if page is not None: ... return self.get_paginated_response(serializer.data) serializer = self.get_serializer(queryset, many=True) return self.get_paginated_response(serializer.data) The fallback branch calls self.get_paginated_response on a non-paginated serializer. With DRF's StandardResultsSetPagination, this only happens if self.paginator is None, at which point get_paginated_response raises. In practice this branch is dead code masking an edge-case bug.
    • Recommendation: Remove the fallback or return Response(serializer.data) — don't pretend it's paginated.

    [medium] RegisterForTripWaitlist missing PermissionMatrix action check¶

    • File: api/views/views_trip.py:348-378
    • Confidence: medium
    • Category: perms
    • Evidence: Only permissions.IsAuthenticated is enforced. Registration is arguably open to any member, but CLAUDE.md §8 states: "every protected view must add a PermissionMatrix.has_permission() call — do not assume one exists." Waitlisting mutates trip state and queues notifications; it qualifies as a protected action. Similar missing check on RegisterForTrip (relies only on IsAuthenticated) and CancelTripRegistration.
    • Recommendation: Confirm intended access model with product; if self-registration is truly level-gated only, make that explicit via a dedicated ActionChoice.SELF_REGISTER_FOR_TRIP matrix entry (defaulting to all groups). Otherwise add a thin permission class.

    [medium] TripEditView.destroy soft-deletes but ignores HasDeleteTripPermission semantics¶

    • File: api/views/views_trip.py:193-197
    • Confidence: medium
    • Category: other
    • Evidence: destroy() only sets approval_status = CANCELED and saves. No send_trip_cancellation_notification, no waitlist cleanup, no gallery deletion webhook (cross-check api/services/gallery_webhook.py — per CLAUDE.md §10 there's a delete_gallery_for_trip_task that should fire).     [medium] permission_matrix_exists_or_user_is_superuser used instead of PermissionMatrix.has_permission¶

    • File: api/views/views_trip.py:273, 341, 500, 534
    • Confidence: medium
    • Category: perms
    • Evidence: CLAUDE.md §8 says: "PermissionMatrix.has_permission(...) is the single authoritative check." The file uses the permission_matrix_exists_or_user_is_superuser helper defined in api/permissions.py, which is narrower (no member, no require_trip_lead). That's fine for straight "does this group have the action" checks, but the gap should be a documented pattern — currently there are two authoritative checks.
    • Recommendation: Either (a) alias permission_matrix_exists_or_user_is_superuser to PermissionMatrix.has_permission and update CLAUDE.md §8, or (b) migrate call sites to the model method. Don't leave two sources of truth.

    [low] handle_check_in_out content-type parser allows a str through the non-JSON branch¶

    • File: api/views/views_trip.py:559-577
    • Confidence: medium
    • Category: error-handling
    • Evidence: First guard requires members_ids to be a Sequence (string is a Sequence!), so a form-encoded single value like "12" passes the first check, then in the non-JSON branch it's .split(',') correctly — but a JSON payload of "12" (string) also satisfies the outer check, then hits the else branch where isinstance(members_ids, list) is False, correctly rejecting. Works but fragile. Also: collections.abc.Sequence matches str and bytes, giving a misleading error message path.
    • Recommendation: Replace the first guard with isinstance(members_ids, (list, str)) explicitly, or use a DRF serializer with ListField(child=IntegerField()) and drop the manual parsing entirely.

    Out-of-scope suggestions¶

    • Add assertNumQueries regression tests for TripViewSet.list, TripViewLogbookView, TripExportRegistrantsView.
    • Consider extracting vehicle_id resolution into a serializer field that returns a Vehicle instance, eliminating the manual Vehicle.objects.filter(...) pattern across six endpoints.
    • The add_to_registered / add_users_from_waitlist / remove_from_registered / remove_from_waitlist service methods each call trip.save(), which is likely unnecessary — M2M .add()/.remove() already persist. Verify and remove to avoid redundant UPDATE trip statements.
