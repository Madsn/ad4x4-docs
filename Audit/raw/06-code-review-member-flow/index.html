    Findings¶

    [critical] set_primary cross-tenant attack — can set another member's vehicle as primary on self¶

    • File: api/views/views_vehicle.py:104-116
    • Confidence: high
    • Category: perms / data-integrity

    • Evidence: ```python def setprimary(self, request, pk=None): vehicle = self.getobject()

      with transaction.atomic(): Vehicle.objects.filter(member=request.user).update(isprimary=False) vehicle.isprimary = True vehicle.save() ``setprimaryis not routed through the router (it is registered manually inad4x4/urls.py:205asVehicleViewSet.asview({'post': 'setprimary'})and is **not** decorated with@action). When mounted viaasview, the viewset'sgetqueryset()filter (Vehicle.objects.filter(member=self.request.user)) does apply, soself.getobject()correctly 404s on a vehicle not owned by the caller. That's fine. However, even ignoring that,setprimarythen executesVehicle.objects.filter(member=request.user).update(isprimary=False)followed byvehicle.save()— the explicitupdateonly touches the caller's vehicles, so ownership is not directly bypassed via this path. **The real issue is that the view is not declared with@action(detail=True, methods=['post'])**, meaninggetpermissions()/getserializerclass()behave withself.action == 'setprimary'only coincidentally because of DRF routing internals, not by design. More urgently, DRF's schema generation / permission classes assume viewset actions are registered; omitting@actionleaves the endpoint invisible toextendschemaviewdecoration at the class level and makes the@extendschemaat line 99 dead code. - **Recommendation:** Decoratesetprimarywith@action(detail=True, methods=['post'], urlpath='setprimary')and register it through the DRF router so that permission classes, schema introspection, andself.action` are consistent.

    [high] MemberViewSet exposes full member list with no pagination scoping and returns PII¶

    • File: api/views/views_member.py:116-154
    • Confidence: high
    • Category: perms
    • Evidence: python def get_permissions(self): ... if self.action in ['list', 'retrieve']: permission_classes = (drf_permissions.IsAuthenticatedOrReadOnly,) Every authenticated user can list all Members via /api/members/ with full BasicMemberSerializer output. There is no PermissionMatrix.has_permission() gate on list or retrieve, despite ActionChoice.SEARCH_MEMBERS and VIEW_CONTACT_INFO existing and being enforced on the dedicated MemberSearch and triphistory endpoints. Since IsAuthenticatedOrReadOnly treats GET as safe, an unauthenticated client with read access can in principle query it too (depending on AllowAny on throttle layer). Per CLAUDE.md §8 "every protected view must add a PermissionMatrix check". A listable member directory is a protected action per the rest of the codebase (see MemberSearch at line 526 requiring HasSearchMembersPermission).
    • Recommendation: Gate list behind HasSearchMembersPermission (or a dedicated VIEW_MEMBER_LIST action). At minimum, require authentication (swap IsAuthenticatedOrReadOnly for IsAuthenticated) so anonymous clients cannot enumerate the directory.

    [high] Vehicle limit check in serializer is not concurrency-safe (TOCTOU)¶

    • File: api/serializers/serializers_vehicle.py:47-57 (called from views_vehicle.py:63-66)
    • Confidence: high
    • Category: data-integrity / tx
    • Evidence: python vehicle_count = Vehicle.objects.filter(member=request.user).count() if not self.instance: settings = ConfigurableSettings.objects.first() limit = settings.vehicle_limit_per_member if settings else 3 if vehicle_count >= limit: raise serializers.ValidationError(...) The count + create sequence is not wrapped in a transaction and there is no select_for_update or unique constraint. A client firing two simultaneous POST /api/vehicles/ requests can race past the limit. views_vehicle.create() does not wrap perform_create in transaction.atomic().
    • Recommendation: Wrap the create path in transaction.atomic() + select_for_update on the member row, or enforce via a database constraint / counter on Member. At minimum add @transaction.atomic to VehicleViewSet.create.

    [high] N+1 on /api/members/ list: level FK not select_related, no trip_count annotation strategy¶

    • File: api/views/views_member.py:123
    • Confidence: high
    • Category: n+1
    • Evidence: python queryset = Member.objects.all().order_by('id') BasicMemberSerializer (confirmed by the ordering field level__numeric_level at line 129) renders level per-row. Without select_related('level'), each of up to 500 rows (default paginator cap per CLAUDE.md §4) triggers a Level SELECT — 500+1 queries on a page. ProfileSerializer (line 54 of serializers_member.py) uses ConciseLevelSerializer and PermissionMatrixProfileSerializer(many=True); the permission matrix is fetched by Member.permissions property (PermissionMatrix.objects.filter(group__in=self.groups.all())) which is an additional per-row query without prefetch_related('groups', 'groups__permissionmatrix_set').
    • Recommendation: Override get_queryset() on MemberViewSet to add .select_related('level').prefetch_related('groups'), and consider prefetching PermissionMatrix entries when action == 'retrieve'.

    [high] LeadSearch and ActiveTripLeads bypass PermissionMatrix despite exposing member directory¶

    • File: api/views/views_member.py:422-492, api/views/views_member.py:595-680
    • Confidence: medium
    • Category: perms
    • Evidence: Both views use permission_classes = (IsAuthenticated,) only. They return arbitrary member records to any logged-in user with no rate limit beyond the global 200/min throttle. ActionChoice.SEARCH_MEMBERS exists and gates MemberSearch. The current setup allows a casual user to enumerate trip leads and lead candidates without SEARCH_MEMBERS permission. If that is intentional (any member should see trip leads), the design is fine, but it is not cross-checked against PermissionMatrix.
    • Recommendation: Confirm whether lead enumeration is a public-authenticated feature. If not, add a PermissionMatrix.has_permission(user, ActionChoice.SEARCH_MEMBERS) check. Either way, document the intent in a comment.

    [medium] ProfileSerializer.last_visited is read-only but there is no write protection at the view layer¶

    • File: api/serializers/serializers_member.py:63-65 and api/views/views_member.py:138-146
    • Confidence: high
    • Category: data-integrity
    • Evidence: last_visited is listed as a field and marked read-only in the serializer — that is correct. The middleware at api/middleware.py:31 updates it once per hour via a direct Member.objects.filter(...).update(). Since both EditMemberSerializer and ProfileSerializer mark last_visited in read_only_fields, DRF will ignore any client-supplied value. This is good. Flagging it as a potential audit risk in case the field is ever added to a future serializer without read_only — grep the project periodically.
    • Recommendation: No action required; keep the read-only guarantee documented on the Member model fieldset. Consider adding an editable=False at the model level to make the contract enforced by Django's admin and forms as well.

    [medium] Avatar 2.5MB limit enforced only via Member.clean(), which DRF never calls¶

    • File: api/models/models_member.py:104-107 and api/serializers/serializers_member.py:56, 107-124
    • Confidence: high
    • Category: data-integrity
    • Evidence: python def clean(self): if self.avatar: if self.avatar.size > 2.5 * 1024 * 1024: raise ValidationError(...) Member.clean() is only invoked by Django's ModelForm.full_clean() path (admin, forms). DRF ModelSerializer.save() does not call full_clean() unless explicitly invoked. ProfileSerializer and EditMemberSerializer accept avatar without calling instance.full_clean() and without a validate_avatar method. Net effect: an API client can upload avatars larger than 2.5MB, defeating the documented limit (CLAUDE.md §5).
    • Recommendation: Add validate_avatar on EditMemberSerializer / ProfileSerializer that rejects sizes over 2,621,440 bytes, or call instance.full_clean() in update(). Mirror the check from Member.clean().

    [medium] ManuallyRegisterMemberPaymentView accepts boolean as string without validation via serializer¶

    • File: api/views/views_member.py:174-181
    • Confidence: high
    • Category: error-handling
    • Evidence: python payment_received = ( request.data.get('payment_received', '').lower() == 'true' ) member.paid_member = payment_received member.save() It bypasses MembershipPaymentSerializer (defined with BooleanField(required=True) at line 89-90 of serializers_member.py). Callers sending {"payment_received": false} (JSON boolean) will have it coerced to False.lower() — but boolean has no .lower() method, so a AttributeError crashes the view. Callers sending {"payment_received": "TRUE"} work; sending actual JSON booleans break. Missing key returns empty-string → False silently, which at best is a footgun.
    • Recommendation: Use the declared serializer: serializer = MembershipPaymentSerializer(data=request.data); serializer.is_valid(raise_exception=True); member.paid_member = serializer.validated_data['payment_received'].

    [medium] VehicleViewSet.destroy race: re-assigning primary after delete is not transactional¶

    • File: api/views/views_vehicle.py:86-97
    • Confidence: medium
    • Category: tx / data-integrity
    • Evidence: ```python wasprimary = instance.isprimary self.perform_destroy(instance)

    if wasprimary: remaining = Vehicle.objects.filter(member=request.user).first() if remaining: remaining.isprimary = True remaining.save() `` If two primary deletes race, both observewasprimary=True, delete their respective primaries, and both promote the "first" remaining vehicle — in principle safe, but the post-delete.first()depends on ordering (-isprimary, -createdat) and can pick a vehicle that a concurrent create has just inserted as primary. Also, ifremaining.save()fails after the delete commits, the member is left with zero primaries. - **Recommendation:** Wrap intransaction.atomic()+selectfor_update()` on the member's vehicles.

    [medium] VehicleSerializer.validate silently unsets other primaries as a side effect of validation¶

    • File: api/serializers/serializers_vehicle.py:59-64
    • Confidence: high
    • Category: data-integrity / style
    • Evidence: python if data.get('is_primary', False): Vehicle.objects.filter( member=request.user, is_primary=True ).update(is_primary=False) A validate method should not mutate the database. DRF documentation and Django convention place side effects in save() / perform_*. If validate succeeds but a later field-level validate_* fails, primaries were already cleared and will not be restored. Also, this runs on partial updates even when is_primary was not sent — data.get('is_primary', False) returns False when the field is not in data, so the path does not trigger in that case, but the intent is subtle.
    • Recommendation: Move the "clear other primaries" logic into a save() / update() / create() override on the serializer, and wrap it in transaction.atomic() alongside the save of the new primary.

    [low] Response for auth-failed get_queryset returns empty list instead of 403¶

    • File: api/views/views_member.py:243, 246, 308, 311, 336, 339, 368, 371
    • Confidence: medium
    • Category: perms
    • Evidence: When the requesting user is not permitted to view another member's data, the queryset returns .none(), yielding an empty 200 list. This hides the authz failure and makes monitoring harder; additionally, it differs from the project's conventional 403-style response on protected endpoints.
    • Recommendation: Raise PermissionDenied (which DRF maps to 403) from inside get_queryset when can_view_other_member_trip_history returns False, so the client can distinguish "no data" from "not allowed".

    [low] LeadSearch.get_queryset computes group_ids with 4 separate queries and Python set merges¶

    • Category: n+1 / style
