    Resolved findings (verified in source)¶

    F-01 — Gate LogbookSkillReferenceViewSet¶

    • Status: RESOLVED
    • Commit: 12b4999
    • Evidence: api/views/views_logbook.py:26 now reads class LogbookSkillReferenceViewSet(viewsets.ReadOnlyModelViewSet). Writes are no longer possible through this ViewSet. Writes only happen via LogbookEntryViewSet._manage_logbook_skill_references (permissioned) and TripLogbookEntryCreateView (permissioned via check_logbook_entry_permissions).
    • Strength of fix: Excellent — cleanest possible approach (read-only instead of trying to gate writes).

    F-02 — Trip cancellation Huey wrong-arity¶

    • Status: RESOLVED
    • Commit: c959c20
    • Evidence: api/views/views_trip.py:440-445, 460-465 — both self-cancel code paths (registered + waitlist) now create a TripRegistrationCancellationReason with reason='self_cancelled' and pass the cancellation object to the notification task. api/services/trip_registration_service.py also updated. Matches the task signature in api/background.py.
    • Tests: tests/test_cancel_trip_registration.py extended by 47 lines.

    F-05 — Upgrade verdict atomicity + downgrade guard¶

    • Status: RESOLVED
    • Commit: 12b4999
    • Evidence: api/views/views_upgraderequest.py:114, 133-137: python upgrade_request = UpgradeRequest.objects.filter(id=pk).select_for_update()... applicant = Member.objects.filter(pk=applicant_id).select_for_update().first() if applicant.level and applicant.level.numeric_level >= upgrade_request.target_level.numeric_level: return Response({'success': False, 'message': 'applicant_already_at_or_above_target_level'}, status=409) Row-level lock on both upgrade request and applicant; explicit 409 CONFLICT if the request would downgrade.
    • Strength of fix: Very good — both atomicity and downgrade-guard concerns addressed.

    F-06 — ClubNews SENT/ERROR status¶

    • Status: RESOLVED
    • Commit: 12b4999
    • Evidence: api/services/notification_service.py:135-148: python first_exception = None for channel in self._channels: try: channel.send_club_wide_news(data) except Exception as e: if first_exception is None: first_exception = e logger.exception(e) data.status = ClubNewsStatus.ERROR if first_exception else ClubNewsStatus.SENT data.save() if first_exception: raise first_exception The news record only flips to SENT if every channel succeeds; partial failures mark it ERROR. Re-raising the first exception means Huey's retry policy fires.
    • Caveat: Per-channel delivery state is still not tracked — if a retry runs, all channels re-fan-out, so users who received the first attempt may get a duplicate. The Codex review flagged this; Mikkel's self-report lists it as still outstanding.

    Partial fixes¶

    F-04 — transaction.on_commit coverage¶

    • Status: PARTIAL — ~10 of ~14 enqueue sites now use on_commit
    • What's done: All enqueues in api/views/views_trip.py (8 sites), api/views/views_upgraderequest.py (1 site), and api/services/trip_registration_service.py (1 site) are wrapped. See lines 109, 413, 420, 456, 467, 550, 551, 576.
    • What's missing: api/signals.py still has 6 direct task calls:
    • Line 66: send_upgrade_request_created_notification(instance) on UpgradeRequest post_save
    • Lines 161, 168, 178, 184, 189: 5 gallery task calls on Trip post_save
    • Line 195: send_new_trip_comment_notification_task(instance) on TripComment post_save
    • Risk: Signal handlers fire inside the transaction that created the row. If the transaction rolls back (validation error, integrity error, etc.), the task already fired — producing notifications for events that didn't happen or trying to create galleries for trips that don't exist.
    • Recommendation: Wrap each signal task enqueue in transaction.on_commit(...). One-line fix per site.

    F-12 — Member directory PII exposure¶

    • Status: PARTIAL — field-level redaction added; view-level gate still broad
    • What's done: api/serializers/serializers_member_base.py — ContactInfoMemberSerializer.to_representation hides phone, email, dob, ice_name, ice_phone unless the viewer has VIEW_CONTACT_INFO permission or is viewing their own profile. Trip leads/deputies get contact info shown.
    • What's missing: MemberViewSet.list and retrieve still use IsAuthenticatedOrReadOnly — any authenticated member can still enumerate all member IDs, usernames, first/last names, levels, trip counts. Codex review explicitly flagged this.
    • Risk: Primary impact is enumeration / directory scraping, not PII leak. But it does expose paid_member and last_visited timestamps.
    • Recommendation: Add a SEARCH_MEMBERS permission class to the ViewSet's get_permissions() for list+retrieve. Clients that need dropdowns should switch to /api/members/search/ or /leadsearch/ which are already permissioned.

    F-17 — Logbook skill reference delete-reinsert loses history¶

    • Status: STILL PRESENT (now atomic, but underlying pattern unchanged)
    • What's done: The _manage_logbook_skill_references helper (line 136-158) is now called inside transaction.atomic(), so half-deleted state cannot leak. TripLogbookEntryCreateView also deletes and re-inserts inside a transaction.
    • What's missing: The delete-reinsert pattern itself is still destructive — if two marshals sign the same trip for the same member, the second one's save wipes the first's signatures. A unique constraint on (member, trip, logbook_skill) + update_or_create would preserve history.
    • Recommendation: Add the unique constraint in a migration, then switch to update_or_create. Low priority since both signers would be marshals writing the same set, but still a data-integrity concern.
