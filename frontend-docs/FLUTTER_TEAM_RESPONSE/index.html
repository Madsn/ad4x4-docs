    Backend Response to Flutter App Performance Audit¶

    Date: 2026-04-01 In response to: FRONTEND_API_PERFORMANCE_AUDIT.md (2026-03-31) From: Backend Team

    Summary¶

    We reviewed all 12 findings from the Flutter performance audit. We implemented 4 backend changes that directly address your highest-impact findings. The remaining items are frontend-only optimizations or deferred for now.

    What changed on the backend: 1. Trip registration responses now include the updated trip object 2. Cache-Control headers added to static/semi-static endpoints 3. Trip list endpoint now supports registered and waitlisted filters 4. Member trip history endpoint returns richer data (8 new fields)

    No breaking changes. All changes are additive — existing response fields and behavior are preserved.

    Finding-by-Finding Response¶

    T1: Trips List + Home Screen = Duplicate Trip Fetches¶

    Status: No backend change needed (as you noted)

    This is a frontend caching concern. The backend now returns Cache-Control headers on static endpoints, but the trips endpoint itself remains uncached since it contains user-specific data (isRegistered, isWaitlisted). Your recommendation to share the upcomingTripsProvider cache between screens is the correct approach.

    T2: Trip Detail Re-fetched on Every Navigation¶

    Status: No backend change (frontend fix recommended)

    Removing the ref.invalidate(tripDetailProvider(trip.id)) call before navigation is the correct fix. The autoDispose + staleness check pattern you already use will handle freshness.

    T3: Trip Actions Trigger Full List Refresh — IMPLEMENTED¶

    Status: Backend change implemented

    All registration endpoints now return the updated trip object in the response body:

    POST /api/trips/{id}/register    -> {"success": true, "message": "trip_registered", "trip": { ...full trip object... }}
POST /api/trips/{id}/waitlist    -> {"success": true, "message": "trip_waitlisted", "trip": { ...full trip object... }}
POST /api/trips/{id}/unregister  -> {"success": true, "message": "trip_registration_cancelled", "trip": { ...full trip object... }}

    The trip field contains the complete trip object (same schema as GET /api/trips/ list response) with up-to-date registeredCount, waitlistCount, isRegistered, isWaitlisted, etc.

    What you need to do on the Flutter side: 1. After a successful registration/waitlist/unregister call, read the trip field from the response 2. Update the local trip in your tripsProvider state with this object 3. Remove the _ref.read(tripsProvider.notifier).refresh() call

    API docs reference: See docs/trips.md — Registration section for the full response schema.

    T4: Member Details Screen — 6+ Waterfall API Calls¶

    Status: Not implementing composite endpoint

    We evaluated creating a GET /api/members/{id}/summary/ composite endpoint but decided against it for now. The maintenance cost of a composite endpoint that duplicates 9 existing endpoints is not justified at this project's scale.

    What you can do instead: - Use Future.wait() (which you already do) to parallelize the 6+ calls - Cache the results with your existing ApiCacheService - Fix the member_details_screen.dart:28 issue where you create a new MainApiRepository() — use ref.read(mainApiRepositoryProvider) instead to share connection pooling and cache

    L1: getLogbookSkills() Called by 19 Files — PARTIALLY ADDRESSED¶

    Status: Backend Cache-Control header added

    GET /api/logbookskills/ now returns Cache-Control: public, max-age=600 (10 minutes). HTTP clients that respect cache headers will skip the request entirely within the TTL window.

    What you need to do on the Flutter side: The backend header provides defense-in-depth, but the real fix is making all 19 files use cachedLogbookSkillsProvider (which already exists in logbook_skills_cache_provider.dart) instead of calling repository.getLogbookSkills() directly.

    API docs reference: See docs/logbook.md for the endpoint details.

    L2: getUpgradeEligibility() Fetched Redundantly¶

    Status: No backend change

    The upgrade eligibility endpoint serves user-specific data that varies by member, so a Cache-Control: public header is not appropriate. The fix is frontend-only: create a cachedUpgradeEligibilityProvider similar to your existing cachedLogbookSkillsProvider, with a 5-minute TTL via ApiCacheService.

    API docs reference: See docs/upgrade-requests.md — Upgrade Eligibility section.

    L3: Trip Skill Opportunities = 2 API Calls Per Trip Detail View¶

    Status: No backend change

    Both getUpgradeEligibility() and getLogbookSkills() return user-level data that doesn't change between trip views. Cache them on the frontend side as recommended in L1 and L2.

    L4: Timeline Provider — N+1 Trip Detail Fetches¶

    Status: No batch endpoint implemented

    The enriched GET /api/members/{id}/triphistory endpoint (see below) now returns meetingPoint, image, and other fields that were previously missing. If the timeline provider was fetching individual trip details to get these fields, it can now use the trip history endpoint instead.

    API docs reference: See docs/members.md — Member Trip History section for the full response field list.

    L5: Logbook Progress = 3 Cached API Calls¶

    Status: No backend change needed

    Your implementation is already well-done — 3 parallel calls with 5-minute TTL caching. The benefit of a composite endpoint is marginal here.

    C1: No HTTP-Level Caching (ETags/Last-Modified) — PARTIALLY ADDRESSED¶

    Status: Cache-Control headers added to static endpoints

    We added Cache-Control headers to endpoints that serve rarely-changing data:

    Endpoint Cache-Control TTL
    GET /api/logbookskills/ public, max-age=600 10 min
    GET /api/levels/ public, max-age=1800 30 min
    GET /api/meetingpoints/ public, max-age=600 10 min
    GET /api/sponsors/ public, max-age=1800 30 min
    GET /api/faqs/ public, max-age=1800 30 min
    GET /api/choices/carbrand public, max-age=3600 60 min

    ETag/Last-Modified support is deferred for now. Cache-Control provides the majority of the benefit with minimal implementation cost.

    What you need to do on the Flutter side: Ensure your Dio client respects Cache-Control headers. If you use dio_cache_interceptor or similar, it should handle this automatically.

    C2: Notifications Fetched Without Pagination¶

    Status: No backend change

    The notifications endpoint currently returns the last 20 notifications (hard-coded limit). For the home badge, you can count isRead: false items from this set. A dedicated count endpoint is not needed at this stage.

    API docs reference: See docs/notifications.md for endpoint details.

    C3: Admin Wizard Fetches ALL Trips (pageSize: 200 in a loop)¶

    Status: Backend already supports server-side filtering

    The GET /api/trips/ endpoint already supports all the filters the admin wizard needs: level__id, meetingPoint_Area, startTimeAfter, startTimeBefore, lead, approvalStatus. The frontend wizard should send these as query parameters instead of fetching all trips and filtering client-side.

    Additionally, the new registered=true and waitlisted=true filters are now available.

    API docs reference: See docs/trips.md — the Query Parameters table for the full list of supported filters.

    C4: getLogbookSkillReferences() Not Using Shared Cache¶

    Status: No backend change needed (frontend-only fix as you noted)

    C5: Member Details Creates New Repository Instance¶

    Status: No backend change needed (frontend-only fix as you noted)
