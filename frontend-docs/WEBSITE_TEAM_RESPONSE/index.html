    Backend Response to Website Team Requests¶

    Date: 2026-04-01 In response to: BACK_END_TODO.md (2026-03-30) From: Backend Team

    Summary¶

    We reviewed both requests from the website team. Request #1 (server-side filtering for user's trips) has been fully addressed with two backend changes. Request #2 (trailing-slash inconsistency) is acknowledged but will not be changed.

    No breaking changes. All changes are additive.

    Request #1: Server-side filtering for user's registered/waitlisted trips — IMPLEMENTED¶

    We implemented both of your recommended options:

    Option A: registered and waitlisted filters on GET /api/trips/¶

    The trips list endpoint now supports two new query parameters:

    GET /api/trips/?registered=true          -> only trips where the authenticated user is registered
GET /api/trips/?registered=false         -> only trips where the authenticated user is NOT registered
GET /api/trips/?waitlisted=true          -> only trips where the authenticated user is on the waitlist
GET /api/trips/?waitlisted=false         -> only trips where the authenticated user is NOT on the waitlist

    These filters can be combined with all existing filters:

    # User's past registered trips (approved only)
GET /api/trips/?registered=true&approvalStatus=A&startTimeBefore=2026-04-01

# User's upcoming registered trips
GET /api/trips/?registered=true&approvalStatus=A&startTimeAfter=2026-04-01

# User's waitlisted trips
GET /api/trips/?waitlisted=true&approvalStatus=A

    Implementation details: - Uses efficient Exists() subqueries — no client-side filtering needed - Requires authentication (anonymous requests ignore the filter) - Returns the full trip object with all fields (isRegistered, isWaitlisted, registeredCount, capacity, meetingPoint, image, etc.)

    Expected impact on your "My Trips" portal page: - Past tab: Response drops from 3,305 trips (95 KB) to just the user's trips (~15-20 trips, ~15 KB) - Load time should drop from 17-30 seconds to under 1 second

    Option B: Enriched GET /api/members/{id}/triphistory¶

    The trip history endpoint now returns all the fields your portal needs. Previously it returned 8 fields; it now returns 17:

    New fields added: | Field | Type | Description | |-------|------|-------------| | image | string/null | Trip cover photo URL | | meetingPoint | object/null | {id, name, area, lat, lon, link} | | registeredCount | integer | Number of registered members | | capacity | integer | Trip capacity | | isRegistered | boolean | Whether the target member is registered | | isWaitlisted | boolean | Whether the target member is on the waitlist | | allowWaitlist | boolean | Whether the trip allows waitlisting | | approvalStatus | string | Approval status (A, P, C) |

    Previously existing fields (unchanged): id, title, description, startTime, endTime, lead, level, checkedIn

    Which option should you use?¶

    For the "My Trips" portal page, we recommend Option A (GET /api/trips/?registered=true): - Returns the full trip list schema with all fields you need - Supports pagination, date range filters, and ordering - Cleanly separates "upcoming" vs "past" with startTimeAfter/startTimeBefore - One endpoint handles both registered and waitlisted trips

    Option B (triphistory) is better for viewing another member's trip history (admin use case), since the registered filter on /api/trips/ only works for the authenticated user's own trips.

    Example: Building the My Trips portal¶

    # Upcoming tab (registered)
GET /api/trips/?registered=true&approvalStatus=A&startTimeAfter=2026-04-01&pageSize=50

# Upcoming tab (waitlisted)
GET /api/trips/?waitlisted=true&approvalStatus=A&startTimeAfter=2026-04-01&pageSize=50

# Past tab
GET /api/trips/?registered=true&approvalStatus=A&startTimeBefore=2026-04-01&ordering=-startTime&pageSize=50

    API docs reference: See docs/trips.md — the Query Parameters table documents all available filters including the new registered and waitlisted parameters.

    Request #2: Trailing-slash inconsistency — NOT CHANGING¶

    We acknowledge the inconsistency. The pattern is:

    • Main resource endpoints (router-registered ViewSets): require trailing slash (/api/trips/, /api/members/)
    • Sub-action endpoints (manually wired paths): require NO trailing slash (/api/trips/search, /api/members/{id}/triphistory)
    • Choices endpoints: require NO trailing slash (/api/choices/carbrand)

    This is a consequence of Django REST Framework's DefaultRouter (which adds trailing slashes) vs manual path() definitions (which don't). Changing this would risk breaking existing clients (Flutter app, website) that already handle the current pattern.

    The pattern is fully documented in our API docs. Each endpoint's documentation specifies whether it uses a trailing slash or not. When in doubt, check the relevant doc page:

    Document Endpoints covered
    docs/trips.md All trip endpoints including registration, approval, search
    docs/members.md All member endpoints including triphistory, tripcounts, search
    docs/trip-search.md Trip search endpoint
    docs/vehicles.md Vehicle CRUD + car brand choices
    docs/notifications.md Notifications + notification settings
    docs/api-concepts.md General API patterns including trailing slash reference

    Bonus: Additional filters you may find useful¶

    While reviewing your requests, we also added these filters that may help with admin portal features:

    Member date_joined filter¶

    GET /api/members/?dateJoinedAfter=2026-03-01&dateJoinedBefore=2026-04-01

    Useful for "new members this month" admin views.

    Member level__id filter¶

    GET /api/members/?level__id=9

    Filter members by level ID (in addition to the existing level__numeric_level and level__name filters).

    API docs reference: See docs/members.md — Query Parameters table for the full filter list.
