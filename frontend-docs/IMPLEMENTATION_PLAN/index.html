    Change 1: Add registered and waitlisted Filters to Trips Endpoint¶

    Priority: HIGH Source: BACKENDTODO #1, Performance Audit T3 File: api/filters.py

    What¶

    Add two custom filter methods to TripsFilter so that GET /api/trips/?registered=true returns only trips where the authenticated user is registered (and similarly for waitlisted=true).

    How¶

    Add two BooleanFilter fields with custom method= handlers to TripsFilter. Each method will filter using Exists() subqueries against TripRegistration / TripWaitlist, referencing request.user. This is the standard django-filters pattern for request-aware filtering.

    # In TripsFilter:
registered = filters.BooleanFilter(method='filter_registered')
waitlisted = filters.BooleanFilter(method='filter_waitlisted')

def filter_registered(self, queryset, name, value):
    user = self.request.user
    if not user or not user.is_authenticated:
        return queryset
    subquery = TripRegistration.objects.filter(trip=OuterRef('pk'), member=user)
    if value:
        return queryset.filter(Exists(subquery))
    return queryset.exclude(Exists(subquery))

    None. This is purely additive. Existing requests without the registered/waitlisted params behave identically.

    Impact¶

    • Website team: Eliminates fetching all 3,305 trips and filtering client-side. Expected load time drop from 17-30s to <1s.
    • Flutter app: Can use same filter for "My Trips" screens.

    Change 6: Add Cache-Control Headers to Static-ish Endpoints¶

    Priority: LOW Source: Performance Audit L1, L2, C1 Files: api/views/ (multiple view files)

    What¶

    Add Cache-Control headers to endpoints that serve rarely-changing data, using Django's built-in @cache_control decorator. This is the standard HTTP caching pattern used by every CDN-aware service.

    Endpoints and TTLs¶

    Endpoint TTL Rationale
    GET /api/logbookskills/ 10 min (600s) Skills catalog changes only when admin edits definitions
    GET /api/levels/ 30 min (1800s) Levels almost never change
    GET /api/meetingpoints/ 10 min (600s) Meeting points rarely change
    GET /api/sponsors/ 30 min (1800s) Sponsor list changes rarely
    GET /api/faqs/ 30 min (1800s) FAQ content changes rarely
    GET /api/choices/carbrand 60 min (3600s) Car brand list is essentially static

    How¶

    Use Django's @method_decorator(cache_control(...)) on the list action of each ViewSet:

    from django.utils.decorators import method_decorator
from django.views.decorators.cache import cache_control

class LogbookSkillViewSet(viewsets.ReadOnlyModelViewSet):
    @method_decorator(cache_control(public=True, max_age=600))
    def list(self, request, *args, **kwargs):
        return super().list(request, *args, **kwargs)

    For endpoints that include user-specific data (trips, members), we do NOT add caching headers — those must remain private / no-cache by default.

    Breaking Changes¶

    None. Cache-Control headers are advisory. Clients that don't implement HTTP caching are unaffected. Clients with Dio/OkHttp/Axios will automatically benefit.

    Impact¶

    • Reduces redundant fetches of static data (logbook skills fetched by 19 Flutter files independently).
    • Saves bandwidth on every cache hit (304 Not Modified or skip entirely).

    Implementation Order¶

    1. Change 1 (registered/waitlisted filter)     — highest impact, medium effort
2. Change 2 (enrich triphistory)                — highest impact, medium effort  
3. Change 3 (dateJoined filter)                 — quick win, 1 line
4. Change 5 (level__id filter)                  — quick win, 1 line
5. Change 4 (trip registration response)        — medium impact, medium effort
6. Change 6 (cache headers)                     — low effort, decorator on views

    What We Are NOT Doing (and Why)¶

    Suggestion from audits Decision Reason
    Composite endpoint GET /api/members/{id}/summary/ Not implementing Too complex, introduces a non-standard endpoint. The individual endpoints are fast enough when cached properly.
    Batch trip endpoint GET /api/trips/batch/?ids=1,2,3 Not implementing N+1 is a frontend issue (timeline provider). Frontend should use shared cache provider.
    GET /api/members/{id}/logbook-summary/ Not implementing Same as above — composite endpoints add maintenance burden.

    Notifications count endpoint Not implementing Current hard-coded limit of 20 is reasonable. Frontend can count isRead: false from that set.

    Change 7: Member Ordering (BACKENDTODO #3)¶

    Priority: HIGH File: api/views/views_member.py (lines 112–139, MemberViewSet)

    Problem¶

    GET /api/members/?ordering=-trip_count is silently ignored. The admin members table cannot offer column sorting.

    Current State¶

    MemberViewSet uses filterset_class = MembersFilter but has no filter_backends list declared, no OrderingFilter, and no ordering_fields. The queryset is hardcoded to .order_by('id').

    What to Change¶

    Add DRF's OrderingFilter to the viewset:

    from rest_framework import filters as drf_filters
from django_filters.rest_framework import DjangoFilterBackend

class MemberViewSet(...):
    queryset = Member.objects.all().order_by('id')
    filter_backends = [DjangoFilterBackend, drf_filters.OrderingFilter]
    filterset_class = MembersFilter
    ordering_fields = [
        'username', 'first_name', 'last_name',
        'trip_count', 'level__numeric_level',
        'date_joined', 'id'
    ]
    ordering = ['id']  # default — preserves current behavior

    Result¶

    GET /api/members/?ordering=-trip_count          → most active first
GET /api/members/?ordering=username             → alphabetical
GET /api/members/?ordering=-date_joined         → newest first
GET /api/members/?ordering=level__numeric_level → lowest level first
GET /api/members/?ordering=-trip_count,username  → multi-field supported

    Breaking Changes¶

    None. Default ordering remains id ascending. The ordering param is optional and ignored if not provided.

    Notes for Frontend¶

    • Param name is ordering (Django REST Framework standard)
    • Prefix with - for descending (e.g., ordering=-trip_count)
    • Invalid field names are silently ignored (returns default ordering)
    • Multi-field ordering supported: ordering=-trip_count,username
    • Field names use snake_case with double underscores for relations (e.g., level__numeric_level)

    Change 10: Last Visited Tracking (BACKENDTODO #7)¶

    Priority: HIGH Files: 6 files + 1 new migration

    This is the most complex item. It has four sub-tasks.

    Problem¶

    There is no record of when a member last accessed the API. Admins cannot identify inactive members or measure engagement. The existing last_user_activity field on NotificationSettings is insufficient (date-only, not in member responses, not filterable).

    10a. Add last_visited Field to Member Model¶

    File: api/models/models_member.py (after line 77, token_version)

    last_visited = models.DateTimeField(null=True, blank=True)

    Add database index (in Meta.indexes):

    models.Index(fields=['last_visited']),

    Create migration: python manage.py makemigrations api

    Default: null — existing members show as "Never" until they next authenticate. No data backfill.

    10b. Add LastVisitedMiddleware¶

    File: api/middleware.py (new class, append after MediaCorsMiddleware)

    from django.utils import timezone

class LastVisitedMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        response = self.get_response(request)
        if hasattr(request, 'user') and request.user.is_authenticated:
            now = timezone.now()
            last = request.user.last_visited
            if not last or (now - last).total_seconds() > 3600:
                type(request.user).objects.filter(
                    pk=request.user.pk
                ).update(last_visited=now)
        return response

    Register in settings: ad4x4/settings.py, add 'api.middleware.LastVisitedMiddleware' to MIDDLEWARE list after AuthenticationMiddleware.

    Design decisions: - Throttle: Updates at most once per hour per user (avoids a DB write on every request) - Uses .update(): Bypasses model .save() to avoid triggering signals or updating other auto-fields - Placed after AuthenticationMiddleware: Ensures request.user is populated

    10c. Add to Serializers¶

    File: api/serializers/serializers_member_base.py (line 36)

    Add last_visited to BasicMemberSerializer.Meta.fields:

    fields = ('id', 'username', 'first_name', 'last_name', 'phone', 'level',
          'trip_count', 'email', 'paid_member', 'last_visited')

    File: api/serializers/serializers_member.py (ProfileSerializer)

    Add last_visited to the detail serializer fields as well.

    Response field name: lastVisited (camelCase via CamelCase middleware). ISO 8601 datetime with timezone (e.g., "2026-03-30T14:22:00Z"). Nullable — returns null for never-visited members.

    10d. Add to Filters and Ordering¶

    File: api/filters.py (MembersFilter)

    File: api/views/views_member.py (MemberViewSet)

    'username', 'first_name', 'last_name',

    Breaking Changes¶

    Notes for Frontend¶

    • Response field: lastVisited (camelCase). ISO 8601 datetime or null.
    • Filter params: last_visited_after, last_visited_before (DateTimeFromToRangeFilter), last_visited__isnull (boolean)

    • Read-only: Not settable via PATCH — only updated by the middleware

    Change 11: Trip Search Enhancements (BACKENDTODO #8 + #10)¶

    Priority: HIGH File: api/views/views_trip.py (lines 899–978, TripSearch)

    Problem¶

    The trip search endpoint (GET /api/trips/search) silently ignores approvalStatus and ordering. It also lacks level_id support (#10) — the level param uses numericLevel values, while the list endpoint uses level__id.

    Current State¶

    TripSearch is a manually-coded ListAPIView that parses query params and builds a Q() filter. It supports: query, level, min_level, max_level, start_date_min/max, end_date_min/max, meeting_point (by ID), area. Results are always ordered by -start_time, id.

    What to Change¶

    11a. approval_status filter¶

    approval_status = request.query_params.get('approval_status', None)
if approval_status is not None:
    if approval_status not in ['P', 'A', 'R', 'C']:
        return Response(
            {'success': False, 'message': 'invalid_approval_status'},
            status=status.HTTP_400_BAD_REQUEST
        )
    filters &= Q(approval_status=approval_status)

    11b. ordering support¶

    ordering = request.query_params.get('ordering', '-start_time')
valid_orderings = {'start_time', '-start_time', 'title', '-title'}
if ordering not in valid_orderings:
    ordering = '-start_time'

# Then use in queryset:
queryset = Trip.objects.filter(filters).select_related(...).order_by(ordering, 'id')

    11c. level_id filter (resolves #10)¶

    level_id = request.query_params.get('level_id', None)
if level_id is not None:
    try:
        filters &= Q(level__id=int(level_id))
    except ValueError:
        return Response(
            {'success': False, 'message': 'invalid_level_id'},
            status=status.HTTP_400_BAD_REQUEST
        )

    Result¶

    # Filter by approval status
GET /api/trips/search?query=sand&approval_status=A   → only approved trips

# Sort by date
GET /api/trips/search?query=sweihan&ordering=start_time    → oldest first
GET /api/trips/search?query=sweihan&ordering=-start_time   → newest first (default)

# Filter by level database ID
GET /api/trips/search?query=sand&level_id=4   → only Intermediate trips (db id=4)

# All three combined
GET /api/trips/search?query=sand&approval_status=A&ordering=start_time&level_id=4

    Meeting Point Filter — Already Works¶

    Correction from frontend audit: The meeting_point param on the search endpoint already works by ID (see code lines 955–960). The frontend team's test returned 0 because meeting_point=117 combined with query=sweihan narrowed results to zero. The filter itself is functional. No change needed.

    Breaking Changes¶

    None. All new params are optional. Existing behavior is preserved: - Default ordering remains -start_time, id when no ordering param is provided - The existing level param (numericLevel) continues to work unchanged - level_id is a separate, additive param

    Notes for Frontend¶

    • approval_status values: P (Pending), A (Approved), R (Rejected), C (Cancelled). Invalid values return 400.
    • ordering param name: ordering (matches the list endpoint convention, NOT order)
    • Valid ordering values: start_time, -start_time, title, -title. Invalid values fall back to -start_time.
    • level_id vs level: Both work. level filters by numericLevel value (5, 10, 100, etc.). level_id filters by database ID (1–9). Use whichever is more convenient.
    • All params combinable: approval_status, ordering, level_id, and level can be combined with each other and with all existing params (query, area, meeting_point, dates).
