    Backend Enhancement Implementation Plan¶

    Date: 2026-04-01 Scope: Address legitimate findings from Flutter and Website team audits Principle: Industry-standard patterns, zero breaking changes

    Overview¶

    After cross-referencing all three frontend audit documents against the actual backend code and current API documentation, we identified 6 actionable items. All documentation issues from the live test audit were already fixed in prior sessions. The items below are code changes only.

    Change 1: Add registered and waitlisted Filters to Trips Endpoint¶

    Priority: HIGH Source: BACKENDTODO #1, Performance Audit T3 File: api/filters.py

    What¶

    Add two custom filter methods to TripsFilter so that GET /api/trips/?registered=true returns only trips where the authenticated user is registered (and similarly for waitlisted=true).

    How¶

    Add two BooleanFilter fields with custom method= handlers to TripsFilter. Each method will filter using Exists() subqueries against TripRegistration / TripWaitlist, referencing request.user. This is the standard django-filters pattern for request-aware filtering.

    # In TripsFilter:
registered = filters.BooleanFilter(method='filter_registered')
waitlisted = filters.BooleanFilter(method='filter_waitlisted')

def filter_registered(self, queryset, name, value):
    user = self.request.user
    if not user or not user.is_authenticated:
        return queryset
    subquery = TripRegistration.objects.filter(trip=OuterRef('pk'), member=user)
    if value:
        return queryset.filter(Exists(subquery))
    return queryset.exclude(Exists(subquery))

def filter_waitlisted(self, queryset, name, value):
    # Same pattern with TripWaitlist

    Breaking Changes¶

    None. This is purely additive. Existing requests without the registered/waitlisted params behave identically.

    Impact¶

    • Website team: Eliminates fetching all 3,305 trips and filtering client-side. Expected load time drop from 17-30s to <1s.
    • Flutter app: Can use same filter for "My Trips" screens.

    Change 2: Enrich Member Trip History Serializer¶

    Priority: HIGH Source: BACKENDTODO #1 (Option B) Files: api/serializers/serializers_trip.py, api/views/views_member.py

    What¶

    Add missing fields to MemberTripHistorySerializer so the website team doesn't need N+1 individual trip detail calls. Fields to add: image, meeting_point, registered_count, capacity, is_registered, is_waitlisted, allow_waitlist, approval_status.

    How¶

    Serializer changes — Extend MemberTripHistorySerializer to include the missing fields. Use the same patterns already established in ListTripSerializer:

    class MemberTripHistorySerializer(serializers.ModelSerializer):
    lead = ConciseMemberSerializer()
    level = LevelSerializer()
    meeting_point = MeetingPointSerializer()
    checked_in = serializers.BooleanField(source='member_checked_in')
    registered_count = serializers.IntegerField(read_only=True)
    is_registered = serializers.BooleanField(read_only=True)
    is_waitlisted = serializers.BooleanField(read_only=True)

    class Meta:
        model = Trip
        fields = (
            'id', 'title', 'description', 'start_time', 'end_time',
            'lead', 'level', 'checked_in', 'image', 'meeting_point',
            'registered_count', 'capacity', 'allow_waitlist',
            'approval_status', 'is_registered', 'is_waitlisted',
        )

    View changes — Update the MemberTripHistory queryset to annotate registered_count, is_registered, and is_waitlisted using Count() and Exists() subqueries (same pattern already used in the view for member_checked_in). Also add select_related('meeting_point') which is already in the base mixin.

    Breaking Changes¶

    None (additive only). All existing fields remain. New fields are added to the response. The camelCase renderer will automatically convert registered_count -> registeredCount, is_registered -> isRegistered, etc.

    Impact¶

    • Website team: Can use GET /api/members/{id}/triphistory as a drop-in replacement for fetching all trips. Response goes from 8 fields to 16 fields. Eliminates N+1 individual trip detail calls (each 3-13s).
    • Flutter app: Gets richer trip history data without extra calls.

    Change 3: Add date_joined Range Filter to Members¶

    Priority: MEDIUM Source: Live Test Audit item 21.2 File: api/filters.py

    What¶

    Add date_joined as a DateFromToRangeFilter to MembersFilter, enabling GET /api/members/?date_joined_after=2026-03-01&date_joined_before=2026-04-01.

    How¶

    class MembersFilter(filters.FilterSet):
    date_joined = DateFromToRangeFilter()

    class Meta:
        model = Member
        fields = {
            # ... existing fields ...
            'level__id': ['exact'],  # Also add this (Change 5)
        }

    This follows the exact same pattern as start_time in TripsFilter and verdict_date in UpgradeRequestsFilter.

    Breaking Changes¶

    None. Purely additive filter.

    Impact¶

    • Admin users can filter members by join date (e.g., "new members this month").
    • Both frontend teams can use this for admin dashboard features.

    Change 4: Return Updated Trip in Registration Responses¶

    Priority: MEDIUM Source: Performance Audit T3 Files: api/views/views_trip.py

    What¶

    After a successful register/unregister/waitlist action, include the updated trip object in the response alongside the existing success message. This follows the Stripe/Uber pattern — mutations return the updated resource.

    How¶

    After each successful registration action, serialize the trip using ListTripSerializer and include it in the response:

    # In RegisterForTrip.post(), after successful registration:
trip.refresh_from_db()
trip_data = ListTripSerializer(trip, context={'request': request}).data
return Response({
    'success': True, 
    'message': msg,
    'trip': trip_data
}, status=status.HTTP_200_OK)

    Apply the same pattern to CancelTripRegistration and RegisterForTripWaitlist.

    Queryset optimization: Before serializing, ensure the trip has proper prefetches:

    trip = Trip.objects.select_related('lead', 'level', 'meeting_point') \
    .prefetch_related('tripregistration_set__member', 'tripwaitlist_set__member') \
    .annotate(
        registered_count=Count('tripregistration'),
        waitlist_count=Count('tripwaitlist')
    ).get(pk=trip.pk)

    Breaking Changes¶

    None. The existing success and message fields are preserved. The new trip field is additive. Frontends that don't read trip are unaffected.

    Impact¶

    • Eliminates 3-5 follow-up GET calls per session after registration actions.
    • Both frontend teams get immediate UI updates without a second round-trip.

    Change 6: Add Cache-Control Headers to Static-ish Endpoints¶

    Priority: LOW Source: Performance Audit L1, L2, C1 Files: api/views/ (multiple view files)

    What¶

    Add Cache-Control headers to endpoints that serve rarely-changing data, using Django's built-in @cache_control decorator. This is the standard HTTP caching pattern used by every CDN-aware service.

    Endpoints and TTLs¶

    Endpoint TTL Rationale
    GET /api/logbookskills/ 10 min (600s) Skills catalog changes only when admin edits definitions
    GET /api/levels/ 30 min (1800s) Levels almost never change
    GET /api/meetingpoints/ 10 min (600s) Meeting points rarely change
    GET /api/sponsors/ 30 min (1800s) Sponsor list changes rarely
    GET /api/faqs/ 30 min (1800s) FAQ content changes rarely
    GET /api/choices/carbrand 60 min (3600s) Car brand list is essentially static

    How¶

    Use Django's @method_decorator(cache_control(...)) on the list action of each ViewSet:

    from django.utils.decorators import method_decorator
from django.views.decorators.cache import cache_control

class LogbookSkillViewSet(viewsets.ReadOnlyModelViewSet):
    @method_decorator(cache_control(public=True, max_age=600))
    def list(self, request, *args, **kwargs):
        return super().list(request, *args, **kwargs)

    For endpoints that include user-specific data (trips, members), we do NOT add caching headers — those must remain private / no-cache by default.

    Breaking Changes¶

    None. Cache-Control headers are advisory. Clients that don't implement HTTP caching are unaffected. Clients with Dio/OkHttp/Axios will automatically benefit.

    Impact¶

    • Reduces redundant fetches of static data (logbook skills fetched by 19 Flutter files independently).
    • Saves bandwidth on every cache hit (304 Not Modified or skip entirely).

    Implementation Order¶

    1. Change 1 (registered/waitlisted filter)     — highest impact, medium effort
2. Change 2 (enrich triphistory)                — highest impact, medium effort  
3. Change 3 (dateJoined filter)                 — quick win, 1 line
4. Change 5 (level__id filter)                  — quick win, 1 line
5. Change 4 (trip registration response)        — medium impact, medium effort
6. Change 6 (cache headers)                     — low effort, decorator on views

    What We Are NOT Doing (and Why)¶

    Suggestion from audits Decision Reason
    Composite endpoint GET /api/members/{id}/summary/ Not implementing Too complex, introduces a non-standard endpoint. The individual endpoints are fast enough when cached properly.
    Batch trip endpoint GET /api/trips/batch/?ids=1,2,3 Not implementing N+1 is a frontend issue (timeline provider). Frontend should use shared cache provider.
    GET /api/members/{id}/logbook-summary/ Not implementing Same as above — composite endpoints add maintenance burden.
    ?expand=skillOpportunities on trip detail Not implementing GraphQL-style field expansion is over-engineering for this project size.
    ETag/Last-Modified on all endpoints Not implementing now Cache-Control headers (Change 6) provide 80% of the benefit with 10% of the effort. ETags require per-endpoint last_modified_func implementations. Can revisit later.
    Notifications count endpoint Not implementing Current hard-coded limit of 20 is reasonable. Frontend can count isRead: false from that set.
    Trailing slash standardization Not implementing Already documented. Django's URL routing makes this non-trivial to change without breaking existing clients.
