    API Performance Audit Report¶

    Date: 2026-03-31 Scope: Full Flutter app — all API calls, caching, and data flow patterns Focus: Realistic backend changes to reduce API calls and improve performance

    Executive Summary¶

    After auditing all 331 Dart files across 16 features, I identified 12 high-impact findings that can significantly reduce API calls. The app already has a solid ApiCacheService (TTL-based, stale-while-revalidate), but many screens and providers bypass it entirely or duplicate calls that could be consolidated.

    The biggest wins come from: 1. Deduplicating the getLogbookSkills() catalog call — fetched independently by 19 files, often multiple times per session 2. Adding a backend composite/aggregate endpoint for Member Details (currently 6 parallel API calls) 3. Backend-side trip filtering to eliminate client-side re-filtering

    SECTION 1: TRIPS ENDPOINTS¶

    Finding T1: Trips List + Home Screen = Duplicate Trip Fetches¶

    Files: trips_provider.dart, upcoming_trips_provider.dart Impact: 2 independent API calls for the same data on app launch

    The home screen fetches upcoming trips via upcomingTripsProvider (pageSize: 100), and the trips list screen independently fetches via tripsProvider.loadTrips() (pageSize: 50). Both call GET /api/trips/ with nearly identical filters (approved, endTime > now).

    Recommendation (Backend): No backend change needed — this is already partially addressed by the shared upcomingTripsProvider. However, the tripsProvider in the trips list screen does NOT reuse this cache. Consider having the trips list screen consume the same cached provider and apply local filters, or add a backend ETag/Last-Modified header so the Dio client can skip re-downloading identical data.

    Recommendation (Quick backend win): Add Cache-Control: max-age=120 and ETag headers to GET /api/trips/. Dio can then send If-None-Match and get 304 Not Modified responses (~50 bytes) instead of the full JSON payload. This saves bandwidth even when data hasn't changed.

    Finding T2: Trip Detail Re-fetched on Every Navigation¶

    File: trips_list_screen.dart:459 Impact: 1 API call every time user taps a trip card

    ref.invalidate(tripDetailProvider(trip.id));
context.push('/trips/${trip.id}');

    The code explicitly invalidates the cached trip detail before navigating. This means every tap = fresh API call, even if the user just viewed that trip 10 seconds ago.

    Recommendation (Backend): Add ETag support to GET /api/trips/{id}/. The app can then always send the request but get a 304 response when nothing changed. This gives freshness guarantees without the full payload cost.

    Alternative (Frontend-only): Remove the invalidate() call and let the autoDispose + staleness check handle it. The trip detail provider already uses FutureProvider.autoDispose, so navigating away disposes it and navigating back fetches fresh.

    Finding T3: Trip Actions Trigger Full List Refresh¶

    File: trips_provider.dart:557-560 Impact: After register/unregister/waitlist, the entire trips list is refetched

    await _ref.read(tripsProvider.notifier).refresh(); // re-fetches ALL trips

    Every registration action calls refresh() which calls loadTrips() which fetches the full trips list again. This is heavy — up to 50 trips re-downloaded just because the user registered for one.

    Recommendation (Backend): Return the updated trip object in the registration/unregistration response body. Currently the POST /api/trips/{id}/register likely returns a simple success message. If it returned the updated trip (with new registeredCount, isRegistered, isFull, etc.), the frontend could update just that one trip in the list without re-fetching everything.

    Example response change:

    // Current: {"message": "Successfully registered"}
// Proposed: {"message": "Successfully registered", "trip": { ...full trip object... }}

    Finding T4: Member Details Screen — 6+ Waterfall API Calls¶

    File: member_details_screen.dart:56-82 Impact: 6 independent API calls PER member view, some with waterfalls

    _loadMemberData();           // 1. getMemberDetail()
_loadTripHistory(memberId);  // 2. getMemberTripHistory()
_loadTripStatistics(memberId); // 3. getMemberTripCounts() + 4. getLeadTripHistory(pageSize:1) + 5. getLeadTripHistory(pageSize:200) + 6. getMemberTripHistory(checkedIn:false)
_loadUpgradeHistory(memberId); // 7. getMemberUpgradeRequests()
_loadTripRequests(memberId);   // 8. getMemberTripRequests()
_loadMemberFeedback(memberId); // 9. getMemberFeedback()

    The statistics section alone does 4 sequential calls: getMemberTripCounts(), then getLeadTripHistory(pageSize:1) for total count, then getLeadTripHistory(pageSize:200) for per-level breakdown, then another getMemberTripHistory(checkedIn:false) for upcoming count.

    Recommendation (Backend — HIGH PRIORITY): Create a single composite endpoint: GET /api/members/{id}/summary/ that returns:

    {
  "profile": { ...member data... },
  "tripCounts": { "total": 45, "checkedIn": 40, "asLeader": 12, "upcoming": 3 },
  "leaderByLevel": { "1": 5, "2": 4, "3": 3 },
  "recentTrips": [ ...last 10 trips... ],
  "upgradeRequests": [ ...list... ],
  "tripRequests": [ ...list... ],
  "feedback": [ ...list... ]
}

    This reduces 9 API calls down to 1. This is a standard pattern (Google calls them "batch endpoints", Facebook uses "Graph API field expansion").

    SECTION 2: LOGBOOK ENDPOINTS¶

    Finding L1: getLogbookSkills() Called by 19 Files Independently (CRITICAL)¶

    Impact: The skills catalog (GET /api/logbookskills/) is fetched independently by 19 different files. Each file calls repository.getLogbookSkills(pageSize: 100-500) directly without going through the cache.

    Files making independent calls (bypassing cache): - trip_logbook_section_v2.dart — on every trip detail view - sign_off_bottom_sheet.dart — on every sign-off - bulk_sign_off_bottom_sheet.dart — on every bulk sign-off - trip_skill_opportunities_provider.dart — on every trip detail view - member_logbook_screen.dart — on every logbook view - logbook_entry_detail_screen.dart — on every entry detail - timeline_provider.dart — on every timeline view - trip_skill_planning_provider.dart — on every planning view - certificate_provider.dart — on every certificate view - level_certificates_provider.dart — on every level cert view - migration_request_provider.dart — on every migration view - admin_sign_off_skills_screen.dart — on every admin sign-off - admin_create_logbook_entry_screen.dart — on every admin entry creation - logbook_provider.dart (admin) — on every admin logbook view - admin_logbook_data_provider.dart — on every admin data view - logbook_enrichment_service.dart — on enrichment - level_configuration_service.dart — on level config

    Only 1 file uses the cache properly: logbook_skills_cache_provider.dart (via cachedLogbookSkillsProvider)

    Recommendation (Backend — EASY WIN): Add Cache-Control: public, max-age=600 (10 minutes) to GET /api/logbookskills/. The skills catalog changes only when an admin modifies skill definitions — this is extremely rare. A 10-minute cache-control header would let the HTTP client skip the request entirely.

    Recommendation (Frontend): Make all 19 files use cachedLogbookSkillsProvider instead of calling repository.getLogbookSkills() directly. This is a pure frontend fix but the backend cache header provides defense-in-depth.

    Finding L2: getUpgradeEligibility() Fetched Redundantly¶

    Files: upgrade_progress_provider.dart, trip_skill_opportunities_provider.dart, skills_matrix_v2_screen.dart, certificate_provider.dart, upgrade_certificate_provider.dart, trip_skill_planning_provider_v2.dart, create_upgrade_request_screen.dart Impact: 7 files call this endpoint independently, and the trip skill opportunities provider calls it ON EVERY TRIP DETAIL VIEW

    The upgrade eligibility data (GET /api/members/{id}/upgradeeligibility) changes only when a logbook entry is signed off. Yet it's fetched: - When viewing logbook home - When viewing any trip detail (skill opportunities) - When viewing skills matrix - When viewing certificates - When creating upgrade request

    Recommendation (Backend): Add Cache-Control: max-age=300 (5 minutes) to this endpoint. The data only changes after a logbook sign-off action, not on every page view.

    Recommendation (Frontend): Create a cachedUpgradeEligibilityProvider similar to cachedLogbookSkillsProvider, using ApiCacheService with CacheCategory.logbookProgress and a 5-minute TTL. All 7 consumers would read from this single provider.

    Finding L3: Trip Skill Opportunities = 2 API Calls Per Trip Detail View¶

    File: trip_skill_opportunities_provider.dart:76-115 Impact: Every trip detail view triggers getUpgradeEligibility() + getLogbookSkills()

    final eligibilityResponse = await repository.getUpgradeEligibility(user.id);
final skillsResponse = await repository.getLogbookSkills(pageSize: 200);

    Both are user-level data that doesn't change between trip views.

    Recommendation (Backend): Merge skill opportunities into the trip detail response. Add an optional ?expand=skillOpportunities parameter to GET /api/trips/{id}/. When present, the backend includes a skillOpportunities field with the user's relevant unmet requirements for that trip's level. This eliminates 2 extra API calls per trip view.

    Finding L4: Timeline Provider — N+1 Trip Detail Fetches¶

    File: timeline_provider.dart:137-157 Impact: Fetches each trip individually via getTripDetail(id) in parallel — up to 15+ calls

    final tripFutures = tripIds.map((id) async {
  final tripResponse = await repository.getTripDetail(id);
  return MapEntry(id, TripBasicInfo.fromJson(tripResponse));
});

    While it uses Future.wait (good), it's still N separate HTTP requests. For a user with 15 trips in their timeline, that's 15 concurrent API calls.

    Recommendation (Backend): Add a batch trip endpoint: GET /api/trips/batch/?ids=1,2,3,4,5 that returns multiple trips in one response. This is standard practice (Stripe, Slack, and GitHub all offer batch/bulk endpoints).

    Alternative: Add expand=trip to GET /api/members/{id}/logbookentries so the backend returns the trip object inline instead of just the trip ID. This eliminates the N+1 entirely.

    Finding L5: Logbook Progress = 3 Cached API Calls, But Still 3 Separate Calls¶

    File: logbook_progress_provider.dart:36-52 Impact: 3 parallel API calls (cached with 5-min TTL) every time logbook home is visited

    final results = await Future.wait([
  cacheService.getOrFetch(...getMemberLogbookSkills...),
  cacheService.getOrFetch(...getMemberLogbookEntries...),
  cacheService.getOrFetch(...getMemberTripCounts...),
]);

    Credit: This is well-implemented with caching. But 3 separate HTTP calls could still be 1.

    Recommendation (Backend): Create GET /api/members/{id}/logbook-summary/ returning:

    {
  "skills": { "results": [...], "count": 45 },
  "entries": { "results": [...], "count": 20 },
  "tripCounts": { "total": 30, "checkedIn": 25 }
}

    This collapses 3 calls into 1. With the existing 5-minute cache, this would mean 1 call every 5 minutes instead of 3.

    SECTION 3: CROSS-CUTTING CONCERNS¶

    Finding C1: No HTTP-Level Caching (ETags/Last-Modified)¶

    File: api_client.dart Impact: Every API call transfers the full response body, even when data hasn't changed

    The Dio client has no If-None-Match or If-Modified-Since interceptor. The app-level cache (ApiCacheService) helps, but when TTLs expire, the full payload is always re-downloaded.

    Recommendation (Backend): Add ETag and Last-Modified headers to all GET endpoints. Django REST Framework supports this via ConditionalGetMixin or middleware. This is a one-time backend change that benefits every endpoint:

    # Django middleware or mixin
from django.utils.cache import patch_cache_control
from django.views.decorators.http import condition

# On DRF ViewSet:
class TripViewSet(viewsets.ModelViewSet):
    @method_decorator(condition(last_modified_func=get_trips_last_modified))
    def list(self, request, *args, **kwargs):
        ...

    For the Flutter side, Dio supports 304 responses natively — no code change needed.

    Finding C2: Notifications Fetched Without Pagination¶

    File: notification_provider.dart:51 Impact: Fetches ALL notifications every time, no pagination or limit

    final response = await repository.getNotifications();

    No pageSize, no limit. For active users with hundreds of notifications, this transfers a large payload.

    Recommendation (Backend): 1. Add pageSize=50 default to the notifications endpoint 2. Add unread_only=true filter — the home badge only needs unread count, not all notification bodies 3. Better yet: Add a lightweight GET /api/notifications/count/ endpoint that returns just {"unread": 5} for the badge. The full list is only needed when the user opens the notifications screen.

    Finding C3: Admin Wizard Fetches ALL Trips (pageSize: 200 in a loop)¶

    File: admin_wizard_provider.dart:62-67 Impact: Fetches ALL trips in the database, 200 at a time, in a while loop

    const int pageSize = 200;
while (hasMorePages) {
  final response = await repository.getTrips(page: currentPage, pageSize: pageSize);
  ...
}

    For a club with hundreds of trips, this downloads everything to the client for client-side filtering.

    Recommendation (Backend): Move the admin wizard filtering entirely to the backend. The GET /api/trips/ endpoint already supports most of the filters (level_Id, meetingPoint_Area, startTimeAfter/Before, lead, ordering). The wizard should just send the final filter criteria as query params and let the backend return a single page of results. No pagination loop needed.

    Finding C4: getLogbookSkillReferences() Not Using Shared Cache¶

    File: skills_comparison_provider.dart:39-58 Impact: Skills comparison fetches skill references for 2 members independently, bypassing cache

    The cachedMemberSkillReferencesProvider exists in logbook_skills_cache_provider.dart but the comparison provider doesn't use it — it calls repository.getLogbookSkillReferences() directly.

    Recommendation (Backend): No backend change needed. Recommendation (Frontend): Use cachedMemberSkillReferencesProvider in the comparison provider.

    Finding C5: Member Details Creates New Repository Instance¶

    File: member_details_screen.dart:28 Impact: Bypasses the Riverpod-managed repository and cache

    final _repository = MainApiRepository(); // creates new instance

    This creates a fresh MainApiRepository (and therefore a fresh ApiClient with a fresh Dio instance) instead of using the Riverpod mainApiRepositoryProvider. This means: - No connection pooling with other screens - No shared interceptors state - No shared cache

    Recommendation (Backend): No change needed. Recommendation (Frontend): Use ref.read(mainApiRepositoryProvider) instead.

    SECTION 5: ESTIMATED IMPACT¶

    Current state (typical user session): - App launch: ~8-10 API calls (home screen widgets + trips + notifications) - View trip details: ~4 API calls (trip detail + logbook skills + upgrade eligibility + skill opportunities) - View logbook: ~4 API calls (progress stats + skills catalog + entries + trip counts) - View member profile: ~9 API calls (profile + trips + stats + leader history x2 + upgrades + requests + feedback) - Total for a 15-minute browsing session: ~40-60 API calls

    After implementing Priority 1-6: - App launch: ~5-6 API calls (deduplicated, cached) - View trip details: ~1-2 API calls (composite response, cached skills) - View logbook: ~1-2 API calls (composite endpoint, cached) - View member profile: ~1-2 API calls (summary endpoint) - Total for a 15-minute browsing session: ~12-20 API calls

    Estimated reduction: 50-70% fewer API calls

    SECTION 6: WHAT BIG TECH WOULD DO¶

    1. GraphQL or field expansion (Facebook/Meta): Instead of 9 REST calls for member details, one query that specifies exactly which fields/relations to include. Django Graphene or DRF's ?expand= pattern.

    2. ETag + Conditional GET (Google): Every GET response includes an ETag. Subsequent requests include If-None-Match, getting 304 Not Modified (zero body) when nothing changed. Django's ConditionalGetMiddleware does this automatically.

    3. Response includes mutation result (Stripe/Uber): After POST /register, the response includes the updated trip object. No need for a follow-up GET.

    4. Batch/composite endpoints (Google, Slack): GET /api/batch?endpoints=/trips/1,/trips/2,/trips/3 or purpose-built summary endpoints that join related data server-side.

    5. Cache-Control headers (Every CDN-aware service): Static-ish data (skill catalogs, level definitions, sponsors) gets Cache-Control: public, max-age=3600. Semi-static data gets max-age=300. The HTTP layer handles caching — no app code needed.

    6. Push-based invalidation (Firebase/Supabase): Instead of polling or TTL-based cache, the server pushes "trip 123 updated" events. The app already uses Firestore for chat — the same pattern could extend to trip state changes.
