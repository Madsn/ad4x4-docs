    #1 — Add server-side filtering for user's registered/waitlisted trips¶

    Priority: High Endpoint: GET /api/trips/ Reported: Session #13 (2026-03-30)

    Problem¶

    The My Trips portal page needs to show only trips where the logged-in user is registered or waitlisted. The API currently has no server-side filter for this. The frontend is forced to:

    1. Fetch ALL club trips (pageSize=100) — returns trips for every member, not just the requesting user
    2. Filter client-side using the isRegistered / isWaitlisted booleans on each trip object

    This causes:

    • ~17-30 second load times on mobile (95 KB payload, 3,305 total trips in the database, only ~17 belong to the user out of the 100 returned)
    • Incomplete data — the Past tab can only show the user's trips that happen to fall within the most recent 100 trips. Older registered trips are invisible.
    • Wasted bandwidth — 80-95% of the downloaded data is discarded

    Evidence (tested 2026-03-30 with user Elle, ID 21144)¶

    What we fetch Time Payload User's trips in response
    GET /api/trips/?startTimeBefore=2026-03-30&pageSize=100 ~1.5-17s 87-95 KB 17 out of 100 results
    GET /api/trips/?startTimeAfter=2026-03-30&pageSize=100 ~0.5s 7 KB 2 out of 5 results
    GET /api/members/21144/triphistory?pageSize=100 ~0.5s 4.6 KB 7 out of 7 (all user's)

    We confirmed that registered=true and isRegistered=true query params are silently ignored — the count does not change.

    Recommended backend changes¶

    Option A (preferred): Add query filters to GET /api/trips/

    Add support for these query parameters:

    GET /api/trips/?registered=true        -> only trips where the authenticated user is registered
GET /api/trips/?waitlisted=true        -> only trips where the authenticated user is waitlisted

    The data already exists — the API already computes isRegistered and isWaitlisted per-trip in the response. This just needs to be wired up as a queryset filter. This would reduce the Past tab response from 3,305 trips to ~17, and from 95 KB to ~15 KB.

    Option B (alternative): Enrich GET /api/members/{id}/triphistory

    The triphistory endpoint already returns only the user's trips and is fast (0.5s, 4.6 KB). However, it returns a slim object missing several fields the portal needs:

    Currently returned: id, title, description, startTime, endTime, lead, level, checkedIn

    Missing fields needed by the portal: - image (trip cover photo URL) - meetingPoint (name, lat/lon, link, area) - registeredCount / capacity (registration count vs capacity) - isRegistered / isWaitlisted (registration status badges) - allowWaitlist (UI logic for full-trip warnings) - approvalStatus (filter cancelled/rejected trips)

    Adding these fields to the triphistory response would make it a drop-in replacement.

    Why not fetch individual trip details?¶

    We tested GET /api/trips/{id}/ for each trip ID from triphistory. Each call takes 3-13 seconds. Seven sequential calls = ~90s. Even in parallel = ~21s. This is worse than the current approach.

    #2 — Trailing-slash inconsistency across endpoints¶

    Priority: Medium Reported: Session #13 (2026-03-30)

    Problem¶

    Some endpoints require a trailing slash, others return 404 when a slash is present. This causes silent failures when the proxy or client guesses wrong.

    Endpoint Without slash With slash Correct form
    /api/trips 403 (authenticated) 200 With slash
    /api/levels 301 redirect 200 With slash
    /api/vehicles 301 redirect 200 With slash
    /api/choices/carbrand 200 404 Without slash
    /api/auth/profile/notificationsettings 200 404 Without slash
    /api/members/request-deletion 200 404 Without slash

    Recommendation¶

    Standardise all endpoints to accept both forms. Django's APPEND_SLASH setting should handle this, but some endpoints (particularly under /api/choices/ and /api/auth/profile/notificationsettings) appear to bypass it.

    The frontend proxy currently works around this with redirect-following and 403/405 retry logic, but a consistent backend would be cleaner.

Both notificationIds and notification_ids work (both return 204). The error message says notification_ids, so that's the canonical internal name.     Priority: High Endpoint: GET /api/members/ Reported: Session #14 (2026-03-30)

    #7 — Track and expose "Last Visited" date for members¶

    Priority: High Endpoints affected: Member model, GET /api/members/, GET /api/members/search, GET /api/members/{id}/ Reported: Session #14 (2026-03-30)

    Problem¶

    There is currently no record of when a member last accessed the app or website. The admin panel has no way to identify inactive members, measure engagement, or distinguish members who signed up and never returned from regularly active ones.

    Requirements¶

    1. Record the timestamp¶

    Add a last_visited (or last_activity) DateTimeField to the member/profile model. Update it automatically on each authenticated request or on login. Recommended approaches:

    • Option A (lightweight): Update last_visited in the JWT token-obtain view (POST /api/token/). Only records logins, not ongoing activity. Simple but coarse.
    • Option B (recommended): Use Django middleware that updates last_visited on every authenticated request, throttled to once per hour (or configurable interval) to avoid a database write on every single API call. This captures actual usage, not just logins.
    # Example middleware (throttled to 1 update per hour)
class LastVisitedMiddleware:
    def __call__(self, request):
        response = self.get_response(request)
        if request.user.is_authenticated:
            now = timezone.now()
            if not request.user.last_visited or (now - request.user.last_visited).seconds > 3600:
                type(request.user).objects.filter(pk=request.user.pk).update(last_visited=now)
        return response

    For existing members who have never triggered this middleware, last_visited should default to null (unknown). The admin panel will display "Never" for these.

    2. Include in API responses¶

    Add lastVisited (camelCase, matching existing API conventions) to these response schemas:

    Endpoint Current fields Add

    #8 — Trip search endpoint: approvalStatus, ordering, and meetingPoint (by ID) are silently ignored¶

    Priority: High Endpoint: GET /api/trips/search Reported: Session #14 (2026-03-30)

    Problem¶

    The trip search endpoint (GET /api/trips/search) silently ignores three important query parameters. The frontend must fall back to the list endpoint (GET /api/trips/) for these features, requiring complex dual-endpoint switching logic (same pattern as members — see #6).

    GET /api/trips/search?query=sand&approvalStatus=A   -> count: 71 (results contain both A and C statuses)
GET /api/trips/search?query=sand&approvalStatus=P   -> count: 71 (identical)
GET /api/trips/search?query=sand&approvalStatus=C   -> count: 71 (identical)

    order — silently ignored¶

    GET /api/trips/search?query=sweihan&order=start_time_asc   -> first result: 2026-12-03

GET /api/trips/search?query=sweihan                        -> first result: 2026-12-03 (identical)

    All three return the same 466 results in the same order. The order parameter has no effect.

    meetingPoint (by ID) — silently ignored or broken¶

    GET /api/trips/search?query=sweihan&meetingPoint=117  -> count: 0 (expected: non-zero, as 475 trips use meetingPoint=117 on the list endpoint)
GET /api/trips/search?query=sweihan                   -> count: 466 (without filter)

    Parameter Status Example
