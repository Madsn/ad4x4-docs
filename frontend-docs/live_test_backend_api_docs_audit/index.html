    Backend API Documentation Audit¶

    Purpose: This report documents every discrepancy found between the backend API documentation (ad4x4-backend/docs/) and the actual live API behaviour. Each item tells the backend team exactly what to fix in their docs.

    Tested by: Frontend AI developer (Session #14) Date: 2026-03-30 API base: https://ap.ad4x4.com Test user: hani amj (ID 10613, Board member, admin permissions) Method: Every endpoint was tested with curl + Bearer JWT token

    Scope limitation: All tests were performed with a Board member (admin) account that has full permissions. This means: - Covered: Endpoint URLs, trailing slashes, HTTP methods, response field names/structures, filter parameters, pagination, query validation — all verified. - NOT covered: Permission-gated behaviour. Endpoints that restrict access or hide fields based on user level were not tested with a lower-permission account. Examples: - GET /api/members/ may hide phone/email fields for users without VIEW_CONTACT_INFO permission. - GET /api/members/search requires SEARCH_MEMBERS permission — a Newbie may get 403. - GET /api/upgraderequests/ requires VIEW_UPGRADE_REQ permission. - Trip registration vehicle_required enforcement may differ for staff vs regular users. - Self-only restrictions (e.g., editing own profile vs another member's) not tested. - Recommendation: When building features that use permission-restricted endpoints, test with a regular member account (e.g., Newbie or Intermediate level) to verify the actual permission behaviour.

    Critical Items (backend team must fix)¶

    1. vehicles.md — Wrong endpoint name: says /api/choices/carbrands/, reality is /api/choices/carbrand
    2. auth-profiles.md — Wrong field names for change-password: says old_password, password, password2, reality is oldPassword, password, passwordConfirm
    3. members.md — Documents car_brand and car_year as working filters, but they are silently ignored
    4. logbook.md — Documents endpoint as /api/logbookskills (no slash), but that returns 301; only /api/logbookskills/ (with slash) returns 200
    5. global-settings.md — Documents GET /api/settings/, but endpoint returns 404 (may not be exposed to API)
    6. trip-search.md — Documents meeting_point parameter but doesn't clarify it's a text filter; using an integer ID returns 0 results and a text name causes timeout
    7. members.md — Missing documentation for email filter behaviour (requires exact match or __icontains suffix)
    8. sponsorships.md — Wrong endpoint name: says /api/sponsorships/, reality is /api/sponsors/ (plain array, not paginated)
    9. club-news.md — Wrong response fields: docs say published and author, reality is submitDate (no author field). Actual fields: id, title, content, submitDate, status, levels, image
    10. members.md — level_Id filter is silently ignored on the list endpoint (level_Id=9, level__id=9, levelId=9 all return full count 10,610)
    11. members.md — dateJoined range filters (dateJoined_Gte, date_joined__gte) are silently ignored
    12. lead-trip-history.md — Docs show URL without trip- prefix (just lead-trip-history), but reality confirms the correct URL is /api/trips/lead-trip-history (no trailing slash; slash returns 404)
    13. upgrade-requests.md — Minor: response field names use camelCase (finalApprover, applicantStr, verdictDate) not snake_case as some docs imply
    14. trips.md — Trip approve endpoint: POST /api/trips/{id}/approve works (no slash). With slash → 404. Not documented which HTTP methods are supported.

→ {
    "clubNewsEnabledEmail": true,
    "clubNewsEnabledAppPush": true,
    "newTripAlertsEnabledEmail": true,
    "newTripAlertsEnabledAppPush": true,

    "tripChatEnabledAppPush": true,
    "lastUserActivity": "2026-03-31",
    "member": 10613,
    "newTripAlertsLevelFilter": []
  }

    Key findings: - The lastUserActivity field returns a date (not datetime) — "2026-03-31" format. - It is NOT included in member list or detail responses (GET /api/members/, GET /api/members/{id}/). - It is only accessible via the notification settings endpoint (which is per-user, not admin-queryable). - For BACKENDTODO #7 to work fully, lastUserActivity (or a lastVisited field) needs to be: 1. Added to the member list/detail response 2. Made filterable (for admin queries like "inactive 90+ days") 3. Made orderable (for sorting by last activity)

    The existence of this field suggests the backend already tracks user activity at some level, which means implementing #7 may be simpler than creating it from scratch.
