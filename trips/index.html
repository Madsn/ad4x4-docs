    Trips¶

    This document outlines the API endpoints for managing trips, including creating, viewing, registering, and managing participants.

    Trip Lifecycle¶

    1. Creation: A trip is created via a POST request. Depending on the creator's permissions, it may be automatically approved or require manual approval.
    2. Approval: Trips requiring approval must be approved by a user with the appropriate permissions before they become visible to regular members.
    3. Registration: Once a trip is approved, members can register for it until the cut_off time is reached or the capacity is filled.
    4. Waitlist: If a trip is full and allow_waitlist is enabled, members can join the waitlist. They can optionally specify a vehicle when joining. The vehicle is stored and used when moved to registered. Members will be automatically moved to the registered list if a spot becomes available.
    5. Check-in/Check-out: The trip lead or a deputy can check members in and out of the trip.

    Endpoints¶

    List and Retrieve Trips¶

    • GET /api/trips/

      • Retrieves a list of all approved trips.

      • Query Parameters:

        Parameter Type Description
        lead integer Filter by trip lead (member ID)
        deputy_leads integer Filter by deputy lead (member ID)
        meeting_point integer Filter by meeting point ID
        meeting_point__area string Filter by meeting point area code (e.g., DXB, AUH)
        level__id integer Filter by level ID
        level__numeric_level integer Filter by exact numeric level
        level__numeric_level__range string Filter by numeric level range (e.g., 100,500)
        approval_status string Filter by approval status (A=Approved, P=Pending, R=Rejected, C=Cancelled)
        start_time_after datetime Filter trips starting after this date
        start_time_before datetime Filter trips starting before this date
        end_time_after datetime Filter trips ending after this date
        end_time_before datetime Filter trips ending before this date
        registered boolean Filter to only trips where the authenticated user is registered (true) or not registered (false). Requires authentication.
        waitlisted boolean Filter to only trips where the authenticated user is on the waitlist (true) or not waitlisted (false). Requires authentication.
        page integer Page number (default: 1)
        page_size integer Number of results per page (default: 20)

      Note: Both camelCase and snake_case parameter names are accepted (e.g., approvalStatus and approval_status are equivalent, startTimeAfter and start_time_after are equivalent).

    • GET /api/trips/{id}/

      • Retrieves the full details of a single trip, including registered members and the waitlist.
      • Contact Info: The trip lead and deputy leads' contact info (email, phone) is always visible to authenticated users. Other members' contact info requires VIEW_CONTACT_INFO permission.
      • Overlap flags: Each registered[] row includes hasOverlap and overlappingTrips so the trip lead can spot members who are already booked on another approved or pending trip. The overlap data uses the same rules as the write-side trip overlap warnings.

    Create a Trip¶

    • POST /api/trips

      Note: The create endpoint does NOT use a trailing slash. This differs from the list/retrieve endpoints which are router-registered.

      • Creates a new trip. The approval_status will be set based on the user's permissions.
      • Request Body: See the CreateTripSerializer for details. Key fields include:
        • lead (Member ID)
        • level (Level ID)
        • title
        • start_time
        • end_time
        • cut_off
        • capacity
        • meeting_point (MeetingPoint ID)

      Note: While the serializer and database use snake_case for field names (e.g., start_time), the API expects camelCase in the request body (e.g., startTime).

      • Overlap warnings: If the chosen lead already has an approved or pending trip that overlaps the new trip, either as a registered member or primary lead, the API returns 409 Conflict and does not create the trip. Resubmit the same request with confirmOverlap: true to create it anyway. See Trip Overlap Warnings.

    Update a Trip¶

    • PUT or PATCH /api/trips/{id}

      Note: The update/delete endpoint does NOT use a trailing slash.

      • Updates an existing trip.
      • Restrictions:
        • A configurable cutoff time (in minutes before the trip's start_time) determines when editing is restricted. The default is 0 minutes, meaning editing is disabled once the trip starts.
        • Before the cutoff time: The trip's lead and users with the EDIT_TRIPS permission can edit the trip.
        • After the cutoff time: Only users with the EDIT_TRIPS permission can edit the trip.
        • Superusers are exempt from all restrictions.
      • Request Body: See the UpdateTripSerializer for a list of editable fields.

    Delete a Trip¶

    • DELETE /api/trips/{id}
      • Deletes a trip. This is a soft-delete, meaning the trip's approval_status is set to CANCELED.
      • Restrictions:
        • A configurable cutoff time (in minutes before the trip's start_time) determines when deleting is restricted. The default is 0 minutes, meaning deleting is disabled once the trip starts.
        • Before the cutoff time: The trip's lead and users with the DELETE_TRIPS permission can delete the trip.
        • After the cutoff time: Only users with the DELETE_TRIPS permission can delete the trip.
        • Superusers are exempt from all restrictions.

    Approve a Trip¶

    • POST /api/trips/{id}/approve

      Note: This endpoint does NOT use a trailing slash.

      • Approves a trip that is pending approval. Requires the APPROVE_TRIP permission.
      • Side effects on the approver:
        1. The approver is added to the trip's deputy_leads.
        2. The approver is automatically registered as a participant (via add_to_registered()) using the provided vehicle_id, or their primary vehicle if none is given.
        3. The approver's TripRegistration.checked_in is set to true immediately (so they don't need to check themselves in on the day).
        4. send_trip_approval_notification and send_trip_notification are dispatched to Huey.
      • Request Body: {"vehicle_id": <vehicle_id>} (optional — defaults to the approver's primary vehicle)

    Decline a Trip¶

    • POST /api/trips/{id}/decline

      Note: This endpoint does NOT use a trailing slash.

      • Declines a trip that is pending approval. Requires the APPROVE_TRIP permission.
      • Sets the trip's approval_status to REJECTED.
      • Triggers a trip approval notification.
      • Request Body: None required.
      • Success Response: {"success": true, "message": "trip_rejected"}

    Registration¶

    Note: All registration endpoints below do NOT use trailing slashes.

    • POST /api/trips/{id}/register
      • Registers the authenticated user for the trip.
      • Request Body: {"vehicle_id": <vehicle_id>}. Add confirmOverlap: true only when confirming an overlap warning.
      • Required for regular users: Users must have at least one vehicle registered. Staff users (with EDIT_TRIP_REGISTRATIONS permission) can omit - defaults to their primary vehicle.
      • Returns vehicle_required error if no vehicle is provided.
      • Returns vehicle_not_found error if the vehicle doesn't exist or doesn't belong to the user.
      • Additional validations: trip_not_approved, level_insufficient, trip_cutoff_exceeded, trip_already_registered, trip_full.
      • If the authenticated user already has an approved or pending overlapping trip as a registered member or primary lead, returns 409 Conflict with trip_overlap_warning and does not register. Resubmit with confirmOverlap: true to register anyway.
      • Success Response: Returns the updated trip object alongside the success message: json {"success": true, "message": "trip_registered", "trip": { ...full trip object... }} The trip field contains the complete trip object (same schema as GET /api/trips/{id}/ list response) with updated registeredCount, isRegistered, isWaitlisted, etc. This eliminates the need for a follow-up GET request.
    • POST /api/trips/{id}/waitlist
      • Adds the authenticated user to the waitlist if the trip is full.
      • Request Body: {"vehicle_id": <vehicle_id>} (optional - defaults to user's primary vehicle). Add confirmOverlap: true only when confirming an overlap warning.
      • Returns trip_waitlist_disabled_for_this_trip if waitlist is not enabled.
      • Applies the same trip-overlap warning guard as registration.
      • Success Response: {"success": true, "message": "trip_waitlisted", "trip": { ...full trip object... }}
    • POST /api/trips/{id}/unregister
      • Cancels the authenticated user's registration for the trip (from either the registered list or the waitlist).
      • Trip leads cannot unregister themselves (trip_lead_cannot_unregister).
      • Success Response: {"success": true, "message": "trip_registration_cancelled", "trip": { ...full trip object... }}

    Trip Overlap Warnings¶

    The create, register, and waitlist endpoints use a two-step guard for overlapping trips:

    • Checked endpoints: POST /api/trips, POST /api/trips/{id}/register, POST /api/trips/{id}/waitlist.
    • Conflict scope: existing trips with approval_status APPROVED or PENDING where the member is registered or is the primary lead.
    • Not counted as conflicts: canceled/rejected trips, waitlist-only memberships, and deputy-lead roles.
    • Time rule: overlaps are detected when existing.startTime < new.endTime and existing.endTime > new.startTime. Trips that touch exactly at the boundary do not conflict.
    • Confirmation: retry the same request with confirmOverlap: true to proceed. On confirmed success, the response keeps the normal success fields and includes the same warnings array.

    Unconfirmed overlap response:

    {
  "success": false,
  "message": "trip_overlap_warning",
  "warnings": [
    {
      "code": "trip_overlap",
      "conflicts": [
        {
          "id": 123,
          "title": "Existing Trip",
          "startTime": "2026-05-20T06:00:00Z",
          "endTime": "2026-05-20T12:00:00Z",
          "role": "registered"
        }
      ]
    }
  ]
}

    Trip Detail Overlap Flags¶

    When retrieving trip details, each registration row can include overlap metadata for the trip lead:

    {
  "registered": [
    {
      "id": 1,
      "member": {
        "id": 123,
        "username": "johndoe",
        "firstName": "John",
        "lastName": "Doe"
      },
      "vehicle": {
        "id": 456,
        "name": "My Land Cruiser",
        "brand": "TO",
        "brandDisplay": "Toyota",
        "model": "Land Cruiser",
        "year": 2020,
        "color": "White",
        "isPrimary": true
      },
      "checkedIn": false,
      "registrationDate": "2026-03-05T10:00:00",
      "hasOverlap": true,
      "overlappingTrips": [
        {
          "id": 789,
          "title": "Friday Beach Run",
          "startTime": "2026-05-15T08:00:00",
          "endTime": "2026-05-15T16:00:00",
          "role": "registered"
        }
      ]
    }
  ]
}
    • hasOverlap is true when the member has at least one overlapping approved or pending trip.
    • overlappingTrips lists the conflicting trips in chronological order.
    • role indicates whether the conflict came from the member being registered or lead on the conflicting trip.

    Force Registration¶

    • POST /api/trips/{id}/forceregister

      Note: This endpoint does NOT use a trailing slash.

      • Force-registers a member for a trip, bypassing level requirements and capacity checks. Requires BYPASS_LEVEL_REQ permission.
      • Request Body: json { "member": 123, "vehicle_id": 45 }
      • vehicle_id is optional; defaults to the member's primary vehicle.

    Participant Management¶

    Note: All participant management endpoints below do NOT use trailing slashes.

    • POST /api/trips/{id}/addfromwaitlist
      • Manually moves a member from the waitlist to the registered list. Requires EDIT_TRIP_REGISTRATIONS permission or being the trip lead/deputy.
      • Request Body: {"member": <member_id>}
      • Success Response: {"success": true, "message": "member_moved_from_waitlist_to_registered"}
    • POST /api/trips/{id}/removemember
      • Removes a member from the trip (from either the registered list or the waitlist). Requires EDIT_TRIP_REGISTRATIONS permission or being the trip lead/deputy.
      • Request Body: {"member": <member_id>, "reason": "..."}
      • Success Response: {"success": true, "message": "user_removed_from_trip_registered"} or "user_removed_from_trip_waitlist"
    • POST /api/trips/{id}/checkin
      • Checks in one or more members to the trip. Requires EDIT_TRIP_REGISTRATIONS permission or being the trip lead/deputy.
      • Request Body: {"members": [<member_id_1>, <member_id_2>]}
    • POST /api/trips/{id}/checkout
      • Checks out one or more members from the trip. Requires EDIT_TRIP_REGISTRATIONS permission or being the trip lead/deputy.
      • Request Body: {"members": [<member_id_1>, <member_id_2>]}

    Important: The checkin/checkout endpoints use a different response format from other trip endpoints:

    json { "succeeded": [1, 2, 3], "failed": [ {"member": 4, "error": "Member is not registered for this trip"} ] }

    This is NOT wrapped in the standard {"success": ..., "message": ...} format.

    Trip Comments¶

    • GET /api/trips/{id}/comments

      Note: This endpoint does NOT use a trailing slash.

      • Retrieves comments for a specific trip, ordered by most recent first.
      • Authentication: Required.
      • Supports ordering via ordering query parameter (field: created).

      Response item fields: comment, member (object with id, username, displayName), trip, created

    • GET/POST/DELETE /api/tripcomments/

      This is the router-registered ViewSet for trip comments (uses trailing slash).

      • GET /api/tripcomments/ - List all comments. Filter by trip or member query params.
      • POST /api/tripcomments/ - Create a comment. Body: {"comment": "...", "trip": <trip_id>}. The member field is automatically set to the authenticated user.
      • DELETE /api/tripcomments/{id}/ - Delete a comment. Requires ownership or DELETE_TRIP_COMMENTS permission.

    Trip Reports (per trip)¶

    • GET /api/trips/{id}/tripreports

      Note: This endpoint does NOT use a trailing slash.

      • Retrieves trip reports for a specific trip, ordered by ID.
      • Authentication: Required.

      See Trip Reports for the full CRUD Trip Reports API.

    Export Registrants¶

    • GET /api/trips/{id}/exportregistrants

      Note: This endpoint does NOT use a trailing slash.

      • Exports the trip's registered members as a CSV file.
      • Authentication: Required. Authorization: trip lead, deputy lead, or a group with EDIT_TRIP_REGISTRATIONS permission for the trip's level (superusers always allowed).
      • Response: CSV file with Content-Disposition: attachment; filename="trip_{id}_registrants.csv"
      • CSV Columns: username, name, level, one column per active level for trip counts (e.g., trips_newbie, trips_intermediate), car_brand_model_color, phone, city

    View Logbooks¶

    • GET /api/trips/{id}/viewlogbooks

      Note: This endpoint does NOT use a trailing slash.

      • Returns a list of checked-in members for the trip along with their logbook entry (if one exists).
      • Authentication: Required.
      • Each item in the response contains a member object and a logbook_entry object (or null).

      See Digital Logbook for the full logbook API.

    Member-Specific Trip Endpoints¶

    These endpoints provide trip information tailored to a specific member.

    Note: All member-specific endpoints below do NOT use trailing slashes.

    Member Trip Counts¶

    • GET /api/members/{id}/tripcounts
      • Retrieves a summary of a member's trips, grouped by trip level.
      • Includes trips where the member was:
        • Registered and checked in (as participant)
        • Lead of the trip
        • Deputy lead of the trip
      • Query Parameters: since and until are optional ISO dates (YYYY-MM-DD) that filter by start_time using a half-open window: since is inclusive and until is exclusive.
      • count keeps the legacy trip-total semantics, including lead and deputy-lead trips.
      • registeredCount and attendanceRate only include completed trips that have already ended, and a level can still appear with count at 0 when the member registered but did not check in.

    Member Trip History¶

    • GET /api/members/{id}/triphistory
      • Retrieves a paginated history of a member's trips.
      • Query Parameters: checked_in (boolean, filter for checked-in trips only), start_time (datetime filter).
      • Permissions: Own history always viewable. Viewing another member's history requires VIEW_MEMBER_TRIP_HISTORY permission or superuser.

      • Note: This endpoint only includes trips with an APPROVED status.

    See also the Digital Logbook page for information on how to manage logbook entries for a trip.
