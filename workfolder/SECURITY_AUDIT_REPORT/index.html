    AD4x4 Security Audit Report¶

    Project: AD4x4 Django REST API Audit Date: 2026-03-24 Auditor: Automated + Manual Code Review Scope: Full codebase, dependencies, configuration, infrastructure Codebase Size: 13,177 lines of Python across 80+ files Django Version: 5.1 | DRF: 3.17.1 | Python: 3.13

    Executive Summary¶

    This audit identified 42 security findings across the AD4x4 Django application:

    Severity Count Description
    CRITICAL 6 Immediate exploitation risk, could lead to full system compromise
    HIGH 17 Significant vulnerabilities requiring urgent remediation
    MEDIUM 13 Notable weaknesses requiring planned remediation
    LOW 6 Minor issues and hardening recommendations

    C2: JWT Tokens Have No Expiration (Permanent Authentication Tokens)¶

    Field Value
    Severity CRITICAL
    CVSS 9.1
    CWE CWE-613 (Insufficient Session Expiration)
    Location api/util.py:38-47
    OWASP A07:2021 - Identification and Authentication Failures

    Evidence (api/util.py lines 38-47):

    class AuthJWTManager(AbstractAuthTokenManager):
    def provide_token(self, user: 'AbstractBaseUser') -> AuthToken:
        encoded_jwt = jwt.encode(
            {"user_id": user.pk},      # <-- NO "exp" claim
            settings.SECRET_KEY,
            algorithm=JWTAuthentication.ALGORITHM,
        )
        return AuthToken(encoded_jwt)

    The provide_token() method generates JWTs with only {"user_id": <pk>} and no exp (expiration) claim. While SIMPLE_JWT settings configure ACCESS_TOKEN_LIFETIME = 1 day, the custom AuthJWTManager bypasses SimpleJWT entirely by using raw jwt.encode().

    The JWTAuthentication.authenticate() method (line 70-96) only catches jwt.ExpiredSignatureError but never encounters it because no exp is set. These tokens are valid forever.

    Additionally, revoke_token() (line 49-51) raises AuthTokenNotRevoked(), meaning tokens cannot be invalidated even when a user changes their password or is deactivated.

    Impact: If any JWT token is leaked (logs, browser storage, network intercept), it provides permanent access to the associated account with no way to revoke it.

    Remediation:

    def provide_token(self, user: 'AbstractBaseUser') -> AuthToken:
    from datetime import datetime, timedelta, timezone
    encoded_jwt = jwt.encode(
        {
            "user_id": user.pk,
            "exp": datetime.now(timezone.utc) + timedelta(hours=1),
            "iat": datetime.now(timezone.utc),
        },
        settings.SECRET_KEY,
        algorithm=JWTAuthentication.ALGORITHM,
    )
    return AuthToken(encoded_jwt)

    Also implement token revocation via a blocklist or token versioning.

    C3: Path Traversal Vulnerability in Media File Serving¶

    Field Value
    Severity CRITICAL
    CVSS 8.6
    CWE CWE-22 (Path Traversal)
    Location api/views/views_media.py:10-15
    OWASP A01:2021 - Broken Access Control

    Evidence (api/views/views_media.py):

    @api_view(['GET'])
def serve_media(request, path):
    full_path = os.path.join(settings.MEDIA_ROOT, path)
    if os.path.exists(full_path) and os.path.isfile(full_path):
        response = FileResponse(open(full_path, 'rb'), content_type='application/octet-stream')
        response['Access-Control-Allow-Origin'] = '*'
        return response

    Proof of Concept (tested in sandbox):

    Input: ../../../etc/passwd
  os.path.join result: /app/uploads/../../../etc/passwd
  Normalized: /etc/passwd
  Stays within MEDIA_ROOT: False  <-- ESCAPES!

Input: avatars/../../../etc/passwd
  os.path.join result: /app/uploads/avatars/../../../etc/passwd
  Normalized: /etc/passwd
  Stays within MEDIA_ROOT: False  <-- ESCAPES!

    The path parameter from the URL uploads/<path:path> is passed directly to os.path.join() without any validation that the resulting path stays within MEDIA_ROOT. Django's <path:path> URL converter accepts ../ sequences.

    Impact: An attacker can read any file on the server that the application user has read access to, including: - /app/config/*.json (Firebase service account keys) - /etc/passwd (system user enumeration) - Application source code - Environment variables from /proc/self/environ

    Remediation:

    import os
from django.http import FileResponse, HttpResponseNotFound, HttpResponseForbidden

@api_view(['GET'])
def serve_media(request, path):
    full_path = os.path.realpath(os.path.join(settings.MEDIA_ROOT, path))
    media_root = os.path.realpath(settings.MEDIA_ROOT)

    # Prevent path traversal
    if not full_path.startswith(media_root + os.sep):
        return HttpResponseForbidden('Access denied')

    if os.path.exists(full_path) and os.path.isfile(full_path):
        response = FileResponse(open(full_path, 'rb'))
        return response
    return HttpResponseNotFound('File not found')

    C4: CORS Allows All Origins¶

    Field Value
    Severity CRITICAL
    CVSS 8.1
    CWE CWE-942 (Permissive Cross-domain Policy)
    Location ad4x4/settings.py:406
    OWASP A05:2021 - Security Misconfiguration

    Evidence:

    CORS_ORIGIN_ALLOW_ALL = True

    This allows any website on the internet to make authenticated cross-origin requests to the API. Combined with SessionAuthentication being enabled, an attacker can create a malicious webpage that makes API requests using a victim's session cookies.

    C5: Sensitive Data Logged in Plaintext (Passwords in Logs)¶

    Field Value
    Severity CRITICAL
    CVSS 7.5
    CWE CWE-532 (Insertion of Sensitive Information into Log File)
    Location api/views/views_auth.py:29
    OWASP A09:2021 - Security Logging and Monitoring Failures

    Evidence:

    # views_auth.py:29
logger.warning(f'Invalid change password request: {serializer.errors}, {request.data}')

    When a password change request fails validation, request.data is logged verbatim. This dict contains old_password, password, and potentially password2 in plaintext. These values are written to: - Console output - Log files on disk - Sentry (if error propagates) - Admin email (via mail_admins handler)

    Additional instances of request.data being logged: - views_trip.py:61 - trip creation data - views_trip.py:131 - trip edit data - views_upgraderequest.py:41 - upgrade request data - views_upgraderequest.py:180 - upgrade request comment data

    Remediation:

    # Never log request.data directly - sanitize first
logger.warning(f'Invalid change password request: {serializer.errors}')
# Or create a sanitize function:
def sanitize_log_data(data):
    sensitive_keys = {'password', 'old_password', 'password1', 'password2', 'token'}
    return {k: '***' if k in sensitive_keys else v for k, v in data.items()}

    C6: Deactivated/Deleted Users Can Still Authenticate via JWT¶

    Field Value
    Severity CRITICAL
    CVSS 8.8
    CWE CWE-863 (Incorrect Authorization)
    Location api/util.py:92-108
    OWASP A07:2021 - Identification and Authentication Failures

    Evidence (api/util.py lines 98-103):

    user_class = get_user_model()
try:
    user = user_class.objects.get(pk=user_id)   # <-- No is_active check!
except user_class.DoesNotExist:
    msg = _('User not found.')
    raise AuthenticationFailed(msg) from None

    The custom JWTAuthentication.authenticate() method retrieves the user by primary key but never checks user.is_active. Combined with: - The anonymize_data() method in models_member.py which sets is_active = False but does not invalidate tokens - The AccountDeletionRequest flow which deactivates accounts after 3 days - The fact that tokens never expire (C2)

    This means a deactivated, suspended, or deleted user's existing JWT token continues to work indefinitely.

    Impact: Users who have been banned, suspended, or who requested account deletion can continue accessing all API endpoints using their old tokens.

    Remediation:

    user = user_class.objects.get(pk=user_id)
if not user.is_active:
    msg = _('User account is disabled.')
    raise AuthenticationFailed(msg) from None

    H6: Mass Assignment Risk via exclude Pattern in Serializers¶

    Location api/serializers/serializers_member.py
    CWE CWE-915 (Improperly Controlled Modification of Dynamically-Determined Object Attributes)

    Three serializers use exclude instead of explicit fields:

    class EditMemberSerializer(serializers.ModelSerializer):
    class Meta:
        model = Member
        exclude = ('password','is_staff','is_superuser','is_active',
                   'date_joined','last_login')

    The level, trip_count, paid_member, and title fields are not excluded, meaning: - level (ReadOnlyField) is safe due to serializer field override - trip_count — NOT protected, user could manipulate their trip count - paid_member — NOT protected, user could set themselves as paid - title — NOT protected

    If any new sensitive field is added to the Member model in the future, it becomes automatically writable via the API.

    Remediation: Switch all serializers from exclude to explicit fields lists.

    H7: No Rate Limiting on Authentication Endpoints (Django Level)¶

    Location ad4x4/settings.py - REST_FRAMEWORK
    CWE CWE-307 (Improper Restriction of Excessive Authentication Attempts)

    There are no DEFAULT_THROTTLE_CLASSES or DEFAULT_THROTTLE_RATES configured in DRF settings. While Nginx provides some rate limiting (200 req/min on /api/, 4 req/min on /api/auth/register), the following endpoints have no Django-level throttling:

    • POST /api/token/ (JWT token obtain)
    • POST /api/auth/login/ (login)
    • POST /api/auth/send-reset-password-link/ (password reset)
    • POST /api/auth/change-password/ (password change)

    Nginx rate limiting is also broken because Cloudflare set_real_ip_from directives are all commented out (see H13).

    Remediation:

    REST_FRAMEWORK = {
    'DEFAULT_THROTTLE_CLASSES': [
        'rest_framework.throttling.AnonRateThrottle',
        'rest_framework.throttling.UserRateThrottle',
    ],
    'DEFAULT_THROTTLE_RATES': {
        'anon': '20/minute',
        'user': '60/minute',
    }
}

    H8: Password Change Doesn't Invalidate Existing Tokens¶

    Location api/views/views_auth.py:23-34
    CWE CWE-613 
    def post(self, request: Request) -> Response:
    serializer = self.get_serializer(data=request.data)
    ...
    user.set_password(serializer.validated_data['password'])
    user.save()
    return Response({'success': True, 'message': 'password_changed'})

    After a password change, all existing JWT tokens remain valid because: 1. The JWT payload only contains user_id (no password hash, no token version) 2. Tokens never expire (see C2) 3. Token revocation raises AuthTokenNotRevoked()

    If an account is compromised and the password is changed, the attacker's stolen token still works forever.

    Remediation: Implement a token version/generation counter on the User model. Increment on password change. Validate in JWTAuthentication.authenticate().

    H13: Nginx Rate Limiting Broken Behind Cloudflare¶

    Location infra/nginx/secure/default.conf.template:6-30

    All Cloudflare set_real_ip_from directives and real_ip_header CF-Connecting-IP are commented out:

    #set_real_ip_from 173.245.48.0/20;
...
#real_ip_header CF-Connecting-IP;

    Nginx rate limiting uses $binary_remote_addr, which behind Cloudflare resolves to Cloudflare's IP, not the client's. This means: - All users share the same rate limit bucket - Rate limiting is effectively disabled - A single user's traffic can exhaust the limit for all users

    Remediation: Uncomment the Cloudflare IP ranges and real_ip_header CF-Connecting-IP.

    H14: Open Redirect Vulnerability in Login View¶

    Location website/views.py:54-55
    CWE CWE-601 (URL Redirection to Untrusted Site)
    OWASP A01:2021 - Broken Access Control 
    next_url = request.GET.get('next', '/')
return redirect(next_url)

    The next parameter is taken directly from user input and used in a redirect without validation. An attacker can craft a URL like:

    https://ap.ad4x4.com/login/?next=https://evil.com/phishing

    After a victim logs in, they are redirected to the attacker's site, which can mimic the AD4x4 site to steal credentials or session tokens.

    Remediation:

    from django.utils.http import url_has_allowed_host_and_scheme

next_url = request.GET.get('next', '/')
if not url_has_allowed_host_and_scheme(next_url, allowed_hosts={request.get_host()}):
    next_url = '/'
return redirect(next_url)

    H15: No File Type Validation on Upload Fields¶

    Location Multiple models
    CWE CWE-434 (Unrestricted Upload of File with Dangerous Type)

    The project has 11 ImageField/FileField upload points across models: - Member.avatar — Only validates size (2.5 MB), not type - UpgradeRequest.attachment — No upload_to path, no validation at all - LogbookMigrationPDF.uploaded_pdf — FileField accepts any file type - TripReport.track_file — FileField accepts any file type - ClubNews.image, Feedback.image, Sponsor.image, Vehicle.image, Trip.image, TripReportImage.image

    While Django's ImageField uses Pillow to verify image headers, this can be bypassed with polyglot files (valid image + embedded script). The FileField instances have no content validation at all.

    The avatar clean() method only checks size:

    def clean(self):
    if self.avatar and self.avatar.size > 2.5 * 1024 * 1024:
        raise ValidationError("Avatar file size must be less than 2.5 MB.")

    Remediation: Add file type validation using django-upload-validator or custom validators. Enforce allowed MIME types. Serve uploaded files from a separate domain.

    H16: CSRF Exemption on PayPal Webhook Without Robust Alternative¶

    Location website/views.py:526
    CWE CWE-352 (Cross-Site Request Forgery) 
    @csrf_exempt
def paypal_webhook(request):

    The webhook endpoint has CSRF protection disabled. While this is standard for webhook receivers, the compensating control (PayPal signature verification) is conditional — it only runs if PAYPAL_WEBHOOK_ID is configured (see M4). Without it, any actor can send forged POST requests to this endpoint.

    Combined with the lack of IP allowlisting (PayPal webhook source IPs are well-documented), this creates a viable attack vector.

    Remediation: Make webhook signature verification mandatory (not optional). Add PayPal IP allowlisting as defense in depth.

    MEDIUM FINDINGS (13)¶

    M1: Every JWT Authentication Triggers Database Write¶

    Location api/util.py:93-95 
    # In JWTAuthentication.authenticate():
obj, created = NotificationSettings.objects.get_or_create(member=user)
obj.save()  # Triggers auto_now on last_user_activity

    Every single authenticated API request writes to the database. Under load, this creates: - Unnecessary database writes (potentially thousands/min) - Increased latency on every request - Lock contention on the notification_settings table

    Remediation: Use caching to batch updates, or update only once per hour per user.

    M2: USE_TZ = False Can Cause Token Timing Bugs¶

    Location ad4x4/settings.py:319

    USE_TZ = False means all datetimes are timezone-naive. This can cause: - Trip cutoff comparisons to fail across timezone boundaries - Token expiration checks (if implemented) to be off by hours - Inconsistent behavior during daylight saving time transitions

    M13: Raw SQL in GeocodingCache.truncate() Without Parameterization¶

    Location api/models/models_geocoding_cache.py:58-61
    CWE CWE-89 (SQL Injection) 
    @classmethod
def truncate(cls):
    table = cls._meta.db_table
    with connection.cursor() as cursor:
        cursor.execute(f'TRUNCATE TABLE "{table}" RESTART IDENTITY CASCADE;')

    While the table name comes from Django's model metadata (not user input) and is therefore not directly injectable, this use of raw SQL: - Bypasses Django's ORM safety net - Sets a risky pattern that developers may copy with user-supplied values - Is called from a signal (api/signals.py:170) that could be triggered unexpectedly

    Remediation: Use cls.objects.all().delete() instead, or if TRUNCATE is needed for performance, add a comment explaining why raw SQL is safe here.
