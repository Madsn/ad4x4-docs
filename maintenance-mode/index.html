    Maintenance Mode¶

    AD4x4 supports a maintenance toggle that responds to public app/API requests with 503 Service Unavailable and a short HTML page. The feature is implemented at the nginx layer, not in Django — so it keeps working even if the Django app or Huey workers are being restarted, migrated, or are otherwise unavailable. Django admin remains available during maintenance mode for operator access.

    How it works¶

    The nginx container inside the Docker Compose stack checks for a marker file on every incoming request:

    • If /etc/nginx/maintenance/maintenance_on exists → nginx returns 503 Service Unavailable with a Retry-After: 3600 header and a small HTML body for public app/API paths
    • /admin, /admin/..., and /static/admin/... bypass maintenance mode so operators can use Django admin while the public site is unavailable
    • API clients can bypass maintenance when the real client IP matches the external whitelist include file or the request sends the configured secret header
    • If the file is absent → traffic flows through to Django and the static locations as normal

    The marker and bypass include directory (nginx/maintenance/) is mounted as a shared volume between the host and the nginx container in infra/docker-compose.yml, so creating or removing the marker from the host is immediately visible to nginx. The nginx if (-f ...) check is re-evaluated per request, so a config reload isn't strictly required for the state change to take effect — but the maintenance toggle scripts run nginx -s reload anyway as a belt-and-braces measure so any in-flight keep-alive connections see a clean state. Bypass whitelist/secret changes are validated with NGINX_TEST_COMMAND and reloaded only after validation succeeds.

    The nginx block that implements the check lives in infra/nginx/secure/default.conf.template:

    map $uri $maintenance_uri_bypass {
    default 0;
    ~^/admin(?:/|$) 1;
    ~^/static/admin/ 1;
}

geo $maintenance_ip_bypass {
    default 0;
    include ${MAINTENANCE_BYPASS_IP_FILE};
}

map ${MAINTENANCE_BYPASS_HEADER_VARIABLE} $maintenance_header_bypass {
    default 0;
    include ${MAINTENANCE_BYPASS_SECRET_FILE};
}

map "$maintenance_ip_bypass:$maintenance_header_bypass" $maintenance_client_bypass {
    default 0;
    "1:0" 1;
    "0:1" 1;
    "1:1" 1;
}

map "$maintenance_uri_bypass:$maintenance_client_bypass" $maintenance_bypass {
    default 0;
    "1:0" 1;
    "0:1" 1;
    "1:1" 1;
}

set $maintenance_mode 0;
if (-f /etc/nginx/maintenance/maintenance_on) {
    set $maintenance_mode 1;
}
if ($maintenance_bypass = 1) {
    set $maintenance_mode 0;
}
if ($maintenance_mode = 1) {
    return 503;
}
error_page 503 @maintenance;
location @maintenance {
    default_type text/html;
    add_header Retry-After 3600;
    return 503 '<html><body><h1>Maintenance</h1><p>We&#39;ll be back soon.</p></body></html>';
}

    Because the if blocks are at the server {} level and run before location routing, public API endpoints, uploads, Swagger UI, and frontend assets are blocked in one sweep. The explicit maintenance_uri_bypass map keeps Django admin and its static files available. The client bypass is separate and allows either maintenance_ip_bypass=1 or maintenance_header_bypass=1.

    The nginx proxy locations set X-Maintenance-Bypass-Granted from nginx's own $maintenance_bypass value before proxying to Django. Nginx overwrites any client-supplied value; Django must treat it only as optional audit/logging context, never as authentication.

    API bypass files¶

    The whitelist and secret are operational files, not Git-tracked source. The tracked examples live at:

    infra/nginx/maintenance/bypass_ips.conf.example
infra/nginx/maintenance/bypass_secret.conf.example

    The production files are ignored by Git:

    infra/nginx/maintenance/bypass_ips.conf
infra/nginx/maintenance/bypass_secret.conf

    The nginx container sees them through the /etc/nginx/maintenance bind mount. The host monitor bot writes the host paths, so infra/.env and /opt/ad4x4-monitor-bot/.env intentionally use different path values for the same setting:

    # nginx container env
MAINTENANCE_BYPASS_IP_FILE=/etc/nginx/maintenance/bypass_ips.conf
MAINTENANCE_BYPASS_SECRET_FILE=/etc/nginx/maintenance/bypass_secret.conf
MAINTENANCE_BYPASS_HEADER_VARIABLE='$http_x_maintenance_bypass'

# monitor bot host env
MAINTENANCE_BYPASS_IP_FILE=/home/admin/ad4x4/infra/nginx/maintenance/bypass_ips.conf
MAINTENANCE_BYPASS_SECRET_FILE=/home/admin/ad4x4/infra/nginx/maintenance/bypass_secret.conf

    Whitelist file format:

    # comments and blanks are allowed
203.0.113.10/32 1;
198.51.100.0/24 1;
2001:db8::1/128 1;

    Single IPv4 addresses are normalized to /32, and single IPv6 addresses to /128. Duplicate normalized CIDRs are not added.

    Secret file format when enabled:

    ~^example\-maintenance\-bypass\-secret\-32\-plus$ 1;

    The enabled entry is a case-sensitive anchored nginx map regex. This avoids nginx literal map key case folding, so only the exact secret value matches.

    Secret file format when disabled:

    # Maintenance bypass header secret disabled.
# No header value is accepted.

    The disabled state must be comments or blanks only. Do not write "" 1;; a blank header must never match.

    Telegram management¶

    The host monitor bot manages the bypass files with these commands:

    /maintenance_ip_add <ip-or-cidr>
/maintenance_ip_list
/maintenance_ip_remove <ip-or-cidr>
/maintenance_ip_purge confirm
/maintenance_secret_set <secret>
/maintenance_secret_clear confirm

    Users listed in TELEGRAM_ADMIN_USER_IDS or TELEGRAM_PRIVILEGED_USER_IDS can run these maintenance-bypass commands. Use TELEGRAM_ADMIN_USER_IDS to grant bypass management without granting deploy/restart privileges. Unauthorized attempts reply exactly Unauthorized. and are logged. The commands write files atomically, run NGINX_TEST_COMMAND, reload with NGINX_RELOAD_COMMAND only if validation succeeds, and roll back file changes when validation fails. Secret replies and logs do not include the full secret.

    Enabling maintenance mode¶

    From the production host, with shell access as admin:

    cd /home/admin/ad4x4/infra
./enable_maintenance_mode.sh

    The script creates the marker file and reloads nginx:

    #!/bin/bash
touch ./nginx/maintenance/maintenance_on
docker exec nginx nginx -s reload

    The site starts returning 503 immediately. Verify from another machine:

    curl -I https://ap.ad4x4.com/
# HTTP/2 503
# retry-after: 3600

    Disabling maintenance mode¶

    From the production host:

    cd /home/admin/ad4x4/infra
./disable_maintenance_mode.sh

    The script removes the marker file and reloads nginx:

    #!/bin/bash
rm ./nginx/maintenance/maintenance_on
docker exec nginx nginx -s reload

    Normal traffic resumes immediately.

    Why nginx instead of a Django middleware¶

    Putting the maintenance gate at nginx rather than a Django middleware has two operational advantages:

    • Nothing in Django needs to be running. The 503 is served even if the Django container is stopped, the database is mid-migration, Huey is stuck, or a release has just unhealthy-checked out. Those are the exact scenarios where maintenance mode matters most.
    • No request ever reaches Django during maintenance, so there is no database load and no risk of side effects from partially processed requests.

    The trade-off is that there is no way for API clients to negotiate a structured maintenance window — the body is a static HTML page, not a JSON envelope with Retry-After metadata or a message key. Clients should match on 503 + Retry-After header to detect the state.

    Client behaviour¶

    The mobile app and web clients should treat 503 responses during any request as a transient maintenance state and:

    1. Show a "We'll be back soon" screen with a manual retry affordance.
    2. Back off for at least the duration in the Retry-After header (currently 3600 seconds).
    3. Do not send these to Sentry / error reporting — they are expected operational states, not bugs, and will drown real errors.

    Gotchas¶

    • The marker and bypass files are on the production host, not in the Django database. There is no API endpoint to enable/disable maintenance or manage bypass access. These are ops-level actions performed with shell access or the restricted host monitor bot commands.
    • Static files under /static/ are blocked except /static/admin/. Admin static files stay available so Django admin remains usable. Frontend assets stay blocked because we do not want the public app UI to render half-loaded while the backend is unavailable.
    • There is no Django-level maintenance toggle. ConfigurableSettings does not have a maintenance_mode_enabled field, and there is no custom Django middleware for this purpose. Do not try to add one — the nginx-based flow is the authoritative mechanism, and a duplicate toggle would split-brain the state.
    • nginx -s reload is a belt-and-braces step. The if (-f ...) check is re-evaluated on every request even without reloading, but the reload guarantees all worker processes agree on the new state for in-flight keep-alive connections.
    • The Huey worker container is unaffected by maintenance mode — scheduled tasks and background notifications continue to run. If you need to stop Huey as well, that's a separate docker compose stop huey action.
