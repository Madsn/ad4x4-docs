    Maintenance Mode¶

    AD4x4 supports a maintenance toggle that responds to public app/API requests with 503 Service Unavailable and a short HTML page. Since the Unraid → OVH hosting migration retired nginx (Coolify-managed Traefik is now the reverse proxy / TLS terminator), the gate is implemented as a Django middleware — api.maintenance.MaintenanceModeMiddleware — rather than in the proxy. Django admin remains available during maintenance mode for operator access.

    History: This used to be an nginx-layer feature (infra/nginx/secure/default.conf.template). Traefik has no drop-in equivalent of nginx's "reload on file touch" gate, and under Coolify we don't hand-edit Traefik's config. Per the decision on #311 (and consistent with #310 moving real-IP handling into Django), the gate now lives in Django. The nginx files are kept for now as the rollback target until nginx is fully retired.

    How it works¶

    The middleware runs early in the stack (right after SecurityMiddleware, before session/DB middleware) and checks for a marker file on every request:

    • If the marker file at MAINTENANCE_MARKER_FILE exists → the middleware returns 503 with a Retry-After: 3600 header and a small HTML body for public app/API paths.
    • /admin, /admin/..., and /static/admin/... bypass maintenance mode so operators can use Django admin while the public site is unavailable.
    • Requests bypass maintenance when the real client IP matches the allowlist file or the request sends the configured secret header (X-Maintenance-Bypass).
    • If the marker is absent → traffic flows through as normal.

    The marker check is re-evaluated per request, so creating or removing the marker on the mounted volume flips the state immediately — no redeploy and no proxy reload required. If MAINTENANCE_MARKER_FILE is unset the middleware disables itself entirely (MiddlewareNotUsed), so local/dev is unaffected.

    The 503 body is byte-identical to the old nginx one so the Flutter app is untouched (its MaintenanceOverlay extracts the first <p>):

    <html><body><h1>Maintenance</h1><p>We&#39;ll be back soon.</p></body></html>

    Dev bypass (no app change)¶

    The bypass mechanism the app already speaks (X-Maintenance-Bypass: <secret>, added in #116) is preserved. The ApiClient interceptor injects this header on every request (including token refresh), so devs keep access during a maintenance window with no app change — the middleware just needs to (a) still return 503 + Retry-After + the same HTML, and (b) check that same header. Both hold.

    Configuration¶

    Set these in the app's environment (infra/.env / Coolify):

    # Presence of this file toggles maintenance mode. Point it at a mounted volume
# so it survives container restarts and can be toggled without a redeploy.
MAINTENANCE_MARKER_FILE=/data/maintenance/maintenance_on

# Optional bypass files (read live on each request, so the monitor bot can
# rotate them without a redeploy). Omit to disable that bypass mechanism.
MAINTENANCE_BYPASS_IP_FILE=/data/maintenance/bypass_ips.conf
MAINTENANCE_BYPASS_SECRET_FILE=/data/maintenance/bypass_secret.conf

# Optional overrides (defaults shown).
MAINTENANCE_BYPASS_HEADER=X-Maintenance-Bypass
MAINTENANCE_RETRY_AFTER=3600

    If MAINTENANCE_MARKER_FILE is empty/unset, the middleware is inert.

    Bypass files¶

    The allowlist and secret are operational files, not Git-tracked source. Tracked examples live at infra/nginx/maintenance/bypass_ips.conf.example and bypass_secret.conf.example. The real files must not be committed.

    IP allowlist — one IP or CIDR per line; # comments and blank lines are ignored:

    # comments allowed
203.0.113.10/32
198.51.100.0/24
2001:db8::1/128

    Bare IPv4/IPv6 addresses and CIDRs are both accepted. The client IP is resolved preferring Cloudflare's Cf-Connecting-Ip (matching #310), then leftmost X-Forwarded-For, then REMOTE_ADDR.

    Trust assumption: the IP allowlist trusts Cf-Connecting-Ip / X-Forwarded-For directly (the #310 decision), so it assumes Traefik/Cloudflare is the only path to the origin. Anyone able to reach the origin directly could spoof an allowlisted IP to bypass the maintenance gate — this only unlocks a temporary maintenance page, no data access, but keep the origin firewalled to the proxy.

    Secret — one secret per line (the whole line is the literal secret):

    super-secret-maintenance-token-at-least-32-chars

    An empty/comment-only file means no secret is accepted (bypass-by-header disabled). Never write a blank secret.

    Legacy compatibility: the middleware also accepts the old nginx file formats the Telegram monitor bot currently writes — <CIDR> 1; allowlist entries and ~^<re.escape(secret)>$ 1; secret entries (matched as an anchored regex, faithfully reproducing nginx). So the existing bot output keeps working during the transition. Simplifying the bot to the plain format above (and dropping its nginx -s reload step) is a follow-up.

    Telegram management (old VPS only — not deployed on the box)¶

    infra/monitor-bot still runs on the old VPS as a rollback target, but was deliberately not carried over to the box (it assumes the old VPS's git-checkout + docker-compose model — see "Provisioning on the box" below). On the box, manage the bypass files by hand over SSH instead. Where the bot is still running, it manages the bypass files:

    /maintenance_ip_add <ip-or-cidr>
/maintenance_ip_list
/maintenance_ip_remove <ip-or-cidr>
/maintenance_ip_purge confirm
/maintenance_secret_set <secret>
/maintenance_secret_clear confirm

    Users in TELEGRAM_ADMIN_USER_IDS / TELEGRAM_PRIVILEGED_USER_IDS may run these. The bot still writes the same files (now read by Django); because Django re-reads them per request, the bot's NGINX_TEST_COMMAND / NGINX_RELOAD_COMMAND steps are no longer needed and should be dropped when the bot is next touched (follow-up).

    Provisioning on the box (Coolify)¶

    Django on the box is a Coolify Docker Image resource deployed straight from a pinned ghcr.io digest — there is no docker-compose stack driven by this repo's infra/ directory, and Coolify regenerates the app's real env file (/data/coolify/applications/<uuid>/.env) itself, so infra/.env in a checkout is never read by anything running on the box. The marker/bypass paths only work once they're backed by a Coolify Storage bind mount, the same pattern already used for the /app/uploads media volume:

    1. On the host: mkdir -p /opt/ad4x4/django-maintenance && chown 1000:1000 /opt/ad4x4/django-maintenance && chmod 750 /opt/ad4x4/django-maintenance (uid 1000 because Django's container runs as non-root appuser, same as the media bind mount).
    2. Coolify UI → the Django app → Storages → add a bind mount: /opt/ad4x4/django-maintenance (host) → /data/maintenance (container).
    3. Coolify UI → the Django app → Environment Variables: MAINTENANCE_MARKER_FILE=/data/maintenance/maintenance_on MAINTENANCE_BYPASS_IP_FILE=/data/maintenance/bypass_ips.conf MAINTENANCE_BYPASS_SECRET_FILE=/data/maintenance/bypass_secret.conf Huey doesn't serve HTTP, so it doesn't need these vars — Django only.
    4. Redeploy Django (rollback = redeploy the previous digest, Coolify keeps deployment history). Confirm the boot log is clean and docker exec <container> ls -la /data/maintenance shows the writable directory.
    5. Deploy infra/enable_maintenance_mode.sh / disable_maintenance_mode.sh to /opt/ad4x4/scripts/ on the box (750, root) — same location convention as scripts/box/redeploy-backend.sh in the ops repo.

    This is an AMBER change (mutating but reversible) per the ops repo's docs/RULES_OF_ENGAGEMENT.md — write a working note + verify live before/after.

    Enabling / disabling maintenance mode¶

    The marker is a file on the Coolify bind mount — create it to enable, remove it to disable. Because the host path and the container path are the same file once the bind mount above is in place, the scripts never need to reach into the container:

    MAINTENANCE_MARKER_FILE=/opt/ad4x4/django-maintenance/maintenance_on \
  /opt/ad4x4/scripts/enable_maintenance_mode.sh

    Verify from another machine:

    curl -I https://ap.ad4x4.com/
# HTTP/2 503
# retry-after: 3600

    Disable with disable_maintenance_mode.sh (same env). Normal traffic resumes on the next request. You can also just touch / rm the marker directly (Coolify terminal, or straight on the host since it's a bind mount).

    No Telegram monitor bot runs on the box — infra/monitor-bot was evaluated and dropped for this migration (it assumes the old VPS's git-checkout + docker-compose model; see docs/working-notes/claude-21-backend-migration.md in the ops repo). Until/unless a box-native bot exists, toggling maintenance mode and editing the bypass files is a manual SSH operation, not a Telegram command. (On the old VPS, where the bot still runs, its /maintenanceon//maintenanceoff commands invoke these same scripts via sudo -n -u root against the docker-compose stack — not applicable on the box.)

    Availability trade-off (deliberate)¶

    nginx served the branded 503 even if Django/Huey/Postgres were fully down, because it was the proxy. A Django-side gate can't paint the branded page if Django itself is completely stopped. This was an accepted trade-off on #311:

    • A file marker still works with the database down or mid-migration — the middleware only reads a file, touches no DB. Planned maintenance / deploys keep Django up, which is the real use case.
    • If the app tier is fully stopped, Traefik/Coolify still returns a plain (unbranded) 503, so clients still see a 503 and back off — they just don't get the branded HTML.
    • The dev bypass never needed the "survives-down" property: it only ever grants access when Django is up anyway.

    If a branded 503 during a total outage is ever required, the right home is the Cloudflare edge (a WAF custom-response or a Worker + KV flag), not the app tier — tracked separately if wanted.

    Client behaviour¶

    Clients should treat 503 on any request as a transient maintenance state and:

    1. Show a "We'll be back soon" screen with a manual retry affordance.
    2. Back off for at least the Retry-After duration (currently 3600 seconds).
    3. Do not send these to Sentry / error reporting — they are expected operational states, not bugs.

    Gotchas¶

    • The marker and bypass files live on the mounted volume, not the Django database. There is no API endpoint to toggle maintenance or manage bypass access — these are ops-level actions (shell / docker exec / Coolify terminal / the restricted monitor-bot commands).
    • Django is now the single source of truth for maintenance state. Earlier revisions of this doc warned against a Django-side toggle — that warning existed to avoid split-brain with the nginx gate. With nginx retired, Django is the authority and that objection no longer applies. There is still no ConfigurableSettings.maintenance_mode_enabled DB field, and one should not be added: the marker file is intentionally out-of-band so maintenance works even when the DB is unavailable.
    • Static files under /static/ are gated except /static/admin/, so admin stays usable while the public app UI is held back.
    • The middleware self-disables when MAINTENANCE_MARKER_FILE is unset — expected in local/dev and CI.
    • The Huey worker is unaffected by maintenance mode — background tasks keep running. Stop Huey separately if needed.
